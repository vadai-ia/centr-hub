# ERRORES.md — Bugs conocidos, workarounds y lecciones del proyecto Centr Hub

> Documento vivo. Cada bug descubierto durante un milestone se documenta aquí antes del commit final del milestone. Permite a milestones posteriores no repetir los mismos errores.

## Estructura de cada entrada

Cada entrada documenta UN bug o lección con la siguiente estructura:

- **Título:** descripción corta del problema.
- **Milestone donde se detectó:** M0, M1, M2, ...
- **Síntoma:** qué se observó.
- **Causa raíz:** qué lo provocó.
- **Workaround / fix:** cómo se resolvió o cómo evitarlo.
- **Lección:** principio general que aplica a milestones futuros.

(Formato y ejemplos ilustrativos en Sección 10.4 de la doctrina, `CENTR-DOCTRINE-v5.md`.)

## Entradas

### RETURNING INTO variable escalar con INSERT multi-fila falla en PL/pgSQL

- **Milestone donde se detectó:** M1.
- **Síntoma:** función `bootstrap_organization` fallaba con `ERROR: P0003: query returned more than one row` en la línea del INSERT de 7 etapas Funnel Venta.
- **Causa raíz:** `INSERT ... VALUES (multi-fila) RETURNING id INTO variable_escalar` es inválido en PL/pgSQL — una variable escalar solo puede recibir 1 fila. Para casos multi-fila se requiere `RETURNING ... BULK COLLECT INTO arr` o, como en este caso, eliminar la cláusula RETURNING si no se necesita.
- **Workaround / fix:** se eliminó la cláusula `RETURNING ... INTO` del INSERT multi-fila. Los IDs de las etapas se recuperan inmediatamente después por nombre con `SELECT ... INTO ...`, que era la lógica funcional. La línea problemática era redundante.
- **Lección:** cuando un INSERT inserta múltiples filas y la lógica posterior necesita los IDs, NO usar `RETURNING ... INTO variable_escalar`. Opciones válidas: (a) recuperar por columna única posterior con SELECT, (b) usar `RETURNING ... BULK COLLECT INTO array`, (c) hacer INSERTs uno por uno con su propio RETURNING. La opción (a) es legible y suficiente cuando ya hay un identificador único como `name + organization_id + funnel`.

### Flujo de invitación incompleto — hash fragment vs PKCE en Supabase Auth

- **Milestone donde se detectó:** M2 (fix post-entrega).
- **Síntoma:** click en el email de invitación de Supabase redirigía al usuario a `/login` sin mostrar ninguna pantalla para definir contraseña. La activación de cuenta nunca se completaba.
- **Causa raíz:** `app/auth/callback/route.ts` (Route Handler) sólo manejaba el flujo PKCE — tokens llegando como `?code=`. Supabase envía las invitaciones (y password recovery) en flujo implícito: los tokens llegan como `#access_token=...&refresh_token=...&type=invite` (hash fragment). Los hash fragments son **client-side only** — el servidor nunca los recibe. El Route Handler veía la request sin `?code=`, caía al catch-all, y redirigía a `/login?error=link_expired`.
- **Workaround / fix:**
  1. **Route Handler actualizado:** si no hay `?code=`, devuelve un HTML mínimo con `<script>window.location.replace('/auth/confirm'+window.location.hash)</script>`. El script ejecuta en el navegador y redirige a `/auth/confirm` preservando el hash fragment (que el servidor nunca habría visto). `window.location.replace` evita que `/auth/callback` quede en el historial del navegador.
  2. **Nueva página `/auth/confirm`** (`app/(auth)/auth/confirm/page.tsx`): Client Component que parsea el hash en `useEffect`. Para `type=invite` o `type=recovery` renderiza un formulario para definir contraseña (validación mínima 8 caracteres + confirmación). Llama `supabase.auth.setSession()` con los tokens del hash y luego `supabase.auth.updateUser({ password })`. Para `type=magiclink`/`email` establece sesión y redirige al dashboard. Edge cases: hash vacío, error en hash, tokens expirados — todos muestran mensaje en español con link a `/login`.
  3. **Middleware actualizado:** `/auth/confirm` agregado a `PUBLIC_ROUTES`.
- **Lección (parte 1 — Route Handler):** Supabase Auth tiene **dos flujos distintos en Next.js App Router**: (a) **PKCE** (`?code=` → `exchangeCodeForSession` en Route Handler o Server Component) y (b) **Implícito** (`#access_token=` → sólo accesible client-side). Las invitaciones y password recovery de Supabase usan el flujo implícito con hash fragment. Un Route Handler nunca puede manejarlos directamente. La técnica correcta es servir desde el Route Handler un HTML mínimo que haga el redirect client-side con `window.location.replace`, preservando el hash. La nueva página `/auth/confirm` actúa como landing unificado para todos los flujos de hash.
- **Lección (parte 2 — Site URL como landing):** `/auth/confirm` sólo recibe tokens si Supabase está configurado con una URL específica como redirect (ej. `redirect_to=/auth/callback`). Cuando el Site URL de Supabase es la raíz del dominio (`http://localhost:3000`), las invitaciones aterrizan en `/login#access_token=...` — la página de login ignora el hash y el flujo muere silenciosamente. **Fix:** `LoginForm` (`components/auth/login-form.tsx`) detecta en `useEffect` si `window.location.hash` contiene `access_token`; si es así, hace `window.location.replace('/auth/confirm' + hash)` antes de renderizar el formulario (`ready` state en `false` evita que el form flashee). No basta con tener `/auth/confirm` aislado: cualquier página pública a la que Supabase pueda redirigir debe también interceptar el hash.

### Validador de env falla en startup por variables opcionales definidas vacías en .env.local

- **Milestone donde se detectó:** M2 (fix post-entrega).
- **Síntoma:** la app falla al arrancar con `Variables de entorno server inválidas: ...` señalando `SHOPIFY_WEBHOOK_SECRET` y/o `WHAAPY_API_KEY`. Estas variables están en `.env.local` como `SHOPIFY_WEBHOOK_SECRET=` (vacías a propósito, pendientes de M3).
- **Causa raíz:** `z.string().min(1).optional()` en Zod NO es equivalente a "ausente o no vacío". `.optional()` permite `undefined` (campo ausente), pero cuando la variable SÍ existe en el entorno como cadena vacía `""`, Zod la ve como presente y aplica `.min(1)` — que falla. En `.env.local`, `VARIABLE=` sin valor se expande como `""` en `process.env`, no como `undefined`.
- **Workaround / fix:** cambiar a `z.string().optional()` (sin `.min(1)`) para las dos variables de entrada diferida. El startup validator solo exige que, si están presentes, sean strings — sin restricción de longitud. Para proteger el uso en runtime, se agregan helpers de acceso tardío `getShopifyWebhookSecret()` y `getWhaapyApiKey()` en `lib/env.ts`: lanzan un error descriptivo con contexto de milestone cuando la variable está vacía o ausente. M3+ debe usar estos helpers en lugar de leer `getServerEnv().SHOPIFY_WEBHOOK_SECRET` directamente.
- **Lección:** en proyectos con milestones incrementales, distinguir entre dos categorías de variables en el schema de Zod: (a) **siempre requeridas** — `z.string().min(1)` sin `.optional()`, falla en startup si faltan; (b) **requeridas desde milestone X** — `z.string().optional()` en startup + helper de acceso que valida en runtime. La validación tardía es preferible a eliminar la protección: el error sigue siendo descriptivo, pero no bloquea arranques legítimos en milestones anteriores. Antipatrón a evitar: `z.string().min(1).optional()` — comunica "no vacío si presente" pero la semántica de startup es confusa cuando `.env.local` define la variable como vacía.

### search_path mutable en funciones PL/pgSQL sin SET search_path

- **Milestone donde se detectó:** M2 (post-entrega, Supabase Security Advisor).
- **Síntoma:** Security Advisor reportó "Function has a mutable search_path" para `tg_set_updated_at`, `current_organization_id`, `assert_organization_context` y `tg_block_mutation`.
- **Causa raíz:** Las funciones PL/pgSQL sin `SET search_path` heredan el `search_path` de la sesión en el momento de ejecución. Un atacante con permisos para alterar el `search_path` de la sesión puede hacer que la función resuelva tablas o funciones de un schema malicioso en lugar del `public` esperado.
- **Workaround / fix:** `ALTER FUNCTION public.<nombre>() SET search_path = public;` en migración nueva idempotente (0011). Para funciones SECURITY DEFINER el riesgo es mayor — pero las del proyecto ya tenían `set search_path` en el cuerpo o como opción de función (`is_member_of`, `bootstrap_organization`); el fix de 0011 cubre las que faltaban.
- **Lección:** Toda función PL/pgSQL debe declarar `SET search_path = public` (o el schema relevante) como **opción de función**, no como primera sentencia del `$$` body. La forma idiomática es: `create or replace function public.myfn() returns void language plpgsql set search_path = public as $$ ... $$;` — el `SET search_path` va entre el `language` y el `as $$`. Si se omite en el `CREATE FUNCTION`, corregir con `ALTER FUNCTION ... SET search_path = public;` en una migración posterior.

### SECURITY DEFINER callable externally — PostgREST expone funciones con EXECUTE en PUBLIC

- **Milestone donde se detectó:** M2 (post-entrega, Supabase Security Advisor).
- **Síntoma:** Security Advisor reportó "Function is callable by PUBLIC" para `bootstrap_organization` e `is_member_of`. También reportó `rls_auto_enable` — que resultó ser una función Supabase-interna, no una función custom del proyecto.
- **Causa raíz:** PostgREST (la capa REST de Supabase) expone como endpoint `/rest/v1/rpc/<nombre>` toda función sobre la que PUBLIC (o cualquier rol equivalente) tenga EXECUTE. Las funciones SECURITY DEFINER expuestas así son un riesgo porque cualquier cliente anónimo puede invocarlas con los privilegios elevados del owner.
- **Workaround / fix (intento 1, migración 0011 — INCOMPLETO):** `REVOKE EXECUTE ON FUNCTION ... FROM PUBLIC; GRANT EXECUTE ... TO <roles>;`. Aplicado en migración 0011. **Resultado: no silenció los warnings.** Ni la migración ni un fix manual posterior del operador (también solo REVOKE FROM PUBLIC) movieron la aguja en Security Advisor.
- **Workaround / fix (intento 2, migración 0012 — DEFINITIVO):** REVOKE explícito de `PUBLIC, anon, authenticated`. Para `bootstrap_organization`: GRANT solo a `service_role`. Para `rls_auto_enable` (no definida en migraciones propias — la creó Supabase): DO block que itera `pg_proc` para aplicar el patrón a todas las sobrecargas existentes. Para `is_member_of`: warning intencional — `anon` y `authenticated` DEBEN conservar EXECUTE para que RLS funcione (ver decisión arquitectónica en 0012). Aplicado en migración 0012.
- **Lección (causa del intento 1 fallido):** Supabase configura por defecto `ALTER DEFAULT PRIVILEGES IN SCHEMA public GRANT EXECUTE ON FUNCTIONS TO anon, authenticated`. Estos grants son **separados** del grant a `PUBLIC` — `REVOKE FROM PUBLIC` NO los toca. PostgREST sigue exponiendo la función como RPC porque `anon`/`authenticated` retienen EXECUTE vía sus grants explícitos. Patrón siempre erróneo: `REVOKE ... FROM PUBLIC` solo. Patrón correcto: `REVOKE ... FROM PUBLIC, anon, authenticated` + GRANT explícito a los roles que realmente lo necesitan.
- **Lección (warnings residuales intencionales):** Funciones SECURITY DEFINER usadas en RLS policies (como `is_member_of`) NO pueden tener `anon`/`authenticated` revocados — las policies fallarían con "permission denied for function". Security Advisor seguirá reportándolas como "callable by anon/authenticated"; documentar como deuda consciente en CLAUDE.md y omitir. Alternativas (SECURITY INVOKER, mover a schema privado) son invasivas y aportan poco frente al riesgo real, dado que la función solo retorna boolean y consulta tablas con RLS propio.
- **Lección (functions desconocidas reportadas por Advisor):** Si Security Advisor reporta una función no encontrada en migraciones propias (caso `rls_auto_enable`), probablemente es función Supabase-interna o de extension/template. NO crear migración con signature asumida — usar DO block + `pg_proc` para descubrir signatures reales y aplicar REVOKE/GRANT a las que existan. El patrón está en migración 0012.

### Protected Customer Data malinterpretado — Custom Apps tienen acceso automático

- **Milestone donde se detectó:** M2 (post-entrega, durante setup de credenciales reales de Shopify).
- **Síntoma:** documentación en CLAUDE.md afirmaba que los scopes `read_customers`, `write_customers` y `read_all_orders` requerían aprobación formal de Shopify antes de operar — Protected Customer Data Form para los dos primeros y request manual en Partner Dashboard para `read_all_orders`. La consecuencia implícita era bloqueo de la sincronización real de contactos en M3 contra la tienda de Centr y del backfill completo de M11 hasta que Shopify aprobara solicitudes externas.
- **Causa raíz:** confusión entre dos categorías distintas de apps Shopify. Los formularios de Protected Customer Data y el request manual de `read_all_orders` aplican **únicamente a apps publicadas en el Shopify App Store** (distribución pública, instalación masiva). Las **Custom Apps creadas en el Dev Dashboard e instaladas por organización vía OAuth** (modelo de Centr Hub) tienen acceso automático a Protected Customer Data Levels 1 y 2 y a `read_all_orders` — el consentimiento del merchant se otorga al aprobar los scopes durante la instalación, no por trámite externo. El malentendido se introdujo al documentar el "Setup post-M2" sin distinguir estos dos modelos.
- **Workaround / fix:** sección "Scopes protegidos de Shopify" en CLAUDE.md reescrita para clarificar el modelo Custom App y explicitar que los scopes están operativos al instalar la app. Nota equivalente en "Alcance del backfill inicial" corregida — M11 no está bloqueado por aprobación pendiente. Si la query de customers u orders devuelve vacío en producción, se trata como bug a investigar (token mal obtenido, scope omitido en la lista solicitada, rechazo silencioso en la instalación), no como restricción regulatoria.
- **Lección:** para proyectos Shopify, distinguir desde el primer milestone entre dos modelos de distribución:
  - **Custom Apps** (Dev Dashboard, instalación 1-a-1 vía OAuth por organización): scopes protegidos operativos al instalar, sin trámite externo. Modelo SaaS multi-tenant típico, aplica a Centr Hub.
  - **Apps públicas del App Store** (distribución masiva, store-listing): scopes protegidos requieren Protected Customer Data Form y, para `read_all_orders`, request manual con justificación en Partner Dashboard.
  - La documentación de Shopify mezcla los dos modelos en páginas adyacentes sin etiquetarlos siempre con claridad. Antes de documentar restricciones operativas o bloqueos a milestones futuros, verificar explícitamente bajo qué modelo opera la app. El disparador de esta corrección fue el cuestionamiento operativo del operador ("¿por qué necesitaríamos un trámite externo si la app es 1-a-1?") durante el setup post-M2 — ese tipo de pregunta es la señal correcta para revisar el supuesto.

### Cancelado ≠ Perdido — la cancelación administrativa NO debe mapearse a etapa `is_lost`

- **Milestone donde se detectó:** M3 (corrección post-entrega).
- **Síntoma:** El worker `draft_orders/delete` movía la oportunidad cuya Draft Order fue eliminada en Shopify a la etapa `is_lost` ("Perdida"). Esto contamina win rate del vendedor: cada DO borrado por error/duplicado/auto-borrado de Shopify tras 1 año contaba como pérdida comercial real. Un vendedor con muchos DOs de ciclo largo (>1 año, auto-borrados por Shopify) y un admin que limpia duplicados generaban pérdidas falsas masivas que NO eran culpa del vendedor.
- **Causa raíz:** El diseño inicial de M3 mapeaba el delete de Shopify al concepto "pipeline" más cercano del Funnel Venta (etapa Perdida). Pero "Perdida" en la doctrina significa transición real del pipeline (vendedor compitió y perdió contra precio/competencia/ghosting → requiere motivo, impacta win rate). Una cancelación administrativa no es lo mismo: no hubo competencia comercial, no requiere motivo, no debe impactar métricas. El modelo conceptual exigía un side-flag independiente de la etapa, no una transición.
- **Workaround / fix:** Migración 0014 agrega columnas `cancelled_at`, `cancellation_source`, `cancellation_note` a `opportunities` + índice parcial `WHERE cancelled_at IS NULL` para el pipeline activo. Worker `draft_orders/delete` ahora invoca `cancelOpportunity(...)` que marca el side-flag SIN transitar de etapa y SIN insertar en `opportunity_stage_history` (no hubo cambio de etapa — la etapa actual se preserva como auditoría de "dónde estaba al cancelarse"). `listOpportunities(...)` excluye canceladas por default; opt-in explícito con `includeCancelled` o `onlyCancelled`. CLAUDE.md sección "Cancelación de oportunidades — modelo independiente de etapa" documenta el contrato para M5/M6/M10. Win rate del dashboard (M10) debe usar el filtro default — denominador = Ganadas + Perdidas SIN canceladas.
- **Lección:** "Borrado externo del proveedor" NO equivale a "transición del pipeline" en sistemas con métricas operativas sensibles al funnel. Cuando un evento externo dispara un side-effect que parece encajar en una etapa existente, validar la **semántica** primero: ¿qué pregunta operativa responde esa etapa? Si la respuesta es "el vendedor perdió comercialmente", entonces eventos administrativos NO deben mapear ahí — necesitan un dimensión independiente (cancelled_at, archived_at, deleted_at) que vive al lado de stage_id pero no lo reemplaza. Patrón aplicable también a (futuro): "snoozed" no es etapa, "archivado por inactividad" no es etapa, "duplicado fusionado" no es etapa. Cada uno son flags ortogonales con sus propias queries de exclusión por default.

### Inngest v4 quitó `EventSchemas` y la signature de `createFunction` cambió

- **Milestone donde se detectó:** M3.
- **Síntoma:** El typecheck falló con `Module '"inngest"' has no exported member 'EventSchemas'` y `Expected 2 arguments, but got 3` al pasar `{ id }, { event }, handler` a `inngest.createFunction(...)`. La documentación pública mencionaba EventSchemas pero la versión instalada (4.4.0) ya no lo exporta.
- **Causa raíz:** Inngest SDK v4 reorganizó la tipificación de eventos. (a) El export `EventSchemas` desapareció — los schemas ahora se aplican **por-trigger** vía `schema: StandardSchemaV1<...>` o se asume `unknown` y se castea en runtime. (b) `createFunction` ahora acepta **2 argumentos**: `(opts, handler)`, donde `opts` incluye `triggers: [{ event: "..." }]`. La firma vieja `(opts, trigger, handler)` ya no existe.
- **Workaround / fix:** (1) Eliminar el generic `Inngest<{ schemas: EventSchemas }>` del cliente — usar `new Inngest({ id })` sin tipos de eventos. (2) Cada función pasa `triggers: [{ event: "topic/name" }]` dentro de las opciones. (3) En el handler, `event.data` queda tipado como `unknown` — castear explícitamente a `ShopifyWebhookEnvelope` al inicio: `const envelope = event.data as unknown as ShopifyWebhookEnvelope;`. Aceptable porque hay UN único productor (endpoint webhook) que construye el envelope antes de `inngest.send`.
- **Lección:** En SDKs que evolucionan rápido (Inngest sube versiones mayores con frecuencia), preferir patrones de tipificación **runtime-castable** sobre type-system fuerte cuando hay un productor único bien controlado. El cast manual es explícito y resistente a cambios de API; el generic tightly-coupled rompe con cada bump. Para validar correctitud, escribir tests sintéticos del productor que validan el shape del envelope antes de enviarlo a Inngest.

### `Insertable<R>` espera todos los campos no-auto-generados — defaults SQL no eximen al TS

- **Milestone donde se detectó:** M3.
- **Síntoma:** Cada `createContact(...)` y `createOpportunity(...)` falló typecheck con `Property 'X' is missing in type '{...}'` para campos como `assigned_advisor_id`, `whaapy_contact_id`, `deleted_in_shopify`, `parent_opportunity_id`, `probability_override`, etc. Aunque la BD tiene `default false`/`default null` para esos campos, el TS hand-written `Insertable<R>` solo marca `id`, `created_at`, `updated_at` como opcionales.
- **Causa raíz:** El tipo `Insertable<R>` definido en `lib/types/database.ts` es: `Omit<R, "id" | "created_at" | "updated_at"> & Partial<Pick<R, "id" | "created_at" | "updated_at">>`. Eso hace OBLIGATORIOS todos los demás campos del Row, incluso los que tienen `DEFAULT` en SQL. Sin generador de tipos automatizado desde el schema, no hay forma de inferir cuáles tienen default sin enumerarlos.
- **Workaround / fix:** Cada caller de `createContact`/`createOpportunity` debe pasar EXPLÍCITAMENTE todos los campos del Row (incluso con `null`/`false`). Para evitar duplicación, se introdujo el helper `buildContactInsert(...)` en cada worker (customers, draft-orders, orders, backfill) que centraliza la construcción del payload con defaults explícitos. Similar para opportunity con `buildOpportunityInsertFromDraftOrder(...)`. Cuando Supabase CLI esté habilitado y `lib/types/database.ts` se regenere, los Insert types reflejarán correctamente los defaults SQL y los helpers podrán omitir esos campos.
- **Lección:** Mientras `lib/types/database.ts` siga hand-written, los inserts son verbosos por necesidad. NO refactorizar agregando `?` manualmente al type Row para "hacer más opcional" — eso enmascara la columna como nullable a nivel modelo, lo que se propaga a queries de lectura como `string | null` cuando son `string`. Mejor: helpers `buildXxxInsert(...)` por aggregate, con todos los defaults explícitos en un solo lugar. Cuando M11+ habilite el generador, todos los helpers se simplifican de golpe.

### Inngest `retries` espera union de literales 0..20, no `number`

- **Milestone donde se detectó:** M3.
- **Síntoma:** `inngest.createFunction({ id, retries: args.retries ?? 5, ... })` falló typecheck con `Type 'number' is not assignable to type '0 | 1 | 2 | ... | 20 | undefined'`. La aritmética `args.retries ?? 5` widena el resultado a `number`, no a literal `5`.
- **Causa raíz:** En Inngest v4 el tipo de `retries` es una unión de literales numéricos 0..20 (el SDK limita reintentos máximos a 20). TypeScript no infiere `5` como literal cuando viene de una expresión `??`.
- **Workaround / fix:** Definir alias local `type InngestRetries = 0 | 1 | 2 | ... | 20;` y tipar el parámetro como `retries?: InngestRetries`. El cast es a nivel de la firma del helper, no en cada callsite.
- **Lección:** SDKs que usan unions de literales en lugar de `number` ofrecen mejor safety pero crean fricción cuando se quiere parametrizar. Patrón: aliasear el union localmente y usar ese alias en todas las firmas internas — el cast se centraliza.

### `vi.mock` se hoistea desde dentro de funciones, perdiendo el closure

- **Milestone donde se detectó:** M3.
- **Síntoma:** Test helpers de M3 (`tests/helpers/fake-supabase.ts`) exportaban una función `installFakeSupabase()` que llamaba `vi.mock(...)` con una referencia a una variable local `fake`. Los tests que importaban este helper fallaban con `ReferenceError: fake is not defined` en `getSupabaseAdminClient` — y la traza apuntaba al closure DENTRO del helper, no al test caller.
- **Causa raíz:** Vitest hoistea TODAS las llamadas `vi.mock(...)` al inicio del archivo donde aparecen, sin importar si están dentro de una función. Cuando `installFakeSupabase()` contenía `vi.mock`, Vitest lo extraía a module-top del archivo `helpers/fake-supabase.ts`. La referencia a `fake` (declarada dentro de `installFakeSupabase`) quedaba apuntando a `undefined` porque la función nunca corría — el módulo solo se importaba.
- **Workaround / fix:** Eliminar `installFakeSupabase()` del helpers file. Cada test que necesita mockear `@/lib/supabase/admin` debe declarar `vi.mock` a module-top en el propio test file, con la instancia `fake` como `const` arriba. El helper solo exporta la `class FakeSupabase` reutilizable.
- **Lección:** No envolver `vi.mock` dentro de funciones — el hoisting de Vitest rompe el closure. Patrón correcto: `const fake = new FakeSupabase(); vi.mock("@/path", () => ({ ...: () => fake }));` a module-top del archivo de test. El `fake` declarado afuera SÍ es accesible porque también queda hoisteado (es un `const` evaluado lazy en runtime, no en parse-time como `vi.mock`).

### Credenciales Shopify por organización: `vault_keys` JSONB pragmático, no `vault.secrets`

- **Milestone donde se detectó:** M3.
- **Síntoma:** La doctrina exige "credenciales en Supabase Vault, cifradas por organización" pero el proyecto no tiene migración que habilite el extension `supabase_vault` (que requiere pgsodium con setup explícito en panel). Sin Vault real, ¿dónde viven los `client_id`, `client_secret`, `access_token` y `whaapy_api_key` por org?
- **Causa raíz:** Supabase Vault (`vault.create_secret`, `vault.decrypted_secrets`) no está habilitado por default en el Free tier sin acción manual en el dashboard. Habilitarlo implica trabajo de setup operacional fuera del scope de M3. El proyecto requiere una solución que funcione hoy y migre limpio a Vault real cuando se justifique (V2).
- **Workaround / fix:** La capa `lib/vault/index.ts` usa la columna existente `organizations.vault_keys` JSONB como store por-org, con fallback a env vars para single-org MVP (Centr). Estructura: `{ shopify: { client_id, client_secret, access_token, access_token_expires_at }, whaapy: { api_key } }`. Las protecciones: (a) `service_role_key` es la única forma de leer JSONB; (b) Supabase cifra at-rest a nivel disco; (c) el repo es público pero el JSONB nunca viaja a código (vive solo en la BD). El `access_token` se cachea acá con TTL para evitar invocar `client_credentials grant` en cada request. Cuando V2 justifique migrar a `vault.secrets`, el API de `lib/vault/index.ts` se mantiene; solo cambia la implementación interna.
- **Lección:** "Cifrado por organización" admite distintos niveles operativos. Para MVP single-org con repo público, `vault_keys` JSONB + service_role es suficiente — el atacante necesita acceso al service_role_key (controlado por env de Vercel/Inngest) Y a la BD (RLS no aplica al service_role pero ese key no debe filtrarse de todas formas). La migración a `vault.secrets` se difiere a cuando: (i) se agregue una segunda org real, (ii) rotación granular por panel sea necesaria, (iii) compliance (PCI, ISO) exija segregación de cifrado por valor. Mantener la API estable (`getShopifyClientId(orgId)`) para que el día del cambio solo se toque `lib/vault/index.ts`.

### supabase-js 2.105 — Database type hand-written incompatible con shape estricta

- **Milestone donde se detectó:** M1.
- **Síntoma:** `next build` fallaba con `Object literal may only specify known properties, and 'organization_id' does not exist in type 'never[]'` en TODAS las llamadas a `.insert(...)` y `.update(...)` del data layer. `tsc --noEmit` reportaba ~30 errores idénticos. El cliente reportaba el shape interno `PostgrestVersion: "12"` con `never` en todas las posiciones.
- **Causa raíz:** la versión de `@supabase/supabase-js` fijada en `package.json` (`2.105.4`) introdujo una forma interna estricta para el generic `Database` que espera, además de `Row/Insert/Update`, los campos `Relationships: []` por cada tabla y un marker `__InternalSupabase: { PostgrestVersion: "12" }` a nivel raíz. La forma hand-written de `lib/types/database.ts` (que omite ambos) hace que el resolver de tipos colapse cada tabla a `never`, lo que rompe el inserto/update.
- **Workaround / fix:** se removió el generic `Database` de los tres clientes (`admin.ts`, `browser.ts`, `server.ts`) — el cliente queda como `SupabaseClient` sin parametrizar. Los tipos fuertes de los resultados siguen viniendo de `lib/types/database.ts` y se aplican como tipos de retorno explícitos en cada función del data layer (los Row types funcionan perfectamente — el problema era solo en las llamadas tipadas del client builder).
- **Lección:** los tipos fuertes del cliente Supabase deben generarse con `supabase gen types typescript` para casar con la shape interna que cada versión espera. Hand-writing el `Database` type es viable solo en versiones más viejas (≤2.50). En M11 o cuando el operador habilite el Supabase CLI, regenerar `lib/types/database.ts` desde el schema real y restaurar el generic en los clientes. Hasta entonces, mantener el patrón actual (clientes sin generic + Row types como retorno explícito).
