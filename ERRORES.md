# ERRORES.md — Bugs conocidos, workarounds y lecciones del proyecto Centr Hub

> Documento vivo. Cada entrada condensa un bug/lección en **causa raíz** + **regla/invariante** a no romper en milestones futuros. Se omiten narrativas de diagnóstico, fechas, hashes de commit e IDs de un solo uso; se conservan TODOS los invariantes que aún protegen el sistema (fechas reales de Shopify, timezone CDMX, idempotencia R4, anti-bucle R11, contrato del trigger F1→F2 / migración 0027, atribución R2/R5, etc.).

## Formato obligatorio de cada entrada (estándar a partir de la condensación de junio 2026)

Toda entrada NUEVA sigue este mismo formato condensado — **solo la lección accionable**, nada más:

- **Estructura:** `### Título` + dos bullets, **`- **Causa raíz:**`** (qué lo provocó) y **`- **Regla:**`** (cómo evitarlo / el invariante a preservar). Si la causa raíz cabe en el título, basta el bullet `Regla:`.
- **Qué NO incluir:** narrativa de diagnóstico (síntomas largos, "N iteraciones de debugging", método de investigación), fechas, hashes de commit, UUIDs/IDs de un solo uso, nombres de ejemplo (personas, números de orden), ni redundancia con entradas existentes (si la lección ya está documentada, enlazar o ampliar la entrada existente — no duplicar).
- **Qué SÍ preservar:** el invariante que protege el sistema (número de migración, nombre de tabla/columna/función, regla doctrinal R#/O#) y la referencia mínima al código (`archivo.ts` o `[texto](ruta)`), sin la cronología de cómo se descubrió.
- **Regla de oro:** si un dato no ayuda a un milestone futuro a *no repetir el error*, se omite. Ante la duda entre "invariante vivo" y "ruido histórico", conservar el invariante.

## Auth y sesión

### Magic link de login daba `otp_expired` → se retiró; recuperación de contraseña lo cubre
- **Causa raíz:** un token de un solo uso emaileado es frágil: escáneres de links (Gmail/Safe Links/antivirus) hacen GET y lo consumen antes del click humano. El fallo ocurre en `/auth/v1/verify` de Supabase (llega como **hash fragment** `#error=otp_expired`), ANTES del callback propio — no era bug de PKCE.
- **Regla:** para "acceso sin contraseña" usar UN solo flujo (recuperación: `resetPasswordForEmail` → `/auth/confirm` type=recovery), no mantener magic link. Al diagnosticar auth en App Router, la URL exacta del rebote (hash `#error` = falló en Supabase verify; query `?error` = falló en callback propio; el `error_code` distingue token muerto vs redirect no permitido) localiza la capa antes de tocar código.

### Recuperación/invitación por correo deben sobrevivir escáneres de links — verificar solo en el submit
- **Causa raíz:** el template default `{{ .ConfirmationURL }}` apunta a `/auth/v1/verify` de Supabase, un GET de un solo uso. Los escáneres de correo corporativo (Google Workspace, M365) pre-fetchean el link y **consumen el token antes del click humano** → `otp_expired` ("Email link is invalid or has expired"). PKCE `?code=` NO lo arregla: el `code` se acuña *después* del verify GET ya consumido; además el `?code=` (query) se pierde en el redirect `/`→`/login` del middleware (`new URL("/login", req.url)` descarta el query string → aterriza en `/login` pelón).
- **Regla:** las plantillas **Reset Password** e **Invite** apuntan directo a la app: `{{ .SiteURL }}/auth/confirm?token_hash={{ .TokenHash }}&type=recovery` (o `&type=invite`), sin pasar por el verify GET consumidor. `/auth/confirm` (Client Component) lee `token_hash`+`type` del **query string**, muestra el form SIN verificar, y consume el token **solo en el submit** vía `verifyOtp({token_hash, type})` — un GET pasivo de escáner nunca dispara el form, así que el token sobrevive. NUNCA verificar en `useEffect` ni en un Route Handler server-side (cualquier GET lo consumiría, reabriendo el agujero). `verifyOtp(token_hash)` no depende de cookie `code_verifier` → funciona cross-device (pedir reset en desktop, completar en móvil). `NEXT_PUBLIC_SITE_URL` (Vercel) y el **Site URL** de Supabase = dominio prod exacto, con esquema y SIN slash final.

### Flujo de invitación incompleto — hash fragment (implícito) vs PKCE
- **Causa raíz:** Supabase Auth tiene dos flujos en App Router: **PKCE** (`?code=` → `exchangeCodeForSession`, server-side) e **implícito** (`#access_token=...&type=invite`, hash fragment, **solo client-side**). Invitaciones y password recovery usan el implícito; un Route Handler nunca ve el hash.
- **Regla:** el Route Handler sin `?code=` sirve un HTML mínimo con `window.location.replace('/auth/confirm'+window.location.hash)`. Página `/auth/confirm` (Client Component) parsea el hash y muestra el form de contraseña. **Cualquier página pública a la que Supabase pueda redirigir (incl. `/login` cuando Site URL es la raíz) debe interceptar el hash** y reenviar a `/auth/confirm`. `/auth/confirm` en `PUBLIC_ROUTES`.

### auth.users insertado por SQL crudo no lo carga GoTrue ("Database error loading user")
- **Causa raíz:** insertar filas en `auth.users` por SQL crudo deja **NULL** columnas de token (`confirmation_token`, `recovery_token`, `email_change*`, `phone_change*`, `reauthentication_token`) que GoTrue escanea como `TEXT NOT NULL` → el driver Go revienta al materializar el usuario. La fila sirve para joins y JWT hook, pero `auth.admin.getUserById/listUsers` falla.
- **Regla:** todo seed/migración que inserte en `auth.users` directo debe inicializar esas columnas a `''`, no NULL. Repair-in-place vía RPC `public.repair_auth_user_tokens(uuid)` (migración 0028, SECURITY DEFINER, EXECUTE solo `service_role`) — normaliza tokens a `''` SIN tocar el `id`, así las FKs colgadas de `membership.id`/`user_id` quedan intactas. Para "vincular login" a una entidad con datos atribuidos, **repair-in-place > recrear**. Diagnóstico: cuando una API bulk de proveedor falla opaca, degradar a la versión por-ítem (`getUserById`) para aislar la fila culpable.

### Validador de env falla por variables opcionales vacías en `.env.local`
- **Causa raíz:** `z.string().min(1).optional()` NO es "ausente o no vacío": `.optional()` permite `undefined`, pero `VARIABLE=` en `.env.local` se expande a `""` (presente) → aplica `.min(1)` y falla.
- **Regla:** variables requeridas-desde-milestone-X usan `z.string().optional()` (sin `.min(1)`) en startup + helper de acceso tardío (`getShopifyWebhookSecret()`, etc.) que valida en runtime con error descriptivo. Antipatrón: `z.string().min(1).optional()`.

### Roles configurables — dos ejes, `isAdmin` fundido separado en dos preguntas (migración 0039)
- **Causa raíz:** el modelo binario `isAdmin = role === 'admin' || 'superadmin'` (cableado inline en ~30 sitios) fundía DOS permisos distintos: "¿ve el panel de administración?" y "¿alcanza todos los datos?". Un rol que ve todo pero no es admin (SDR) era inexpresable: caía por el `else` (asesor sin asignaciones) y no veía nada.
- **Regla:** modelo de DOS EJES en la tabla `roles` (0039): `allowed_tabs` (qué pestañas ve) + `data_scope` (`own`|`all`). Los helpers PUROS de `lib/auth/capabilities.ts` sustituyen a `isAdmin`: **`canSeeAllData`** (data_scope='all' → admin/superadmin/SDR) gatea alcance de datos y operación en pestañas generales (reasignar, ver sin asignar, breakdown, vista de equipo de Mi Día vía `resolveSeesAllContext`); **`canAccessAdminPanel`**/`hasTab(tab)` gatea rutas y actions de admin (`resolveAdminContext(tab)` per-pestaña, `requireTabOrRedirect` per-página). El *else* sigue siendo "solo lo propio" → ningún rol existente cambia. `getSession` cuelga `activeRole` (capacidades resueltas de la tabla; `fallbackCapabilities` si falta la fila — nunca deja la sesión rota). **"Solo vendedores son asesores" NO se materializa como flag configurable**: `listActiveRealVendors`/`listRealVendorsForMapping` siguen filtrando `role='vendedor'`, así que un rol nuevo (key ≠ 'vendedor') queda fuera de round-robin/selector/tags/Whaapy sin trabajo extra. Al agregar un rol/pestaña, tocar `TAB_REGISTRY` (capabilities.ts) Y el seed de `allowed_tabs` en 0039 — deben coincidir 1:1.

### `memberships.role`: de CHECK fijo a FK dinámico → sembrar roles ANTES de la primera membership (migración 0039)
- **Causa raíz:** al pasar `memberships.role` de `check (role in (...))` a FK compuesto `(organization_id, role) → roles(organization_id, key)`, cualquier `(org, role)` vivo sin fila en `roles` reventaría la validación del FK; y el cascade de borrar una organización elimina `memberships` y `roles` como hermanos, con orden no garantizado.
- **Regla:** la migración siembra los roles de sistema (`superadmin`/`admin`/`vendedor`) + `sdr` para TODAS las orgs existentes ANTES de agregar el FK; `bootstrap_organization` se re-CREA desde la versión vigente (patrón 0027/0030) insertando el bloque de roles ANTES del membership "Histórico". El FK es **`deferrable initially deferred`** para sobrevivir el cascade de org-delete (validación al commit). Borrar un rol con memberships vivos viola el FK (guardrail en BD) además del pre-chequeo `countMembershipsWithRoleKey` en la action. `MembershipRow.role` es `string` (dinámico); el alias `Role` queda solo para comparar contra roles de SISTEMA. Roles de sistema (`is_system=true`): no editables ni borrables desde el constructor.

### Realtime no entrega al browser sin claim `organization_id` en el JWT
- **Causa raíz:** Realtime evalúa RLS en rol `authenticated` leyendo SOLO del JWT (corre en su propio proceso; el setting de sesión `app.current_organization_id` del wrapper server-side NO le llega). El JWT estándar no trae `organization_id` → `current_organization_id()` = NULL → toda policy SELECT cierra → eventos descartados en silencio (subStatus sigue `SUBSCRIBED`).
- **Regla:** el hueco lo cierra el **Auth Hook** `custom_access_token_hook` (migración 0017) que inyecta `organization_id` en la RAÍZ del JWT — requiere habilitarlo manualmente en Supabase Dashboard (ver CLAUDE.md "Hook de claim organization_id"). El filtro `organization_id=eq.X` en `postgres_changes` es defensa multi-tenant pero NO sustituye RLS (filtra ruido, no entrega sin RLS pasada). Polling fallback (30s) es la red mientras tanto; no retirarlo hasta validar delivery empírico (M5-DT-03).

## Migraciones, RPC y triggers SQL

### `create or replace function` reemplaza el cuerpo ENTERO — regresión 0025 pisó herencia de la hija (0021)
- **Causa raíz:** 0025 hizo `create or replace` de `trigger_f1_to_f2` rebasándose sobre 0020 (versión vieja), soltando en silencio lo que 0021 (datos comerciales + line items) y 0022 (asesor coalesce) habían agregado. El asesor sobrevivió solo porque el hook `orders/*` de 0022 lo rellena después (red de seguridad enmascaró la regresión); los datos comerciales no tenían hook → regresión expuesta.
- **Regla (contrato F1→F2, migración 0027 = definición CANÓNICA ÚNICA):** toda redefinición de una función SQL parte de la versión VIGENTE y arrastra TODA la lógica acumulada, nunca de una vieja "porque el cambio es pequeño". 0027 contiene la unión de invariantes: (A) datos comerciales + line items, (B) asesor `coalesce(orden, F1)`, (C) `won_at`/`shopify_event_at` desde `orders.shopify_created_at`, + atomicidad/idempotencia/R2. Guard estático [tests/f1-to-f2-trigger-sql-contract.test.ts](tests/f1-to-f2-trigger-sql-contract.test.ts) auto-rastrea la última definición y asierta las 4 invariantes en CI (`tsc`/tests mockeados no ven dentro de plpgsql). Cuando un fix tiene red (hook) y otro no, una misma regresión se ve "a medias" — auditar TODAS las cláusulas que el re-CREATE debía conservar.

### Trigger F1→F2: atomicidad por RPC, idempotencia por hija-existente (no por flag)
- **Causa raíz:** la completación llega como `draft_orders/update` (repetible) y toca 4 tablas; emularlo en TS con varios `await` deja ventana de inconsistencia y un compensating-revert no cierra el caso "el proceso muere".
- **Regla:** toda la transición vive en `public.trigger_f1_to_f2` (PL/pgSQL SIN bloque EXCEPTION → Postgres revierte todo si algo falla). Idempotencia por **existencia de la hija** (`SELECT ... WHERE parent_opportunity_id=F1.id AND funnel='post_venta'`) + `FOR UPDATE` sobre la F1, **nunca por `won_at`** (un movimiento manual a Ganada setea `won_at` sin crear hija — usarlo como guardia saltaría la creación legítima). R2: copia `assigned_advisor_id` a la hija UNA vez, nunca propaga reasignaciones posteriores de la F1.

### Trigger F1→F2 creaba la hija sin datos comerciales (migración 0021)
- **Causa raíz:** el INSERT de la hija solo copiaba identidad (contacto/asesor/parent/currency), nunca campos comerciales ni line items.
- **Regla:** la hija hereda `actual_amount`, `estimated_amount`, `shopify_order_id`, `display_reference` + INSERT-SELECT de line items, dentro del mismo RPC atómico. **`shopify_draft_order_id` NO se hereda**: tiene `unique (organization_id, shopify_draft_order_id)` (copiarla abortaría el RPC) y `findOpportunityByDraftOrderId` usa `.maybeSingle()` sin filtrar funnel (dos filas romperían idempotencia de todos los webhooks `draft_orders/*`). La referencia visible vive en `display_reference` (texto, sin constraint). Al crear una entidad derivada "completa", enumerar TODOS los campos de negocio a heredar; verificar constraints de unicidad y lookups por cardinalidad antes de copiar.

### Hija de Post-venta heredaba el asesor de la F1 (NULL) en vez del de la orden (migración 0022)
- **Causa raíz:** la atribución por tag aterriza en la **orden**, no en la F1, y por un webhook `orders/*` independiente sin orden garantizado. Si la orden llega después del trigger, la hija nace con el fallback NULL de la F1 y nada la corrige.
- **Regla:** (1) trigger resuelve asesor `coalesce(asesor_orden, asesor_F1)` (orden por `shopify_order_id`, unique → ≤1 fila); (2) **hook en `orders/*`** (`reattribute_postventa_child_advisor`) cierra la ventana de carrera realineando la hija cuando la orden con asesor aterriza; (3) correctivo de hijas existentes reusa el mismo RPC. Guard anti-pisado de reasignación manual: el RPC se salta si hay audit `opportunity_advisor_reassigned`/`opportunity_reassigned` con `actor_user_id` no nulo. Para 0022 la decisión es **pisar** (quien cierra atiende post-venta); R2: solo toca el asesor de la HIJA, nunca F1 ni contacto. No infla KPIs (dashboard filtra `funnel='venta'`).

### Opp de Venta sin asesor pese a orden con asesor — tag de vendedor tardía (migración 0023)
- **Causa raíz:** misma carrera que 0022 un nivel arriba: la opp de Venta avanza por la tag del Draft Order, pero el asesor aterriza en el **pedido** por un `orders/*` posterior.
- **Regla:** el hook `orders/*` también realinea la F1 de Venta (`reattribute_venta_opportunity_advisor`). Diferencia clave con 0022: aquí la regla es **"rellenar solo si NULL, nunca pisar"** — la atribución manual o por tag de draft (R2) nunca se toca. El guardrail "solo NULL" subsume la protección anti-manual y la idempotencia en una sola condición (segundo run → `opportunity_already_assigned`).

### El hook 0022/0023 NUNCA disparó en vivo — Shopify no envía `draft_order_id` en orders
- **Causa raíz:** el 100% de las órdenes estaban huérfanas (`orders.opportunity_id` NULL) porque `orders.ts` resolvía el enlace SOLO por `draft_order_id`, que Shopify no manda en el webhook de orders. El gate `if (order.opportunity_id && order.assigned_advisor_id)` era siempre falso → los hooks de re-atribución nunca corrían en producción (los correctivos funcionaban por llamar el RPC directo, saltándose el gate).
- **Regla (3 capas):** (1) enlazar orden→opp por `shopify_order_id` (`findVentaOpportunityIdByShopifyOrderId`, filtra `funnel='venta'`) además de `draft_order_id`; invocar hooks resolviendo opp por `opportunity_id ?? shopify_order_id`. (2) En creación de opp de draft, quitar el fallback `?? contact.assigned_advisor_id` — la opp toma asesor del tag del draft o queda NULL (subsumido en el guardrail "solo NULL"); **R12 sí sigue heredando del contacto** (ahí el contacto es dueño). (3) Cron horario `advisor-reattribution-reconcile` (TZ Mexico_City, `withTenantContext`, idempotente) como red de seguridad. **Un hook condicionado a un campo que el sistema externo no garantiza enviar es un hook muerto — verificar contra datos reales que la condición del gate llega a ser verdadera, no solo que el correctivo manual funciona.** Cuando dos entidades se referencian asimétricamente, resolver por el lado que SÍ tiene el dato. **Supuesto operativo (Ajuste post-Discovery 2 #10):** el vendedor pone la tag al **cobrar/facturar** (en la orden), no al crear el draft.

### Reconciliación de seeds con FK `on delete restrict`: renombrar in situ, no borrar+crear
- **Causa raíz:** `DELETE` de una `pipeline_stage` con opps apuntándola (`opportunities.stage_id ... on delete restrict`) aborta por FK.
- **Regla:** cuando X y Y son semánticamente equivalentes y X está protegida por FK, **renombrar** preserva el `id` y todas sus filas dependientes (migración 0019 renombró "Preparación/Envío"→"Envío en curso"). Con índices únicos parciales (`WHERE is_initial = true`), liberar el valor único ANTES de insertar el nuevo titular. Reservar borrar+crear solo sin equivalencia semántica, migrando dependencias antes.

### `RETURNING INTO` escalar con INSERT multi-fila falla en PL/pgSQL
- **Causa raíz:** `INSERT ... VALUES (multi-fila) RETURNING id INTO variable_escalar` es inválido (`P0003: query returned more than one row`).
- **Regla:** recuperar IDs por columna única posterior con `SELECT ... INTO`, o `RETURNING ... BULK COLLECT INTO array`, o INSERTs uno por uno.

### `search_path` mutable en funciones PL/pgSQL
- **Causa raíz:** funciones sin `SET search_path` heredan el de la sesión → un atacante puede redirigir la resolución de tablas/funciones a un schema malicioso (riesgo mayor en SECURITY DEFINER).
- **Regla:** toda función declara `SET search_path = public` como **opción de función** (entre `language` y `as $$`), no como primera sentencia del body. Corregir omisiones con `ALTER FUNCTION ... SET search_path = public;`.

### SECURITY DEFINER callable by PUBLIC — `REVOKE FROM PUBLIC` solo no basta
- **Causa raíz:** Supabase corre por default `ALTER DEFAULT PRIVILEGES ... GRANT EXECUTE ON FUNCTIONS TO anon, authenticated`. Esos grants son **separados** del de PUBLIC — `REVOKE FROM PUBLIC` no los toca y PostgREST sigue exponiendo la función como RPC.
- **Regla:** `REVOKE EXECUTE ... FROM PUBLIC, anon, authenticated` + GRANT explícito a los roles que la necesitan. **Excepción intencional:** `is_member_of` DEBE conservar EXECUTE en `anon`/`authenticated` (se usa en RLS policies; sin ello las policies fallan "permission denied for function") — Security Advisor lo seguirá reportando; deuda consciente. Para funciones reportadas no encontradas en migraciones propias (`rls_auto_enable`), usar DO block + `pg_proc` para descubrir signatures reales, no inventar una.

### Atomicidad del movimiento de oportunidad emulada en app (trade-off documentado)
- **Causa raíz:** M5 prohíbe tocar schema/RPC; sin RPC, PostgREST no expone transacciones → cada paso (UPDATE opp + INSERT history + INSERT audit) es su propio statement.
- **Regla:** emulación con optimistic lock (`eq("last_modified_at", expected)` → `stale_version` si 0 rows) + compensating revert. Modo de falla residual: si el INSERT history falla tras el audit, queda audit sin history (ruido conocido, opp consistente). Camino correcto futuro: RPC `move_opportunity_stage_atomic` (hermano del trigger F1→F2 atómico). Monitor: job que detecte `stage_id` distinto de la última entrada de history.

### Borrar etapa fallaba en silencio — FK `opportunity_stage_history.to_stage_id ... on delete restrict` no pre-chequeado
- **Causa raíz:** `deleteStageAction` solo pre-chequeaba `opportunities.stage_id` (ocupación actual) pero NO el historial. `opportunity_stage_history` es append-only/inmutable (`tg_block_mutation`) y su `to_stage_id` es `on delete restrict`: cualquier etapa por la que ALGUNA vez pasó una opp tiene filas permanentes que la referencian, aunque hoy esté vacía. El `DELETE` reventaba con violación de FK; `deleteStage` hace `throw error`, la server action no tenía try/catch → la promesa se rechazaba, la UI quedaba colgada en "Eliminando…" sin banner (síntoma: "no se puede borrar", sin error visible).
- **Regla:** una etapa con historial NO se puede borrar en duro (preserva trazabilidad) → se **DESACTIVA** (`is_active=false`); el kanban ya filtra `is_active` ([lib/actions/pipeline.ts](lib/actions/pipeline.ts)) así que desaparece del pipeline y deja de ser destino de `moveOpportunityStage` (`stage_inactive`), reversible con `reactivateStageAction`. `deleteStageAction` pre-cuenta `countStageHistoryReferences` (solo `to_stage_id`; `from_stage_id` es `on delete set null`, no bloquea) y `countOpportunitiesForStage`, decide borrar/desactivar/bloquear, y envuelve `deleteStage` en try/catch (defensa de fondo ante cualquier FK nuevo). Al agregar una acción destructiva sobre una entidad referenciada por FKs `restrict`, pre-chequear TODAS las tablas que la referencian, no solo la obvia.

### "Etapa ligada a automatizaciones" no es un booleano — se compone de flags + nombres canónicos + reglas activas
- **Causa raíz:** las automatizaciones resuelven sus etapas por DOS mecanismos: (A) flags (`is_initial`/`is_won`/`is_lost`) y (B) **NOMBRE hardcodeado con fallback posicional** ("Cotización" del webhook `draft_orders/create`; las 4 zonas + "Caso problemático" del motor Post-venta; "Contacto calificado" del dashboard) + reglas del admin que guardan `stage_name` en su config. Renombrar una etapa resuelta por nombre rompe la automatización en silencio (cae al fallback posicional equivocado, o `stage_not_found` en el motor de reglas).
- **Regla:** el detector vive en el módulo PURO [lib/services/stage-automation.ts](lib/services/stage-automation.ts) (`computeStageAutomation`) — fuente única de los nombres canónicos, testeable, con guard estático que verifica que esos strings sigan coincidiendo con los motores (draft-orders, postventa-transition, dashboard-stages). La UI advierte al **editar** y al **borrar/desactivar** una etapa `linked`; el borrado en duro de una etapa `linked` exige teclear la palabra `eliminar` (revalidado en backend, `confirm`). La desactivación (por historial) NO pide la palabra (no es un borrado) pero SÍ muestra la advertencia. Si cambian los nombres canónicos en un motor, actualizar también este módulo (CI lo atrapa).

### El fallback POSICIONAL del detector de automatizaciones cruzaba funnels
- **Causa raíz:** `computeStageAutomation` ramificaba `if (funnel==='venta') {...} else {...}`, tratando TODO lo no-venta como Post-venta. Con un tercer funnel (Outbound), sus 3 etapas caían en el `else` y heredaban etiquetas del Post-venta por POSICIÓN: pos 1-3 → "zona del motor Post-venta", última → "sumidero de cancelaciones", y la `is_initial` → "destino F1→F2" (el mensaje del flag inicial también asumía no-venta=post_venta). Falsas advertencias en Admin → Etapas para Outbound.
- **Regla:** el fallback posicional (y CUALQUIER resolución por posición) vive DENTRO de la rama del funnel dueño — nunca cruza funnels. Ramificar explícito `if venta / else if post_venta`; los funnels sin automatización propia (Outbound en Fase 2) caen fuera y no marcan nada. El mensaje del flag `is_initial` también es por-funnel. Una etapa de un funnel en la posición N JAMÁS hereda la zona N de otro funnel. Cubierto por `stage-automation.test.ts` (las 3 Outbound → `linked:false` + guard de que el fallback posicional del Post-venta sigue intacto).

### `bootstrap_organization` re-creado desde una versión vieja (0039 regresó el seed a v5.0)
- **Causa raíz:** 0039 hizo `create or replace` de `bootstrap_organization` rebasándose sobre **0010 (v5.0)** en vez de la VIGENTE **0033 (v5.1)** — su cabezal decía "desde la versión VIGENTE (0010)" pero 0010 NO era la vigente. Resultado: toda org nueva nacía con 7 etapas Venta viejas ("Calificado/Cotización enviada/En negociación/Esperando pago"), Post-venta v5.0 y reglas ancladas a esos nombres → automatizaciones rotas en silencio (draft_orders/create sin "Cotización", dashboard sin "Contacto calificado", motor Post-venta sin "Envío en curso"/"Caso cerrado"). ### Una pantalla que cruza organizaciones no puede autorizarse con `resolveAdminContext`

### Dominio de `funnel` ampliado a un tercer valor ('outbound') toca 6+ puntos hardcodeados

Screens que gestionan solo un subconjunto de funnels (ej. admin de Reglas = venta/post_venta) se tipan con `Extract<Funnel, ...>`, no arrastran 'outbound'.

### `opportunities.is_outbound` denormalizado del contacto — estampar en TODO path de creación

### Asesor de la entrega (handoff) gana sobre el tag de Shopify, con advertencia (no lo pisa)

### La entrega (handoff) debe asignar el vendedor al CONTACTO + propagar a Whaapy (Track 2), no solo a la opp
- **Causa raíz:** el handoff 0043 asignaba el vendedor solo a `opportunities.assigned_advisor_id`. Verificar con `maintenance:diagnose-users-and-advisors` (imprime `whaapy_agent_id` por vendedor).

### `conversation.*` usa `conversation_id` (no `id`); Whaapy NO emite `contact.created` para writers orgánicos → los leads morían en DLQ
- **Causa raíz:** DOS cosas juntas. (1) **Los schemas Zod de `conversation.*` exigían `data.id` + `data.contact_id`**, pero el payload REAL de Whaapy usa **`data.conversation_id`** (no `id`) y `conversation.assigned` **NO trae `contact_id`** (solo `phone_number` + `assigned_to`). Toda `conversation.*` fallaba Zod → 5 reintentos → **DLQ** (verificado en prod: 66 fallos de `conversation.created`, 11/11 al DLQ). (2) **Whaapy NO emite `contact.created` para un writer orgánico** (primera vez que alguien escribe) — solo `conversation.created` (verificado: de 62 `contact.created`, source=api:48/blank:14, **orgánico:0**). El worker `conversation.created` además **descartaba** contactos desconocidos en vez de crearlos. Resultado: un lead orgánico con agente en Whaapy NUNCA llegaba a la plataforma (ni el contacto ni el asesor). Mismo origen para "cambio de agente no sincroniza": el canal es `conversation.assigned`, que moría en el mismo schema.
- **Regla:** schemas `conversation.*` reconstruidos desde payloads REALES capturados (guard `whaapy-conversation-schema.test.ts` con los bodies exactos de MHFP y Daniel Ronzón). El worker `conversation.created` **CREA** el contacto si no existe (GET snapshot para agente/email → `ingestWhaapyContact` = mismo match/mapeo/LWW que `contact.created` → R12 "Lead nuevo" con el vendedor del agente). `conversation.assigned`/`unassigned` resuelven el contacto **por teléfono** (no hay `contact_id`) y setean/limpian el asesor (+ tag Shopify, NO propagan a Whaapy = evitan eco). **Regla dura: cuando un evento de asignación NO resuelve contacto por teléfono, audita EXPLÍCITO (`whaapy_conversation_assign_unresolved`), nunca drop silencioso — el drop silente es exactamente cómo este bug sobrevivió semanas.** El backfill de orgánicos (`maintenance:backfill-whaapy-organic`, SOLO `source=webhook`, deja los `source=import` del import histórico) recupera los que ya cayeron. **Monitoreo (no opcional):** cron horario `whaapy-inbound-health-check` alerta a admins cuando un topic inbound falla ≥3 veces/hora (drift de schema) — el DLQ handler ya notificaba por-fallo pero se perdía en el ruido; la señal que faltaba es la agregada "este topic falla el 100%". Reafirma la regla de ERRORES: **el primer test de una integración inbound se construye desde un payload REAL capturado, no de campos asumidos** (los schemas viejos asumían `id`/`contact_id`/`channel`).

### R2 refinado: reasignación MANUAL de opp de VENTA SÍ materializa el dueño del contacto (era display-only → no propagaba)
- **Causa raíz:** `contacts.assigned_advisor_id` (dueño-Venta) es lo ÚNICO que se propaga a Whaapy/Shopify, pero ninguna vía de UI normal lo seteaba: reasignar el asesor en la OPP solo tocaba `opportunities.assigned_advisor_id` (R2 estricto) y el contacto mostraba un "asesor heredado" **calculado en lectura** (`getDerivedAdvisorsForContacts`) sin escribir nada → el usuario creía que asignó pero Whaapy nunca recibía nada (mostraba un valor viejo). Sync de asignación efectivamente inalcanzable.
- **Regla:** una reasignación **MANUAL** de opp de **Venta** (`reassignOpportunityAdvisor`, actor no nulo) recalcula y MATERIALIZA el dueño del contacto (`syncVentaContactOwnerFromOpp` → `computeVentaContactOwner`, `lib/services/contact-advisor-sync.ts`, guard `contact-venta-owner.test.ts`) y propaga (Whaapy + tag Shopify), best-effort (si falla, la opp ya quedó reasignada; es derivado y re-disparable). Recompute desde opps de Venta activas (`cancelled_at IS NULL AND lost_at IS NULL` → Ganadas cuentan, Perdidas/Canceladas no): 1 asesor→ese; 0→desasigna; >1 conflicto→explicit-wins (en desasignación hacia conflicto conserva el actual). **Límites del refinamiento (NO tocar):** (a) **solo Venta** — una reasignación de Post-venta NUNCA toca el contacto ni el Whaapy de Venta (aislamiento: vendedor en Venta + Customer Success en Post-venta a la vez); (b) **solo manual** — las atribuciones AUTOMÁTICAS (tag/orden 0022/0023, reconciliación horaria) NO propagan al contacto (dejar que el tag reescriba el dueño de mensajería invertiría "el asesor gana sobre el tag de Shopify"); el guard "solo NULL" (0023) sigue intacto sobre la opp. El "asesor heredado" (`getDerivedAdvisorsForContacts` / `getContactIdsWithDerivedAdvisor`) ahora filtra `funnel='venta'` (antes mezclaba Post-venta → Customer Success aparecía como dueño). **Burst:** una desactivación masiva reasigna N opps de Venta → N PATCH a Whaapy; el worker `whaapyOutboundContactSync` tiene `throttle` 30/min por org + `concurrency` 4 → drena sin 429 (429 es `retriable` de todas formas); la propagación Shopify es síncrona pero early-return en leads.

## Sincronización Shopify/Whaapy (R3 LWW, R11 anti-bucle, R12)

### LWW convertía `[]` a `null` → violación NOT NULL en `shopify_tags`
- **Causa raíz:** `isEmptyValue()` trataba `[]` como vacío y `normalizedValue = proposalEmpty ? null : ...` lo convertía a `null`; `UPDATE contacts SET shopify_tags = NULL` viola `text[] NOT NULL default '{}'`. Determinístico para `tags=[]` (camuflado por customers de prueba siempre con tags).
- **Regla:** para columnas `NOT NULL DEFAULT X`, la representación de "vacío" en el reconciler LWW debe ser ese default, no `null`. `ARRAY_TYPED_FIELDS` + `emptyValueFor(field)` (→ `[]` para arrays). R3 (empty overwrites) intacto: `[]` sigue sobrescribiendo `["X"]` cuando es más reciente. Tener al menos un test del "happy path mínimo" (customer sin tags) por entidad. Únicas columnas `text[] NOT NULL`: `contacts.shopify_tags` (afectada) y `orders.shopify_tags` (no — INSERT directo sin reconciler).

### LWW seal: proposals vacíos sellaban campos de por vida
- **Causa raíz:** `reconcileContactFields` escribía `field_metadata[field]` para CUALQUIER proposal, incluso vacío-sobre-vacío. Un proposal `{value: null}` (por un bug intermedio del mapper) sembraba metadata `{updated_at:T}`; un re-fetch posterior con el mismo `customer.updated_at` se descartaba `older_ignored` (T > T = false) → campo bloqueado salvo que la fuente avanzara su timestamp.
- **Regla (asimetría):** vacío-sobre-**poblado** escribe patch+metadata (R3 — preserva el borrado intencional para que valores viejos no refilen); vacío-sobre-**vacío** es no-op total (`noop_both_empty`, ni patch ni metadata — preserva la posibilidad de fill futuro). La metadata existe para PROTEGER información; proteger un vacío solo bloquea repair. Un test de R3 DEBE arrancar con valor poblado — si arranca vacío, verifica el sellado, no R3.

### `normalizePhone` perdía teléfonos en silencio bajo tsx (bundling de libphonenumber-js)
- **Causa raíz:** `libphonenumber-js` (dual `"type":"module"` + exports CJS) carga `metadata.min.json` vía `require` dinámico; el loader de `tsx` (bajo Node 24) devuelve `undefined` para ese JSON → `TypeError` interno. Un `try { } catch { return null; }` se lo tragaba → proposal vacío → anti-sealing lo descartaba → teléfono nunca llegaba a BD. Vitest (Vite/esbuild) y Next.js (webpack/SWC) cargan bien; solo los scripts tsx fallaban.
- **Regla:** importar `parsePhoneNumberFromString` desde `libphonenumber-js/core` + `import metadata from "libphonenumber-js/metadata.min.json"` explícito (sin require dinámico). El `catch` debe **distinguir esperado de inesperado**: `parsePhoneNumberFromString` devuelve `undefined`/`false` para inputs inválidos (rama silenciosa → null), así que un throw real significa bug de runtime → loguear a stderr + propagar, nunca tragar. **Código que corre en múltiples runtimes (Next.js + Vitest + scripts tsx) necesita un smoke test bajo el runtime de scripts** (`npx tsx -e ...`); los tests verdes en un runtime no garantizan otro, sobre todo con paquetes dual ESM/CJS que cargan recursos no-JS internamente → preferir subpaths `/core`.

### Teléfono del customer en `default_address.phone`, no en top-level
- **Causa raíz:** los mappers leían solo `data.phone` e ignoraban `data.default_address.phone`. Shopify Admin muestra un único campo "Phone" pero la API lo expone en dos lugares según cómo se creó el customer (edit manual → top-level; checkout → solo dirección).
- **Regla:** helper compartido `pickCustomerPhone(profilePhone, address)` con precedencia perfil→dirección. El mismo bug raíz vivía en 3 mappers paralelos (`mapCustomerWebhookToNormalized`, `mapEmbeddedCustomer`, `mapCustomerGraphqlToNormalized`) — **al arreglar un mapeo de campo, grep todos los call-sites en otras shapes del mismo recurso** (REST + GraphQL + Webhooks). Para campos que un proveedor expone en múltiples ubicaciones, leer con fallback explícito validado contra captura real.

### Contactos Shopify creados vacíos desde webhooks de orders/draft_orders
- **Causa raíz:** los webhooks `orders/*` y `draft_orders/*` traen el snapshot completo del customer embebido, pero los schemas Zod lo tipaban solo con `id` → al no existir contacto local se creaba un stub con todos los campos en `null`. Para customers históricos sin `customers/create` retroactivo, el stub vacío era el único registro.
- **Regla:** reusar el sub-schema dedicado de la entidad referenciada (`embeddedCustomerSchema` espeja `shopifyCustomerWebhookSchema`) en lugar de re-declarar uno estrecho. Cuando una entidad nace por múltiples rutas, factorizar el constructor común a un helper (`hydrateContactFromEmbeddedShopifyCustomer`) — rutas paralelas divergen en silencio. El webhook satélite de un recurso trae el body completo de la entidad relacionada, no solo el id.

### Direcciones: actualizar sub-recurso de colección requiere el `id` del hijo
- **Causa raíz:** el outbound mandaba la dirección dentro de `addresses[]` del **PUT de customer sin `address_id`**. Shopify trata un objeto de `addresses` sin `id` como **ALTA** → crea una segunda dirección y deja la vieja como default (responde 200 → el worker lo daba por éxito). Escalares (`first_name`, `phone`, etc.) sí se actualizan en sitio; solo `addresses[]` tenía semántica de append.
- **Regla:** actualizar un sub-recurso de colección (`addresses`, `metafields`) se hace por su **endpoint dedicado con el `id` del hijo resuelto vía GET en el momento** (`syncCustomerDefaultAddress`: `PUT /customers/{id}/addresses/{address_id}.json`, o POST+default si no hay ninguna), nunca por el array del PUT del padre. `updateCustomer` ya no manda `addresses`. R11: `markOutboundWrite` antes de escribir → los ecos `customers/update` caen en la ventana de 30s. **Gap R3 aceptado:** vaciar la dirección en el maestro NO la borra en Shopify (no se metió un DELETE destructivo). Un comentario de cabezal que contradice el código real suele marcar dónde una ruta se agregó sin validar el contrato del proveedor.

### Modal "Crear contacto en Shopify" no persistía la dirección en el maestro
- **Causa raíz:** `createContactInShopifyAction` mapeaba la dirección a Shopify pero nunca llamaba `updateContact` — la dirección era efímera (solo en el request saliente).
- **Regla:** todo formulario que capture un campo de la entidad maestra **persiste al maestro como acción primaria** (antes de la llamada al espejo, en su propio try/catch para sobrevivir un fallo de Shopify), y la propagación al espejo es secundaria. R3: dirección vacía → `null` sobrescribe.

### Shopify rechaza país/estado con acento (422) + error genérico ocultaba el motivo
- **Causa raíz:** `structuredAddressToShopify` mandaba `country: "México"` literal; Shopify valida `country`/`province` contra catálogo cerrado y rechaza variantes acentuadas. El catch ignoraba `e.body` (que en 422 trae el detalle de validación).
- **Regla:** normalizar campos validados-contra-catálogo (país, estado, moneda, timezone) a su **código canónico ISO** en el borde saliente (`COUNTRY_TO_ISO2`, `MX_PROVINCE_TO_CODE`; `lookupKey` quita diacríticos solo para el lookup), conservando la forma legible en el maestro. Propagar el motivo específico del proveedor cuando sea seguro: leer SOLO `errors` (feedback de validación), nunca el body completo (tokens/datos), truncado.

### R11 falso positivo posible en la ventana de 30s (trade-off aceptado)
- **Causa raíz:** R11 opción B (comparación de timestamps + `last_modified_source='platform'`) no distingue un eco real de un edit legítimo del usuario hecho en Shopify Admin dentro de la ventana de ~30s post-escritura outbound — descarta ambos como eco.
- **Regla:** trade-off aceptado (opción A —marker en metafield— duplicaría tráfico API por webhook). Probabilidad baja, impacto alto (silencioso). Defensa: el audit `sync_loop_prevented` expone `delta_ms`, `payload_updated_at`, `last_local_write_at`, `echo_window_ms` para diagnosticar si se manifiesta (`delta_ms`~25-30s + `payload_updated_at > last_local_write_at` = sospecha de falso positivo; `delta_ms<5s` = eco real). Defensas heurísticas con ventana temporal: siempre exponer en audit los parámetros de la decisión, no solo el resultado.

### Lead nuevo duplicado con Cotización por race de webhooks (R12 eco Shopify→Whaapy)
- **Causa raíz:** doble bug: (1) `whaapyContactCreated` no tenía defensa R11 sobre `contact.created` → el eco de la propagación Shopify→Whaapy disparaba R12 como lead orgánico; (2) `draftOrdersCreate` insertaba la Cotización sin mirar si el contacto ya tenía Lead nuevo activo. La precondición de R12 (`active_opportunity_exists`) solo cubre la dirección "R12 evalúa con Cotización ya en BD", no la inversa.
- **Regla:** (1) R11 opción A (`isEchoByCustomFieldMarker`, marker `custom_fields.last_platform_write_at`, ventana 5min) se aplica también a `contact.created` — el primer webhook trae el marker → suprime R12 con audit `sync_loop_prevented`, sin suprimir la hidratación. (2) `absorbInitialStageOpportunities` cancela el Lead nuevo tras crear la Cotización (`cancellation_source="absorbed_by_advanced_opportunity"`). **Cualquier worker inbound debe distinguir eco vs evento orgánico ANTES de disparar lógica de auto-creación/notificación/propagación.** Precondiciones contra "estado actual de BD" son frágiles ante races de workers paralelos sin serialización por contacto — cubrir AMBAS direcciones.

### Absorción de leads: por POSICIÓN de etapa, no por nombre
- **Causa raíz:** la absorción solo cancelaba opps en `is_initial=true`; una opp en etapa intermedia pre-Cotización sin draft coexistía con la Cotización nueva.
- **Regla:** filtrar por **posición de etapa < posición de la opp absorbente** (la Cotización nace en su etapa, su propia posición es el umbral — sin hardcodear "Cotización", respeta etapas editables por admin). `shopify_draft_order_id IS NULL` distingue "lead a absorber" de "negociación paralela legítima". Resolver "anterior a etapa X" contra posiciones reales, nunca nombres.

### Orden de operaciones del worker `whaapyContactUpdated` (R11 + GET reconcile)
- **Regla (secuencia fija):** (1) **GET reconcile** `/contacts/v1/{id}` (el payload `contact.updated` no trae snapshot; fallo → audit `whaapy_reconciliation_failed` + throw → retry → DLQ, maestro pre-webhook); (2) **R11 opción B** (timestamps + `last_modified_source='platform'`, ventana echo 30s); (3) **R11 opción A** (marker `custom_fields.last_platform_write_at`, ventana 5min, cubre latencia del GET); (4) **LWW por campo** desde el snapshot; (5) **propagación a Shopify solo si** `lwwChangedSomething && shopify_customer_id && !missing_phone`. `last_whaapy_activity_at` se actualiza en TODOS los caminos excepto cuando el GET falla. Trade-off aceptado: el GET corre antes de R11 (cada eco consume una API call) a cambio del cross-check con el marker (más confiable que timestamps solos). Reordenar para R11-primero pierde esa precisión — documentar el nuevo costo/beneficio.

### Re-proceso de tags no cubría contactos; `assigned_advisor_id` sin field_metadata (LWW nominal)
- **Causa raíz:** el re-proceso solo tocaba `orders`. Además **ni el worker Shopify ni el Whaapy escriben `field_metadata` para `assigned_advisor_id`** — el LWW por campo de ese campo es nominal (sin productor de metadata).
- **Regla:** `reattributeContacts` (LWW-aware): NULL→asigna; difiere y no-null→solo pisa si la tag es más reciente que `last_whaapy_activity_at` (proxy, ya que no hay metadata). Al escribir, puebla `field_metadata.assigned_advisor_id` para LWW futuro. **Un campo en `EDITABLE_FIELDS` no garantiza LWW efectivo sin que TODO productor escriba su metadata.** Si V2 quiere LWW estricto, añadir la escritura en `customers.ts` y `whaapy-conversations.ts`.

### Borrado en Whaapy quedaba a medias (worker `contact.deleted` era stub)
- **Causa raíz:** el worker solo seteaba `deleted_in_whaapy=true`: no cancelaba opps, `searchContactsForList` no filtraba, y el badge "WHAAPY" deriva de `whaapy_contact_id !== null` (independiente del flag) → ambos badges a la vez.
- **Regla:** servicio compartido `whaapy-contact-archival.ts` (worker + correctivo) que: cancela opps **no-terminales** (`!is_won && !is_lost`, las terminales son historia real), **etiqueta** el customer Shopify (`"Eliminado en Whaapy"` vía `updateCustomerTags`, nunca DELETE — Shopify bloquea borrar customers con órdenes + doctrina), deriva el badge con `inWhaapy = whaapy_contact_id !== null && !deleted_in_whaapy` (conserva el identificador externo), y excluye de vistas activas con opt-in `includeArchived`. Un fallo de Shopify no bloquea el archivado local. Propagar un archivado requiere enumerar TODAS las consecuencias (lead, espejo, vistas, badges).

### `businessId` de Whaapy vive en root del payload, no en `data`
- **Causa raíz:** la implementación asumía `payload.data.businessId`; el payload real trae `businessId` a nivel ROOT junto a `event`/`timestamp`. Además el id del contacto es `data.contact_id` (no `data.id`) para eventos `contact.*`. El descarte respondía 200 silencioso (`whaapy_webhook_missing_business_id`).
- **Regla:** `extractBusinessId` lee `obj.businessId` (root); schemas declaran `businessId` y `timestamp` en root; `contact.*` usa `data.contact_id`. **El primer test sintético de una integración inbound se construye desde un payload REAL capturado del proveedor**, no de la doc (los ejemplos usan placeholders ambiguos y la indentación no es vinculante).

### Schemas Zod inbound Whaapy intolerantes a omisiones — `.nullable()` vs `.nullish()`
- **Causa raíz:** `WhaapyAddressSchema` usaba `.nullable()` (= `T | null`, NO acepta `undefined`); cuando Whaapy **omite** `address` el parser ve `undefined` y falla.
- **Regla:** `.nullable()`=null, `.optional()`=omisión, `.nullish()`=ambos. Para campos opcionales de proveedores externos, **siempre `.nullish()`** salvo evidencia mecánica de que solo manda una forma. Toda integración inbound necesita DOS niveles de test: (1) endpoint (HMAC/dedup/routing), (2) **mapper/schema** que ejecuta `Schema.parse(payload)` con payload mínimo real + completo + edge cases (null explícito vs omitido).

### GET `/contacts/v1/{id}` de Whaapy envuelve en `{contact:{...}}`, no es flat
- **Causa raíz:** Whaapy expone DOS APIs en el mismo host: `/contacts/{id}` (camelCase, `{data:{...}}`, Highlevel) y `/contacts/v1/{id}` (snake_case, `{contact:{...}, conversations:[]}`, la v1 documentada). El reconcile worker usaba el path sin `/v1`; el outbound ya usaba `/v1` (inconsistencia entre workers). El schema asumía shape flat. **CORRECCIÓN (jul-2026): el `POST /contacts/v1` TAMBIÉN retorna envuelto `{contact:{id}}`, NO flat `{id}`** (capturado en vivo — la nota vieja "POST flat" era errónea). `runCreate` leía `result.data.id` → `undefined` → `no_id_in_response` → nunca enlazaba `whaapy_contact_id`. El 409 sí trae `existing_contact_id` (plano). Fix: leer `data.contact?.id ?? data.id`.
- **Regla:** schema wrapper `z.object({contact: ...})`, worker extrae `.contact`. **Validar schemas de responses outbound contra captura real, igual que payloads inbound** (el cliente controla el request pero no la response). Cuando un proveedor expone múltiples versiones de API en el mismo host (ambas dan 200), buscar qué versión usa el resto del código y unificar — usar la equivocada no falla con 404, falla con shape inesperado downstream. Script de captura `scripts/whaapy/inspect-get-contact.ts`.

### `x-webhook-id` de Whaapy es persistente por contact, no único por delivery
- **Causa raíz:** el dedup usaba `x-webhook-id`, que Whaapy **reusa durante todo el ciclo de vida del contact_id** (un mismo valor cubrió 5 deliveries de 3 topics). Updates 2..N del mismo contacto colisionaban en `dedup_hit`. El header único por entrega es `x-webhook-delivery-id` (`whd_*`).
- **Regla:** dedup por `x-webhook-delivery-id` (`WHAAPY_DELIVERY_ID_HEADER`). **La semántica de headers de webhooks NO es portable entre proveedores** (Shopify `x-shopify-webhook-id` SÍ es por delivery; Whaapy no). Antes de elegir un header como dedup key, capturar headers reales de **múltiples deliveries del mismo recurso** y validar empíricamente cuál cambia entre entregas — el test "mismo header 2 veces → dedup hit" es necesario pero no suficiente; falta "mismo recurso editado 2 veces → 2 headers distintos → 2 enqueues". Script `scripts/whaapy/inspect-webhook-headers.ts`.

### Secret HMAC de Whaapy desactualizado en Vault tras recrear el webhook
- **Causa raíz:** Whaapy obliga a borrar+crear el webhook para cualquier cambio (no edita in-place); cada creación genera un secret HMAC nuevo mostrado UNA vez. Sin rotar Vault, todo evento falla `invalid_hmac` y se descarta — síntoma "200 + audit vacío + contact no entra", indistinguible de dispatch roto. El path `invalid_hmac` corre ANTES de resolver tenant → no puede escribir `audit_log` (constraint NOT NULL en `organization_id`).
- **Regla:** SOP en CLAUDE.md ("Operativa Whaapy — rotación de secret HMAC"): tras CUALQUIER toque al webhook, `UPDATE organizations SET vault_keys = jsonb_set(...)` + validación con `whaapy_raw_webhooks.exit_reason='enqueue_succeeded'` como acción atómica. **Cada endpoint inbound debe exponer desde el primer commit un `exit_reason` auditable** (a una tabla operativa que no dependa de tenant resuelto, como `whaapy_raw_webhooks`) — sin él, cada bug downstream cuesta horas de instrumentación reactiva. La observabilidad necesita una capa que NO dependa de la resolución multi-tenant.

### Endpoint Whaapy sin visibilidad — audit solo en el worker
- **Causa raíz:** `whaapy_webhook_received` vivía solo dentro del worker Inngest; si el dispatch fallaba (signing key, función no registrada) era invisible desde BD aunque el endpoint respondiera 200.
- **Regla:** el endpoint público audita la **recepción a nivel HTTP** (`safeAuditAtEdge`, con `source:"endpoint"`) ANTES del enqueue, independientemente del worker — los dos miden cosas distintas (endpoint="HTTP llegó y pasó HMAC"; worker="Inngest dispatchó y arrancó"). El audit del endpoint es **non-blocking** (try/catch que solo loguea a stderr — un 500 a Whaapy/Shopify desactiva el webhook tras N fallos). Diagnóstico cruzado: ambos = OK; endpoint sí + worker no = dispatch roto; ninguno = endpoint roto. (M3 Shopify tiene la misma deuda diferida.)

### Teléfono compartido entre dos customers de Shopify los fusiona en un solo contacto (merge-collapse) — LATENTE en flujo live
- **Causa raíz:** `matchContactIdentity` tier-2 (phone, `findByPhone`) devuelve CUALQUIER contacto con ese teléfono, incluido uno que ya carga el `shopify_customer_id` de OTRO customer. `customersCreate`/`customersUpdate` solo setean `shopify_customer_id` si el contacto matcheado NO tiene uno; si ya lo tiene, no lo sobreescriben y aplican LWW de los campos del 2º customer sobre el 1º → dos customers Shopify distintos colapsan en un solo `contact` y el 2º `shopify_customer_id` nunca se persiste.
- **Regla:** el tier-phone debe enlazar SOLO a **leads** (`shopify_customer_id IS NULL`); un match de teléfono contra un contacto que ya carga OTRO `shopify_customer_id` se ignora → el customer entrante crea su propia fila (dedup por su `shopify_customer_id`, constraint `contacts_org_shopify_customer_unique`). Placeholder (teléfono compartido por ≥3 customers) → no actúa como clave de match, importar phoneless + `missing_phone`. Blast radius medido en la tienda de Centr: 32 números compartidos por >1 customer / 74 customers (incl. 1 placeholder ×12). El backfill M11 (`CENTR-M11-BACKFILL-DESIGN.md`) neutraliza esto SOLO en su path; **el flujo live (webhooks `customers/*`) sigue expuesto** — fix pendiente en `lib/services/identity-matching.ts` (`findByPhone`/`matchContactIdentity`) + `lib/inngest/functions/customers.ts`. Un match de teléfono nunca debe pisar/fusionar un contacto que ya tiene identidad externa de otra entidad.

## Creación de leads (manual + webhook, migración 0038)

### Camino canónico único: `createLead` (ni la vía manual ni el webhook escriben "por atrás")
- **Causa raíz:** dos vías nuevas de creación (manual + webhook) que escribieran contactos/oportunidades por su cuenta divergirían en efectos (una crearía el contacto en Whaapy y la otra no, una registraría atribución y la otra no) → leads huérfanos que "se ven en la tabla pero no existen para el resto del sistema".
- **Regla:** ambas vías llaman a `lib/services/lead-creation.ts` `createLead` — fuente única de los efectos: dedup por identidad, resolución de asesor, guard R12 de opp inicial, atribución de origen (`opportunities.lead_source` + `inbound_webhook_source_id`) + audit `lead_created` SIEMPRE (cubre el caso deduplicado-sin-opp), y propagación a Whaapy con asesor. NUNCA crea en Shopify. Cualquier vía futura de creación de lead pasa por aquí, no reimplementa los efectos.

### Match de identidad de un lead de plataforma NO se restringe a leads (el merge-collapse no aplica)
- **Causa raíz:** el bug merge-collapse (ERRORES.md "Teléfono compartido entre dos customers de Shopify…") exige restringir el tier-phone a leads, pero ESE bug solo muerde cuando la entidad ENTRANTE carga una identidad externa (`shopify_customer_id`) que podría perderse. Un lead nacido en la plataforma no carga ninguna → restringir a leads sería incorrecto: crearía un duplicado en vez de enlazar a un **cliente** que re-consulta (viola la regla Duplicados).
- **Regla:** `matchLeadIdentity` (dedicado, en `identity-matching.ts`) reusa los tiers phone→email de `matchContactIdentity` SIN el tier de id externa; enlaza a cualquier match único (lead O cliente), conflicto (>1) → crear nuevo + audit. Restringir el match por tipo solo tiene sentido cuando lo entrante trae identidad externa a proteger.

### Fuentes de webhook: token HASHEADO (show-once), slug global resuelve tenant pre-context
- **Regla:** cada fuente (`inbound_webhook_sources`, 0038) guarda `token_hash` (sha256) + `token_last4`, NUNCA el token crudo — se muestra una sola vez al crear/rotar (`webhook-token.ts`, comparación constant-time `verifyWebhookToken`). El `slug` es GLOBALMENTE único: el endpoint `/api/webhooks/leads/{slug}` lo resuelve con cliente admin (pre-tenant, como `getOrganizationByShopifyDomain`) para obtener org+fuente. Revocar = `is_active=false` (no borrar — preserva atribución de leads históricos; FK `on delete set null`). Observabilidad: se reusa `whaapy_raw_webhooks` con `endpoint="leads"` + `exit_reason` (token redactado), tabla tenant-independiente — misma lección de "exit_reason auditable desde el primer commit".

### Whaapy: reason `create_from_platform_ui` + elegir create/update por `whaapy_contact_id`
- **Regla:** un lead de plataforma se propaga al Whaapy de Venta con `recordWhaapySyncIntent(contact, reason)`; `createLead` elige `create_from_platform_ui` (POST, contacto aún no en Whaapy) o `update_from_platform_ui` (PATCH, ya existe → refleja la asignación). El worker `whaapyOutboundContactSync` enruta ambos create-* a `runCreate`. `assigned_agent_id` viaja SOLO si el asesor mapea a `memberships.whaapy_agent_id` — hoy ese mapeo NO se puebla en código (deuda Track 2, ver PENDIENTES.md + memoria whaapy-agent-id-mapping-gap); mientras tanto el contacto se crea en Whaapy sin asignar agente, sin rework cuando el mapeo exista.

### Whaapy 400 por `email: null` en el body outbound — omitir opcionales null, no mandarlos
- **Causa raíz:** `buildOutboundBody` mandaba `email: snapshot.email` (y `name`) tal cual; para un contacto sin email eso era `email: null`, y Whaapy valida los opcionales como `string` (solo `phone_number` es requerido) → **400 `validation_error` "Expected string, received null"**. El `POST/PATCH /contacts/v1` LANZA `WhaapyApiError` en cualquier no-2xx/no-409 y `runCreate`/`runUpdate` NO lo cazaban → el throw subía SIN audit (solo visible en el dashboard de Inngest) → invisible desde BD. Enmascarado porque los contactos de Shopify casi siempre traen email (string → OK); mordía el path outbound/lead (sin email). Mismo riesgo con `name` null.
- **Regla:** `buildOutboundBody` OMITE los campos de TEXTO opcionales cuando son null (incluir `name`/`email` solo si truthy); NUNCA enviar `null` en esos. Trade-off PATCH: omitir null = "no cambiar" (no se puede VACIAR un campo) — mismo gap R3 aceptado que las direcciones Shopify. **Excepción `assigned_agent_id`** (ver entrada de abajo): Whaapy SÍ acepta null ahí para desasignar. Guard: `whaapy-outbound-body.test.ts` (name/email nunca null; agente tri-estado). **Observabilidad:** `withOutboundFailureAudit` envuelve create/update y audita `whaapy_outbound_failed` con `{status, retriable, body_excerpt, reason, phase}` ANTES de re-lanzar — un throw del REST outbound debe dejar rastro en `audit_log`, no solo en Inngest (lección "exit_reason auditable desde el 1er commit"). Diagnóstico: reproducir el POST con el body exacto (`scripts/whaapy/redrive-outbound-sync.ts`) captura el status/body reales; `whaapy:diagnose-outbound-bugs` traza opps+audit de un contacto.

### `contact.created` de Whaapy NO trae el marker custom_field → el worker necesita R11 opción B (timestamp), no solo A
- **Causa raíz:** `whaapyContactCreated` solo tenía R11 **opción A** (`isEchoByCustomFieldMarker` leído del *payload del webhook*). El `contact.created` de Whaapy **no incluye `custom_fields`** aunque el contacto SÍ tenga el marker en Whaapy (visible por GET). Resultado: el eco del propio `POST /contacts/v1` (outbound) no se detecta → **R12 crea un "Lead nuevo" duplicado**. El worker de `contact.updated` no sufría esto porque hace GET reconcile + tiene opción B (timestamp). Confirmado en prod: audit `c2_opportunity_auto_created` 1s después de `whaapy_contact_created_outbound`, sin `sync_loop_prevented`.
- **Regla:** el worker de `contact.created` corre `discardIfOwnEcho` (R11 opción B, timestamp `last_modified_source='platform'` que dejó `markOutboundWrite`) **ANTES de la hidratación LWW** (que sobreescribe el source a 'whaapy' y borra el marcador). Defensa en profundidad: `evaluateAndCreateC2Opportunity` también SALTA si el contacto tiene una opp **outbound** activa (`active_outbound_opportunity_exists`) — un contacto que trabaja el SDR no recibe un Lead nuevo paralelo aunque un evento se cuele. Limpieza de duplicados históricos: `maintenance:cancel-orphaned-lead-nuevo` (dry-run primero).

### Inbound de Whaapy no mapeaba `assigned_agent_id` → todo contacto nuevo aterrizaba sin asesor
- **Causa raíz:** `whaapyContactCreated` hardcodeaba `assigned_advisor_id: null` al crear un contacto y NUNCA leía `data.assigned_agent_id` (que SÍ viene en el schema del webhook y en el GET). Afectaba a TODO contacto que entra desde Whaapy con agente, no a un caso puntual.
- **Regla:** resolver `assigned_agent_id` → membership por `memberships.whaapy_agent_id` (`findActiveMembershipIdByWhaapyAgentId`) y sellarlo en el contacto nuevo; para un contacto matched sin asesor, fill-if-null (R2 nunca roba). Depende de que el agente esté mapeado (Admin·Agentes Whaapy) — sin mapeo el contacto queda sin asesor (degradación, no error). Correctivo histórico solo para `last_modified_source='whaapy'`: `maintenance:assign-whaapy-origin-advisors` (deja shopify/platform intactos).

### Cambio/quita de agente en Whaapy sobre un contacto EXISTENTE no llegaba a la plataforma — `contact.updated` no consumía `assignedAgentId`
- **Causa raíz:** para un contacto que ya existe, el cambio de agente en Whaapy viaja por `contact.updated` con `updated_fields` incluyendo `"assignedAgentId"` (el valor NO está en el delta; sale del GET reconcile). El worker `whaapyContactUpdated` solo reconciliaba name/email/phone/address → el cambio/quita de agente se ignoraba. `conversation.assigned` SÍ setea el asesor (`whaapy-conversations.ts`) pero ese canal casi no se usa (verificado en prod: 1 evento sin `contact_id`) y `conversation.unassigned` NUNCA limpia el asesor (gap latente); además un contacto sin conversación no emite `conversation.*`. Por eso el canal real es `contact.updated`.
- **Regla:** el worker `contact.updated` sincroniza agente→asesor **solo si `updated_fields.includes("assignedAgentId")`** (un cambio de otro campo NO toca el asesor), DESPUÉS de las defensas de eco R11 (solo cambios genuinos de Whaapy llegan → no hay bucle). Decisión pura en `decideAgentAdvisorSync` (`lib/services/whaapy-agent-sync.ts`, guard `whaapy-agent-sync.test.ts`): agente mapeado → SET/CHANGE (Whaapy gana, LWW por evento); agente removido → CLEAR (desasigna); agente sin mapeo → NO borra + audit `whaapy_agent_mapping_missing`. R2 intacto (solo el contacto, no la opp). **Caveat R11 (documentado):** un cambio de agente GENUINO en Whaapy dentro de la ventana de eco (30s opción B / 5min opción A) tras una escritura de la plataforma al mismo contacto se descarta como eco (falso positivo conocido) — poco probable para acciones humanas pero posible. **Gap Whaapy-side (fuera de código):** un cambio de agente hecho en la UI de Whaapy puede NO emitir webhook (verificado: `updated_at` del contacto avanzó pero no llegó `contact.updated`); sin webhook, nada sincroniza — validar la suscripción del webhook en Whaapy.

### `buildOutboundBody` omitía `assigned_agent_id` null → no se podía DESASIGNAR el agente en Whaapy
- **Causa raíz:** la política "omitir opcionales null" (del fix `email:null`) también omitía `assigned_agent_id`. Al quitar el asesor a nivel contacto, el PATCH corría (marker actualizado) pero SIN el campo → Whaapy conservaba el agente. Confirmado por GET: agente seguía asignado tras la desasignación.
- **Regla:** `assigned_agent_id` es tri-estado (`AgentDirective`): **set** (id) cuando el asesor mapea; **clear** (`null`, la doc de Whaapy dice "envía null para quitar la asignación") SOLO en UPDATE cuando el asesor es genuinamente null (desasignado); **omit** cuando el asesor existe pero no tiene `whaapy_agent_id` (no podemos setear y NO se debe borrar un agente válido por falta de mapeo). En CREATE, "clear" degrada a omit (no hay agente que limpiar). name/email siguen omit-if-null.

### Round-robin de leads por webhook: pool con toggle por-vendedor (migración 0045)
- **Regla:** el reparto round-robin (`pickRoundRobinAdvisor`) aplica SOLO a leads que entran por WEBHOOK (`createLead` con `assignment.mode='round_robin'`, vía `lead-webhook`). Leads de origen Whaapy (heredan el agente) y Shopify NO rotan; las opps Outbound tampoco. El pool = `listRotationEligibleVendors` (activos, reales, rol vendedor, `in_lead_rotation=true`). El flag `memberships.in_lead_rotation` (0045, default true = todos los elegibles siguen elegibles) es admin-gestionable (toggle en Editar usuario, action `updateUserRotationAction`, solo vendedores). Pool vacío → lead sin asignar + aviso al admin, nunca bloquea. **`listRotationEligibleVendors` se usa SOLO en el round-robin** — el resto (selectores, mapeo de tags, reasignación manual) sigue con `listActiveRealVendors` sin filtrar por el toggle.

## Middleware, scripts y tipos

### Middleware redirigía endpoints server-to-server a `/login`
- **Causa raíz:** el matcher cubría todo salvo assets, incluyendo `/api/webhooks/*` y `/api/inngest`. Los webhooks llegan sin cookies → `getUser()` null → 307 a `/login`. Invisible en dev (el browser lleva cookie).
- **Regla:** excluir `api/webhooks` y `api/inngest` del **matcher** (no de `PUBLIC_ROUTES` — eso seguiría corriendo `getUser()` por webhook). El primer commit que crea un endpoint server-to-server bajo `/api/*` actualiza el matcher y se valida con `curl -X POST -i` SIN cookies que la respuesta no sea 307.

### Scripts tsx no pueden importar `server-only`
- **Causa raíz:** `server-only` es un marker package que Next.js aliasea en build; fuera del bundler Node no lo resuelve (y su `index.js` lanza error sin la condition `react-server`).
- **Regla:** `scripts/_lib/server-only-shim.ts` (vacío) + `scripts/tsconfig.json` con `paths: { "server-only": [...] }`; los scripts npm corren `tsx --tsconfig scripts/tsconfig.json`. El tsconfig raíz NO se toca (Next.js conserva el `server-only` real). **Todo script bajo `scripts/` que importe (directa o transitivamente) algo de `lib/` corre vía ese tsconfig.**

### `Insertable<R>` exige TODA columna no-auto-generada (defaults SQL no eximen al TS)
- **Causa raíz:** `Insertable<R>` (hand-written) solo hace opcionales `id`/`created_at`/`updated_at`; cualquier otra columna del Row es requerida aunque tenga `DEFAULT` en SQL.
- **Regla:** helpers `buildXxxInsert(...)` por aggregate con todos los defaults explícitos (`null`/`false`) en un solo lugar. **Al sumar una columna no-default a un Row, `tsc` lista todos los inserts a actualizar — seguirla, no asumir que el default de BD la hace opcional en el tipo.** NO agregar `?` manual al Row (lo enmascara como nullable en lecturas). Para columnas nuevas que romperían callers V1, relajar el tipo Insert: `Omit<Insertable<Row>, "col"> & Partial<Pick<Row, "col">>`. Se simplifican todos al habilitar el generador de tipos.

### supabase-js 2.105 — `Database` type hand-written incompatible
- **Causa raíz:** 2.105 espera en el generic `Database` los campos `Relationships: []` + marker `__InternalSupabase` que la forma hand-written omite → cada tabla colapsa a `never` y rompe insert/update.
- **Regla:** clientes (`admin/browser/server`) sin parametrizar (`SupabaseClient` sin generic); los Row types se aplican como tipos de retorno explícitos en el data layer. Regenerar con `supabase gen types typescript` cuando el CLI esté habilitado y restaurar el generic.

### Credenciales Shopify por organización: `vault_keys` JSONB
- **Causa raíz:** Supabase Vault (`vault.create_secret`) no está habilitado por default en Free tier.
- **Regla:** `lib/vault/index.ts` usa `organizations.vault_keys` JSONB (`{ shopify: {client_id, client_secret, access_token, access_token_expires_at}, whaapy: {api_key, webhook_secret}, whaapy_postventa: {api_key, webhook_secret, inbound_token} }`), leído solo con `service_role`. `access_token` cacheado con TTL. **Mantener la API estable** (`getShopifyClientId(orgId)`) para que migrar a `vault.secrets` en V2 solo toque la implementación interna.

### El fallback a env de las credenciales era un fallo de aislamiento multi-tenant (fail-closed, 0046)
- **Causa raíz:** cada getter del Vault caía a una variable de entorno GLOBAL (`SHOPIFY_API_KEY`, `WHAAPY_API_KEY`, …) cuando el bag de la organización estaba vacío. Con una sola organización pasaba por comodidad; con dos, la organización nueva —sin credenciales propias— autentica en silencio contra la tienda Shopify y el Whaapy de la PRIMERA: escribe en el sistema equivocado sin un solo error. Además cambiar una env var movía las credenciales de toda organización con el bag vacío. Estado real medido antes del fix: Centr tenía `vault_keys.shopify` VACÍO y `whaapy.api_key` ausente — operaba 100% por env.
- **Regla:** los getters resuelven EXCLUSIVAMENTE del bag de su organización y lanzan `VaultMissingCredentialError` (nombra namespace+key+org, nunca el valor) si falta. Un secreto es per-tenant y el env es global: no hay versión segura de mezclarlos. Guard `vault-fail-closed.test.ts` corre con el env POBLADO a propósito — si alguien reintroduce el fallback "por conveniencia", los tests fallan. **Antes de desplegar un cambio que retire un fallback, medir el estado real de producción** (`maintenance:adopt-env-credentials --dry-run` imprime qué hay en Vault sin revelar valores); retirar un fallback del que producción depende es una caída, no una mejora. Materialización env→Vault: `npm run maintenance:adopt-env-credentials -- --org-slug <slug>` (idempotente, nunca pisa lo ya presente).

### Cambiar el sistema externo conservando sus IDs fusiona entidades de dos sistemas (reemplazo de conexión, 0046)
- **Causa raíz:** `matchContactIdentity` matchea por `shopify_customer_id` en su tier 1. Si la tienda cambia y los ids viejos sobreviven, el customer #123 de la tienda NUEVA matchea contra el contacto que guardaba el #123 de la VIEJA → dos personas fusionadas en silencio (misma clase que "Teléfono compartido entre dos customers"). Igual con `whaapy_contact_id` (un PATCH outbound escribe en el contacto de un desconocido) y `memberships.whaapy_agent_id`.
- **Regla:** cambiar un discriminador (`shopify_store_domain`, `whaapy_business_id`, `whaapy_postventa_business_id`) con datos enlazados está BLOQUEADO en la action; el único camino es el RPC atómico `replace_integration_connection` (0046, sin bloque EXCEPTION → rollback total), que desenlaza toda identidad externa del proveedor, limpia su bag de Vault y sube `generation`. **Desenlazar ≠ borrar:** oportunidades, pedidos, montos, etapas, historial y asesores quedan intactos (guard estático `integration-replace-rpc-contract.test.ts` INV-2 verifica que no haya DELETE). `orders.shopify_order_id` es `NOT NULL + UNIQUE` → se PREFIJA (`unlinked:g<N>:<original>`) en vez de anularse: preserva el valor, mantiene el invariante y garantiza que un id idéntico del sistema nuevo no colisione. El dry-run usa la MISMA función SQL que el desenlace (`count_integration_linked_rows`) — si se separan, el preview miente. **Desconectar es otra cosa:** borra credenciales y NADA más (los ids se conservan; reconectar el mismo sistema restaura el enlace).

### Endpoint de Shopify: `unknown_shop` respondía 200 sin dejar rastro en BD
- **Causa raíz:** el path "dominio no registrado" corre ANTES de resolver el tenant (no puede escribir `audit_log`, cuyo `organization_id` es NOT NULL) y solo emitía un `console.warn`. Síntoma indistinguible de "la tienda no tiene actividad" — y es exactamente el error que un admin puede cometer ahora que puede editar el dominio desde la UI.
- **Regla:** el endpoint de Shopify persiste toda request en `whaapy_raw_webhooks` con `endpoint='shopify'` y taggea `exit_reason` en CADA salida (`missing_headers`, `unknown_shop`, `missing_secret`, `invalid_hmac`, `dedup_hit`, `unhandled_topic`, `invalid_json`, `enqueue_failed`, `enqueue_succeeded`) — misma lección que Whaapy en M4, aplicada al proveedor que la tenía diferida. Helper compartido `lib/db/webhook-ingress.ts`; **los headers portadores de credencial se REDACTAN al persistir** (la tabla no tiene RLS a propósito, para sobrevivir a la no-resolución de tenant). La tarjeta de Admin → Integraciones lee esos conteos: distingue "muda porque nadie escribe" de "muda porque tiramos todo lo que llega".

### Gotchas de SDK/build (TS strict, Inngest v4, Vitest, Next.js)
- **`"use server"` solo exporta funciones async** — un `const` objeto rompe `next build` ("can only export async functions"); `tsc` no lo caza. Constantes/defaults van en un módulo aparte sin `"use server"`, importadas con `import type`. **Correr `next build` antes de cerrar, no solo el typecheck.**
- **Target TS < es6:** NUNCA iterar `Map`/`Set` con `for...of`/spread (usar `Array.from(...)`); nada de regex unicode `\p{...}`/flag `u`. Restricción del target fijado.
- **recharts v3:** los callbacks (`formatter`, `tickFormatter`, `labelFormatter`) tipan valores como `ValueType`/`NameType` (uniones que incluyen `undefined`). No anotar parámetros estrechos; coercir con `Number()`/`String()` en el cuerpo.
- **Inngest v4:** `EventSchemas` desapareció; `createFunction(opts, handler)` (2 args) con `triggers: [{event}]`; `event.data` es `unknown` → castear explícito (productor único). `retries` es union de literales 0..20 — aliasear `type InngestRetries = 0|...|20`.
- **`vi.mock` se hoistea a module-top** aunque esté dentro de una función → pierde el closure. Declararlo a module-top del archivo de test con la instancia `fake` como `const` arriba; el helper solo exporta la clase reutilizable.
- **Dependencias del dashboard:** "documentado en la doctrina" ≠ instalado — verificar `package.json` real. Usar **`exceljs`** (mantenido) en lugar de `xlsx`/SheetJS (deprecado + advisories en npm). No correr `npm audit fix --force` (rompe el stack fijado).
- **Zod v4 (4.4.x):** `invalid_type_error`/`required_error` se eliminaron del constructor (`z.number({...})`) → usar `{ error }` o pasar el mensaje en `.refine()/.min()` (forma string sigue válida). `z.string().uuid()` valida **RFC 4122 estricto** (nibble de versión 1-8 + variante 8/9/a/b): UUIDs de prueba tipo `11111111-1111-1111-1111-111111111111` son RECHAZADOS — los fixtures de test deben usar UUIDs válidos (`…-4xxx-8xxx-…`), si no `safeParse` falla y el test verifica la rama equivocada.
- **`"use server"` SÍ puede exportar `type`/`interface`** (se borran en compilación; el check solo aplica a exports en runtime). Solo los VALORES no-función rompen el build (un `const` objeto). Patrón vivo: `lib/actions/dashboard.ts` exporta interfaces + actions y compila.

## Dashboard y KPIs (fechas reales de Shopify, win rate)

### Orders fechadas por `created_at` de BD en vez de la fecha real de Shopify (migración 0024)
- **Causa raíz:** `orders` nunca guardó la fecha de creación del Order en Shopify; el dashboard filtraba/agrupaba por `created_at` (= hora del INSERT local) → órdenes históricas importadas contadas en el mes de importación. El mapper ya extraía `normalized.createdAt` pero el worker no lo persistía.
- **Regla:** columna `orders.shopify_created_at` (nullable, índice parcial); worker + backfill la pueblan (`coalesce` defensivo en update). Dashboard cuenta "Pedidos en el periodo" por `shopify_created_at` (pagados + pendientes). **Revenue NO se toca (sigue por `paid_at`, R5).** Filtro excluye NULL (no se inventa fecha). **Distinguir SIEMPRE "fecha del evento en el sistema externo" de "fecha de entrada a la BD".** Correctivo verifica existencia (GET 404) y reporta ANTES de actuar; un huérfano (sin `opportunity_id`) puede ser válido (O6) — nunca borrar por inferencia.

### KPIs de opportunities / opportunity_stage_history fechados por importación (migración 0025)
- **Causa raíz:** `opportunities.created_at`/`opportunity_stage_history.changed_at` son `default now()`; `won_at` se setea `now()`. Al importar históricos, todo queda fechado en la importación. A diferencia de orders, `opportunities` MEZCLA filas de Shopify (Cotizaciones con draft) y nacidas en plataforma (lead R12, win manual).
- **Regla:** fecha efectiva = **`COALESCE(shopify_date, platform_date)`** materializada como columna generada (filtrable/indexable — PostgREST no expresa COALESCE en `.gte()`): `opportunities.shopify_created_at` + `effective_created_at`; `opportunity_stage_history.shopify_event_at` + `effective_event_at`. `won_at` corregido in situ = `orders.shopify_created_at` (momento de conversión draft→orden, NO `paid_at`). **`opportunity_stage_history` es inmutable** (`tg_block_mutation`): no re-escribir `changed_at` — agregar columna nueva y relajar la guarda SOLO para `shopify_event_at` (DELETE y el audit trail siguen bloqueados). Distinción genuino-vs-importación por **`context`** (`webhook`/`trigger_f1_f2` → re-fechar; `manual`/`automation` → conservar), no por heurística temporal.

### El filtro de fecha del kanban usaba `created_at` (importación), no `effective_created_at`
- **Causa raíz:** `listKanbanOpportunities`/`countKanbanOpportunitiesByStage` filtraban `dateFrom`/`dateTo` por `created_at` (hora de INSERT local), mientras el dashboard ya usaba `effective_created_at` = COALESCE(shopify_created_at, created_at) (migración 0025). Las opps backfilleadas (M11) tienen `created_at` = fecha de importación → el filtro del pipeline las metía en el periodo de importación, no en su periodo real, y la MISMA opp caía en un mes distinto en pipeline vs dashboard.
- **Regla:** el kanban filtra por `effective_created_at` (indexado por `opportunities_org_effective_created_at_idx`), igual que el dashboard. Toda vista que "acota por cuándo se creó la opp" usa la fecha REAL de Shopify, no la de entrada a la BD — la lección de 0024/0025 aplica al pipeline, no solo al dashboard.

### Piso de visibilidad del pipeline (cutoff de arranque) — `last_modified_at` lo bumpean fuentes automáticas
- **Causa raíz:** Centr quería que el kanban mostrara solo opps desde una fecha de arranque (1-jun-2026) "sin importar filtros", conservando los tratos viejos AÚN trabajados. El filtro de fecha es del usuario (ajustable) → no impone un piso; y usar `last_modified_at >= corte` crudo resucita opps viejas inertes que un sync automático tocó (el motor de Post-venta escribe `source='automation'`, el trigger F1→F2 `source='trigger_f1_f2'`, los webhooks Shopify `source='shopify'`, todos con `last_modified_at=now`).
- **Regla:** piso DURO e incondicional en el data layer del kanban (`listKanbanOpportunities` + `countKanbanOpportunitiesByStage` + `getKanbanOpportunityById` del refresh de realtime), NO un archivado (nada se muta): `effective_created_at >= minIso OR (last_modified_at >= minIso AND last_modified_source NOT IN (automation, trigger_f1_f2, system))`. Config-driven en `organizations.config.pipeline.min_effective_date` (default `DEFAULT_PIPELINE_MIN_DATE=2026-06-01`, leído como inicio de día CDMX vía `readPipelineMinDateIso`). El PostgREST `or()` usa `neq` por cada fuente automática (no `not.in`, más robusto). El backfill M11 NO envenenó la señal: escribió `last_modified_at = fecha real de Shopify` (`d.updatedAt`), no la de importación — por eso las inertes ya quedan ocultas por ambos brazos. Solo visualización: dashboard/búsqueda/KPIs intactos (no pasan por este data layer). Whaapy bumpea `last_modified_at` del CONTACTO, no de la opp → no es vector. Trade-off aceptado: una opp trabajada por humano y luego tocada por webhook pierde su marca humana (columna única sobrescrita) — cae al arranque `effective_created_at`; precisión total exigiría una columna `last_human_activity_at` dedicada.

### Filtro de fecha custom no se aplicaba; Pipeline $/Activas eran snapshot fijo
- **Causa raíz:** (a) el rango custom se auto-aplicaba en `onChange` y retornaba temprano con una fecha vacía → "no pasa nada" silencioso; (b) `listLivePipelineOpps()` no recibía periodo.
- **Regla:** botón **"Aplicar" explícito** para rangos con campos interdependientes (deshabilitado hasta ambas fechas llenas), no auto-aplicar sobre estado parcial. Todo KPI que el usuario espera "acotado al periodo" recibe el periodo en su query. (Ver también la distinción snapshot vs periodo, abajo.)

### "Activas" y "Pipeline $" mezclaban snapshot del ahora con actividad del periodo
- **Causa raíz:** un único query (`listLivePipelineOpps`, filtrado por `effective_created_at`) alimentaba "Activas" y "Pipeline $", pero el kanban (`listKanbanOpportunities`) no filtra por fecha → conteos distintos para "el mismo" concepto.
- **Regla:** separar **estado actual (snapshot)** — lo vivo AHORA, no responde al filtro de fecha (`listLivePipelineSnapshot`, misma definición de "viva" que el kanban: org + venta + `cancelled_at IS NULL` + `won_at IS NULL`) — de **actividad del periodo** (sí responde a fecha). Si una métrica del dashboard pretende reflejar lo que otra vista muestra, anclar ambas al mismo helper o documentar por qué difieren. Pipeline $ sigue BRUTO y excluye ganadas/perdidas/canceladas en ambas variantes.

### Auto-ocultar cerradas — `lost_at` materializado (migración 0026)
- **Causa raíz:** el kanban debe ocultar Ganadas/Perdidas tras N días; existía `won_at` pero "Perdida" solo vivía en `opportunity_stage_history` (cruzarlo en cada render reintroduce lag).
- **Regla:** columna `opportunities.lost_at` espejo de `won_at` (poblada hacia adelante en `pipeline-move.ts`, backfilleada del historial); cerrada con timestamp NULL no se oculta. El filtro de ocultar vive SOLO en el data layer del kanban (`listKanbanOpportunities`/`countKanbanOpportunitiesByStage`), NO en el dashboard (sus queries no pasan por ahí → KPIs intactos). Gotcha: `.select(variable_dinámico)` rompe la inferencia de PostgREST (colapsa a `ParserError`) → castear `as unknown as Array<...>` o usar dos `.select(literal)` ramificados.

### Pipeline M6: filtros silenciosos, conteos lentos, URL Shopify, autoría
- **Causa raíz:** (1) `.or()` de PostgREST mezclando predicados de tabla principal + embedded se ignora en silencio; (2) filtro de fecha usaba `last_modified_at` (se actualiza con cada webhook) en vez de `created_at`; (3) `countKanbanOpportunitiesByStage` traía todas las filas con `!inner` join para contar en JS; (4) URL `https://{domain}/admin/customers/{id}` redirige a root; (5) autoría desde `user_profiles.full_name` sembrado con el nombre del operador.
- **Regla:** (1) pre-resolver la sub-query a IDs y aplicar `contact_id.in.(...)` sobre la tabla principal — `.or()` con embedded resources es trampa silenciosa; (2) "fecha de creación" = `created_at`, no `last_modified_at`/`updated_at`; (3) queries de count usan `count:'exact', head:true` + `.limit()` defensivo + select mínimo — sin eso el costo escala con la tabla entera; (4) URL admin moderna = `https://admin.shopify.com/store/{handle}/customers/{id}` (handle = parte antes de `.myshopify.com`); (5) el display de "quién hizo qué" prioriza el campo que el usuario controla (`auth.users.raw_user_meta_data.full_name`) sobre el sembrado.

### Cancelado ≠ Perdido (migración 0014)
- **Causa raíz:** `draft_orders/delete` movía la opp a etapa `is_lost` → cancelaciones administrativas (DO borrado/duplicado/auto-borrado de Shopify >1 año) contaban como pérdida comercial e inflaban el win rate del vendedor.
- **Regla:** "Perdida" = transición real del pipeline (requiere motivo, impacta win rate). Cancelación = **side-flag** independiente de etapa: `cancelled_at` + `cancellation_source` + `cancellation_note` (la etapa se PRESERVA, NO se inserta en `opportunity_stage_history`). `listOpportunities` excluye canceladas por default (opt-in `includeCancelled`/`onlyCancelled`). **M5 kanban** y **M6 detalle**: default (excluir). **M10 win rate**: denominador = Ganadas + Perdidas SIN canceladas (`cancelled_at IS NULL`). **M10 revenue**: por `orders.paid_at` (R5) — la cancelación de opp no afecta revenue. Patrón aplicable: "snoozed"/"archivado"/"duplicado fusionado" tampoco son etapas — flags ortogonales con exclusión por default.

### Decisiones de cómputo del dashboard (intencionales, no-bugs)
- El **desglose por vendedor NO suma al total**: el usuario sistema "Histórico" (R10) se excluye de filas pero su revenue/conteos entran en los totales de la org.
- **Leads/Calificados/Cotizaciones excluyen canceladas** (consistente con "cancelado ≠ perdido", evita inflar con duplicados absorbidos R12).
- **Pipeline $ y Activas son SNAPSHOT** (estado vivo, no acotado al periodo); el resto de KPIs sí respeta el periodo.
- **Tasa de recompra** usa ventana fija de 12 meses (`DASHBOARD_REPURCHASE_WINDOW_MONTHS`).
- **Win rate por etapa:** "avanzó" = alcanzó (en cualquier momento) una etapa de posición mayor que no sea la perdida; muestra <10 → "Muestra pequeña" (`DASHBOARD_STAGE_WINRATE_MIN_SAMPLE=10`).
- **Frontera "Cotización"/"Contacto calificado"** se ancla por NOMBRE una vez para obtener su POSICIÓN; toda clasificación posterior es por `position` (etapas editables por admin; fallback en `dashboard-stages.ts`).

### Tooltips de KPI clipeados por `overflow-hidden`
- **Causa raíz:** `overflow-hidden` en la tarjeta (para redondear barra de acento) recorta cualquier popover hijo que desborde.
- **Regla:** lograr el redondeo con `rounded-xl` sobre background tintado (no requiere `overflow-hidden`) o portalizar el popover. Tooltip local mínimo (`<button>` enfocable + estado local + `role="tooltip"` + `aria-describedby`, texto estático) — CLAUDE.md prohíbe deps sin aprobación, no hace falta Radix.

### Track de barra (semáforo de metas M2v2) invisible en dark sobre tarjetas slate-800
- **Causa raíz:** el track usaba `dark:bg-slate-800`, idéntico al fondo de la tarjeta contenedora → la porción VACÍA de la barra desaparecía en dark mode (solo se veía el relleno).
- **Regla:** el fondo de un elemento (track, chip, input) debe contrastar con la SUPERFICIE donde vive, no solo "ser un neutro". Para barras sobre tarjetas slate-800: `bg-slate-200 dark:bg-slate-700`. Probar componentes reutilizables en AMBOS modos sobre su superficie real, no en aislamiento (un swatch sobre fondo blanco oculta el bug).

## Motor de Reglas y Mi Día (M1v2)

### Motor de Reglas + Mi Día — decisiones estructurales
- **Alcance V2:** las reglas SOLO `create_task`/`notify_advisor`/`notify_admin`. Acciones que modifican la opp (`move_to_stage`, `add_tag`, `assign_*`) **prohibidas en dos capas**: migración 0029 las depura de data + bootstrap; el motor las rechaza en ejecución (`parseActions` filtra elemento por elemento). Solo triggers de TIEMPO cableados (`stage_aging`, `no_activity`, `contact.no_activity`) vía cron horario; los de evento quedan latentes.
- **Idempotencia R4:** no se duplica tarea/aviso mientras siga ABIERTO (pending|snoozed) el de la MISMA regla para el MISMO sujeto (`tasks.created_by_rule_id`; `notifications.origin='rule'` + `origin_reference->>'rule_id'`). Circuit breaker hardcodeado (`MAX_SUBJECTS_PER_RULE_PER_TICK=300`, `CIRCUIT_BREAKER_EXECUTIONS_PER_HOUR=600`) → autodesactiva + alerta.
- **`bootstrap_organization` re-CREATE** siempre desde la versión VIGENTE (patrón de 0027), copiando el cuerpo entero con el único delta.
- **"Última actividad de plataforma"** (Clientes silenciosos + `no_activity`): agrega cambio de etapa, tarea completada, nota/actividad, orden, reasignación manual. NUNCA `last_whaapy_activity_at` (los mensajes Whaapy no se sincronizan).
- **Aislamiento del vendedor:** filtro de aplicación (`assigned_user_id`/membership) forzado en actions + filtro explícito `organization_id` (service_role bypassa RLS). NO es RLS para "solo lo mío".

### Mi Día pintaba opps sin tarea (centro mezclaba tasks + notifications)
- **Causa raíz:** el centro derivaba cards de DOS fuentes (`tasks` + `notifications`); el detalle de la opp lee SOLO `tasks`. Reglas solo-`notify_admin` (o opps sin asesor donde `create_task` se omitía) producían card-fantasma sin tarea detrás.
- **Regla:** centro = **SOLO tasks** (misma fuente que el detalle); los avisos viven solo en la campanita. Toda regla `create_task` crea la tarea **incluso sin asesor** (fallback al admin determinista `fallbackAdminUserId`) — una vista que depende 100% de que un registro exista debe garantizar su creación con destinatario de respaldo. Si dos vistas que muestran "lo mismo" leen fuentes distintas, convergir a una sola fuente es el fix.

### Tareas/avisos de regla se recreaban al tick siguiente (sin cooldown de re-insistencia)
- **Causa raíz:** la idempotencia R4 solo mira registros ABIERTOS → al completar/cerrar, el tick siguiente (≤1h) lo recreaba si la condición persistía.
- **Regla:** cooldown anclado al cierre del último registro, ventana = **umbral propio de la regla** (`thresholdHoursFromConfig`; 24h→24h, 72h→72h — cada regla insiste a su ritmo, no un valor global). Tareas: `hasRecentlyCompletedRuleTask` (ancla `completed_at`). Avisos: `hasRecentlyClosedRuleNotification` (ancla **`updated_at`** — `dismissNotificationAction` no estampa `completed_at`; debe cubrir todas las formas de cierre incl. `dismissed`). Una idempotencia basada solo en "registro abierto" recrea al instante apenas se cierra.
- **Hallazgo sin bug:** las reglas crean tareas con `due_at: null` → `bucket(null)` = "hoy", no atrasada. Solo una tarea manual con `due_at` pasado cae a "Atrasada".

### La creación de tarea ya no cuenta como "actividad de plataforma"
- **Causa raíz:** `lastPlatformActivity*` hacía `bump` con `tasks.created_at` Y `completed_at` → que una regla/sistema creara una tarea reseteaba el reloj de "silencioso" sin acción humana.
- **Regla:** solo `completed_at` cuenta (ahí hubo acción humana). "Última actividad real" excluye los eventos que el SISTEMA genera en nombre del usuario. Verificado que la creación no se cuela por otra vía (registra `audit_log`, no fila en `activities`).

## Motor de transiciones de Post-venta (M3v2)

### El motor lee la fila `orders` persistida, no el payload del webhook
- **Causa raíz:** evaluar el estado contra el payload reintroduciría lógica de timestamps/LWW y sería vulnerable a webhooks tardíos/desordenados.
- **Regla:** `evaluatePostventaTarget` (núcleo puro, `lib/services/postventa-engine.ts`) lee la fila `orders` ya reconciliada por LWW (`upsertOrderShell`) → hereda esa protección sin lógica de timestamps propia. Precedencia (cambio 0036) **entrega > pago**: `delivery_status` delivered→Entregado, in_progress→Envío en curso; sin señal de entrega (null) → pago: paid→Pago confirmado, pending **y partially_paid**→Cotización completada. `cancelled`/`refunded`/`partially_refunded` → "Caso problemático" (one-way, evaluado ANTES). Estado inesperado → no mover (`none`), registrar. **`fulfillment_status` (preparación) YA NO participa** en la decisión (ver entrada "Envío/Entregado por estado de ENTREGA").

### "Caso problemático" es un SUMIDERO del motor (avance solo desde la zona 1-4)
- **Regla:** el driver `applyPostventaTransition` AVANZA solo si la opp está en una de las 4 etapas pago/preparación (la "zona", anclada por nombre con fallback posicional, patrón `dashboard-stages.ts`); el PROBLEM-EXIT (→ Caso problemático) dispara desde cualquier etapa activa excepto la propia Caso problemático. Como Caso problemático **nunca** es origen de avance ni de problem-exit, una opp resuelta+archivada que vive ahí queda intocada SIN chequear `resolved_at` en el driver. Idempotente (solo mueve si la etapa difiere); usa `moveOpportunityStage` con `context='automation'`/`actorUserId=null` (trazable) y **NO toca `assigned_advisor_id`** (R2/R5 intactos). Carrera con movimiento manual → `stale_version` → reintenta el próximo tick. Hook inline en `orders.ts` (no-fatal) + cron horario `postventa-transition-engine-hourly` (red + backfill histórico en la 1ª corrida).

### Un cron de mutación masiva NO debe correr solo al desplegar — kill switch + dry-run
- **Causa raíz:** un cron horario registrado movería todas las opps históricas en su primer tick tras el deploy, antes de poder revisar el resultado sobre datos de producción.
- **Regla:** gatear los DOS puntos de entrada automáticos (cron + hook inline) con `POSTVENTA_ENGINE_ENABLED` (default OFF, `isPostventaEngineEnabled()`). Habilitar SOLO tras revisar el preview read-only `npm run maintenance:preview-postventa-transitions` — que comparte la función de decisión `decidePostventaStageMove` con el run real, así "lo que mostraría" es bit-a-bit lo que ejecutaría (anti-deriva). El preview y el cierre manual de casos NO se gatean. El motor también se suprime por `organizations.backfill_in_progress` (modo pasivo M11), guardado dentro del driver (única fuente para hook + cron). **Toda mutación masiva automática nace detrás de un kill switch + dry-run que comparte la decisión con el run real.**

### Envío/Entregado por estado de ENTREGA, no preparación; capturado read-only (read_orders), sin webhook fulfillments/* (cambio 0036)
- **Causa raíz:** "Entregado" debe reflejar la entrega REAL al cliente, no que el pedido se haya despachado. `orders.fulfillment_status` (null/partial/fulfilled) es PREPARACIÓN del pedido, distinta del estado de ENTREGA que vive en el FULFILLMENT individual (`displayStatus`/`shipment_status`). Centr muestra dos valores: "Seguimiento añadido" y "Entregado" (carrier FedEx). "Seguimiento añadido" NO es un literal del enum: cuando el carrier aún no escanea, `shipment_status` viene NULL aunque exista tracking — atar la etapa a un enum perdería ese estado.
- **Regla:** columna `orders.delivery_status` normalizada (migración 0036): `delivered` / `in_progress` / null, derivada por `normalizeDeliveryStatus` (`lib/shopify/delivery-status.ts`, puro) con la señal **"hay tracking y no entregado" = in_progress** (robusto al NULL de "Seguimiento añadido" y a in_transit/out_for_delivery). Multi-fulfillment: delivered solo si todos los con-señal entregados, si no in_progress. **Scope read-vs-subscribe (clave):** LEER el objeto `Fulfillment` (displayStatus/deliveredAt/trackingInfo) está cubierto por **`read_orders`** (validado contra el schema); SUSCRIBIR el webhook `fulfillments/create|update` exige **`read_fulfillments`** (≠ read_orders) + re-instalación de la app. Por eso NO se suscribe el webhook: el cron horario hace **pull** (`fetchOrderDeliveryStatus`, `lib/shopify/order-delivery.ts`) y persiste vía `refreshDeliveryStatusForOpp` antes de decidir. `orders/updated` NO se dispara de forma garantizada en el "delivered" scan del carrier (el `fulfillment_status` del pedido sigue `fulfilled`), así que el pull es la vía confiable; el hook inline de `orders/*` solo aprovecha los fulfillments embebidos del payload (gratis). Latencia ≤1h, tolerable en Post-venta.
- **Regla (anti-retroceso):** `decidePostventaStageMove` dentro de la zona SOLO avanza (`target.position` estrictamente **>** la actual → mueve; igual → `already_in_target`; menor → `advance_no_backward`). Sin esto, al cambiar el criterio una opp ya en Entregado (por el `fulfilled` viejo) rebotaría a Envío/Pago si la señal de entrega aún no llegó. El PROBLEM-EXIT (→ Caso problemático) queda **exento** (un reembolso manda al sumidero desde cualquier etapa). `delivery_status` se popula histórico con `npm run maintenance:backfill-order-delivery-status` (read-only en `--dry-run`) ANTES del dry-run del motor.

### `is_won` reusado en Post-venta "Caso cerrado" — válido porque el funnel filtra airtight (migración 0033)
- **Causa raíz:** M4v2 necesita una terminal de cierre normal en Post-venta ("Caso cerrado", renombrada in situ desde "Cliente activo", pos 6) que se archive EXACTO como Ganada/Perdida. El mecanismo de archivado (auto-ocultar + "Ver cerradas") deriva de `is_won`/`is_lost` (`partitionClosedStages`/`closedFilterForStage`) + `won_at` que `pipeline-move` setea al entrar a una etapa `is_won`. Marcar la etapa `is_won` reusa todo ese camino sin path paralelo. Riesgo: "is_won" nominalmente = venta ganada, y un cierre de Post-venta NO es venta → posible contaminación de win-rate/metas.
- **Regla:** se reusa `is_won` SOLO porque está PROBADO que ningún consumidor de Venta se contamina: win-rate/Cotizaciones/Ganadas/Pipeline$/metas (`lib/db/dashboard.ts`, `tallyAchievement`) filtran `funnel='venta'` en SQL; `resolveVentaStageBoundaries` busca `wonStage` solo en `listPipelineStages("venta")`; el motor de reglas cruza `terminalStageIds` contra opps ya acotadas a `rule.funnel`; `partitionClosedStages` recibe las etapas del funnel cargado. Donde `is_won` cambia algo en Post-venta es lo DESEADO (KPI "vivos" excluye cerrados; `users.ts` no los cuenta como pendientes; kanban auto-oculta). La UI muestra el NOMBRE "Caso cerrado", nunca "Ganada" (no hay badge de `is_won`). **Antes de reusar un flag con semántica de un dominio en otro, trazar TODOS sus consumidores y probar el aislamiento por la dimensión que los separa (aquí `funnel`); si es airtight, el reuso evita un camino paralelo.** No hay constraint de unicidad de `is_won` por funnel (solo `is_initial`, 0004).

### Migración de datos keyeada por nombre (mutable) salta filas pre-editadas a mano (0033 → correctivo 0034)
- **Causa raíz:** 0033 marcó `is_won`/color de la terminal Post-venta keyeando el UPDATE de orgs existentes por `WHERE name='Cliente activo'` (nombre SEMILLA). Centr ya tenía esa etapa renombrada A MANO a "Caso cerrado" en la BD viva antes de 0033 → el WHERE no la matcheó → quedó `is_won=false` (no archiva); Rustr (aún con nombre semilla) sí quedó correcta. El diagnóstico previo concluyó "Caso cerrado no existe" mirando solo migraciones/seed, sin ver el estado VIVO de la BD.
- **Regla:** una migración de datos que matchea filas vivas por una columna MUTABLE (name) salta en silencio cualquier fila hand-edited. **Keyear el correctivo por el ESTADO OBJETIVO y hacerlo idempotente** (0034: `WHERE name='Caso cerrado' AND is_won=false` → toca solo lo roto, no-op en orgs correctas y en bootstraps nuevos). Antes de una migración de datos sobre filas vivas, **dry-run que liste exactamente las filas a tocar** (SELECT del mismo WHERE) — el seed no es la verdad, la BD viva sí.

### "Caso cerrado" (is_won) sigue siendo origen válido de PROBLEM-EXIT del motor (interacción 0033)
- **Regla:** el cron alimenta el motor con `listActivePostventaOppIds` (`funnel='post_venta' AND cancelled_at IS NULL`, SIN filtrar `won_at`/`resolved_at`), así que las opps en "Caso cerrado" (archivadas, `won_at` seteado) siguen evaluándose. El driver NUNCA las AVANZA (pos 6 ∉ zona 1-4) pero SÍ puede dispararles PROBLEM-EXIT si su pedido se cancela/reembolsa → las mueve a "Caso problemático" (vía `moveOpportunityStage`, que limpia `won_at` → las des-archiva). Es el mismo comportamiento que tenía la vieja "Cliente activo" (también fuera de zona y origen de problem-exit) + el bonus de limpiar el flag de archivado: un auto-reopen-on-refund coherente con la reapertura manual de M4v2. NO es regresión. El motor sigue gateado por `POSTVENTA_ENGINE_ENABLED` (default OFF).

### Cierre de "Caso problemático": flag ortogonal `resolved_at`, etapa preservada (migración 0032)
- **Regla:** resolver un caso NO mueve la etapa (se queda en Caso problemático para auditoría) — `resolved_at`/`resolved_by_user_id`/`resolution_note` lo **archivan** de las vistas activas (mismo patrón que "cancelado ≠ perdido", 0014). `listKanbanOpportunities`/`countKanbanOpportunitiesByStage` excluyen `resolved_at IS NOT NULL` por default (opt-in `resolvedScope:'resolved'` para la vista "Casos resueltos"). El motor no toca resueltos (viven en el sumidero). Búsqueda por orden/contacto sigue encontrándolos (sin reopen — el flag permite des-setear en V2). Servicio `resolvePostventaCase` (guards: post_venta + en Caso problemático + no resuelto), audit `postventa_case_resolved`, **no toca asesor**. Al sumar `resolved_*` al Row, relajar el Insert de opportunities (`Omit … & Partial<Pick…>`) para no romper callers, y actualizar el SELECT + interfaz `KanbanOpportunity` + fixtures de test (tsc los lista).

### Reapertura a "Caso problemático": híbrida por funnel, nunca mutar la Venta (migración 0035)
- **Causa raíz:** reabrir una opp cerrada hacia "Caso problemático" (Post-venta) cruzando desde Venta. Mutar el funnel de una Venta Ganada/Perdida la sacaría del win-rate (denominador `funnel='venta'`) y rompería su historial; duplicar hijas Post-venta crea opps huérfanas.
- **Regla (`reopenOpportunityIntoProblemCase`, flujo HÍBRIDO):** opp **Post-venta** → muta en sitio (limpia `won_at`/`lost_at`/`resolved_at`/`cancelled_at`, set `reopened_at`, a Caso problemático; history solo si la etapa cambió). Opp **Venta** → NO se toca; se reabre su hija Post-venta existente (`findPostventaChildOpportunityId`) o, si no hay, se CREA una hija enlazada (`parent_opportunity_id`, hereda comercial como F1→F2 pero **NUNCA** `shopify_draft_order_id` — unique constraint, 0021). **NUNCA toca `assigned_advisor_id`** (R2/R5: hereda/preserva, no reasigna). `reopened_at` (0035) es flag de procedencia ortogonal (badge "Reabierto"), nullable+default NULL (opcional en Insert, patrón `Omit & Partial`). La opp reabierta vive en el sumidero → el motor no la arrastra. No toca el motor de transiciones.

### `searchOpportunitiesAnyState` es la ÚNICA lectura que ignora flags de archivado — scope por asesor obligatorio
- **Causa raíz:** la reapertura necesita encontrar opps en cualquier etapa/funnel incluidas cerradas/canceladas/resueltas, así que esta función NO filtra `cancelled_at`/`won_at`/`lost_at`/`resolved_at` (a diferencia de todo el resto del pipeline). Exponerla sin scope dejaría a un vendedor ver opps ajenas.
- **Regla:** cuando el caller es vendedor, pasa `assignedAdvisorId = membership.id` (CLAUDE.md "Vista de vendedor — scoping a nivel data"); admin pasa `undefined`. La action `reopenOpportunityAction` RE-valida permiso (admin o asesor dueño) porque el id llega del cliente. Toda lectura nueva alcanzable por vendedor aplica el mismo scope por asesor.

### Limpieza de "Ver cerradas"/"Casos resueltos" a 30 días: dos umbrales, solo visualización (M4v2)
- **Regla:** `CLOSED_LIST_RETENTION_DAYS=30` (fijo, corte CDMX vía `computeClosedListRetentionCutoffIso`). Modelo de dos umbrales por opp: `0–N días`→activo, `N–30`→solo "Ver cerradas", `>30`→fuera de ambas vistas, **vivo en BD**. El bucketing vive en `countKanbanOpportunitiesByStage` (3 estados: visible / hidden=revelable `[retención,cutoff)` / expired=descartada); "Ver cerradas (N)" cuenta SOLO lo revelable, no el histórico infinito. Resueltos usan el mismo umbral sobre `resolved_at`. Es SOLO visualización — ninguna query del dashboard pasa por este data layer (KPIs/revenue/win-rate intactos); nada se borra.

### Customer Success es una SEGUNDA ranura, no una reasignación de asesor (migración 0047)
- **Causa raíz:** el modelo tenía UNA sola ranura de persona por oportunidad (`assigned_advisor_id`) y la asignabilidad estaba cableada a `role='vendedor'` (invariante 0039). Meter al Customer Success por ahí habría borrado al vendedor que cerró la venta y contaminado la atribución (el vendedor perdía su opp de Post-venta y las métricas por asesor).
- **Regla:** `opportunities.customer_success_membership_id` es un eje INDEPENDIENTE. `assignOpportunityCustomerSuccess` ([lib/services/opportunity-customer-success.ts](lib/services/opportunity-customer-success.ts)) NUNCA toca `assigned_advisor_id` y NO emite `opportunity_reassigned` — ese evento es el contrato "reasignación manual del asesor" que los hooks 0022/0023 leen para no pisar; emitirlo aquí ensuciaría la señal. Su evento propio es `opportunity_customer_success_assigned`. "Un solo CS por opp" es estructural (una columna), no una regla que haya que hacer cumplir. El invariante de 0039 sigue vivo: `listActiveRealVendors` sigue filtrando `role='vendedor'` y un CS nunca entra a round-robin, mapeo de tags, agentes de Whaapy ni al selector de asesor — su catálogo propio es `listActiveCustomerSuccess`.

### El default de Customer Success vive en un trigger de BD porque Post-venta nace por 4 vías (una es SQL puro)
- **Causa raíz:** las opps de Post-venta se crean desde el trigger F1→F2 (0027, **SQL — no pasa por TS**), el webhook de Whaapy Post-venta, la reapertura de casos y el backfill. Poner el default en la capa de servicio habría dejado sin CS justo a la vía principal (la venta pagada).
- **Regla:** `tg_opportunity_default_customer_success` (BEFORE INSERT OR UPDATE OF funnel, 0047) cubre las cuatro y cualquier vía futura. Solo rellena cuando la columna viene NULL → jamás pisa una asignación manual ni el CS que hereda una reapertura. La persona se ancla por `membership_id` estable en `organizations.config.postventa.customer_success_membership_id` (mismo patrón que `resolver_user_id`): editar nombre/email no rompe nada; cambiar de persona es un UPDATE, no un deploy. La key `'customer-success'` está hardcodeada en TS (`CUSTOMER_SUCCESS_ROLE_KEY`) **y** en SQL — renombrar el rol de un solo lado desconecta la feature en silencio; lo cubre el guard `tests/customer-success-sql-contract.test.ts`.

### Un filtro exclusivo de un funnel debe limpiarse al cambiar de funnel
- **Causa raíz:** el select de Customer Success solo se pinta en Post-venta. Si el valor persistía al saltar a Venta, quedaba un filtro activo **invisible** (ninguna opp de Venta tiene CS) → tablero vacío sin explicación ni forma de limpiarlo.
- **Regla:** `changeFunnel` limpia `customerSuccessId` al salir de Post-venta, igual que ya apagaba `resolvedView`. El servidor además ignora el filtro fuera de `post_venta` (defensa en la capa de datos, no solo en la UI). El filtro viaja también en `loadKanbanPageAction`: sin eso la primera página respeta el filtro y el scroll trae opps de otros CS.

## tag_mappings y atribución

### tag_mappings huérfano (tag con 0 entidades)
- **Causa raíz:** `tag_mappings` es append-only (`upsert onConflict normalized_tag`) y NO refleja si la tag sigue viva. Una tag queda huérfana por corrección de ortografía/acento en Shopify, borrado de la entidad, o tag de prueba. La normalización actual (`trim().toLowerCase()`, SIN strip de acentos) es consistente.
- **Regla:** una tag con conteo 0 = señal de huérfano, eliminable manualmente desde la UI de Mapeo (`deleteTagMappingAction` re-verifica el conteo en servidor, bloqueado si >0). **Sin purga automática** (decisión manual del admin). NO asumir "fila en tag_mappings ⇒ tag activa".

### Crear mapeo de tag a mano (Bloque B) — anti-duplicado por normalización idéntica al parser
- **Causa raíz:** la pantalla de Mapeo era tag-céntrica (solo listaba tags ya detectadas en datos de Shopify), así que un vendedor nuevo no tenía ninguna fila a la cual asignarse hasta que su tag aterrizaba en ingest. Crear una fila a mano arriesga duplicar si la misma tag luego llega de Shopify con otra forma.
- **Regla:** `createTagMappingAction` normaliza la tag con EXACTAMENTE la misma función del parser (`trim().toLowerCase()`, sin strip de acentos) y la unicidad es `(organization_id, normalized_tag)` (citext) — así una tag creada a mano y la misma que luego llegue de Shopify colapsan a la misma fila (`parseShopifyTags` la encuentra por `normalized_tag` y NO auto-crea otra). La action **bloquea** si la fila ya existe (`getTagMappingByNormalized`) → el admin la edita desde la lista, no la re-crea. Si se cambia la normalización del parser, cambiar también aquí (deben coincidir o reaparecen duplicados).

## Integración Post-venta ↔ Whaapy Post-venta (segundo Whaapy, webhooks 1–4)

### `contact.stage_changed` no es un evento suscribible; el inbound va por Automation `http_request`
- **Causa raíz:** la doc de Funnels de Whaapy referencia `contact.stage_changed`, pero NO está en la lista real de eventos suscribibles (solo `contact.created/updated/deleted`, `conversation.*`, `message.*`, `broadcast.*`, `agent.*`). Además `contact.updated` no trae la etapa (solo `updated_fields` + name/phone) y no está confirmado que un cambio de etapa lo dispare.
- **Regla:** el webhook 3 (resolución Whaapy → plataforma) NO usa webhook firmado por HMAC. Usa una **Automation `http_request`** (trigger `pipeline_stage_entered` sobre "Caso Resuelto") autenticada con **token compartido** (`Authorization: Bearer` o header `x-centrhub-token` o body `token`; comparación constant-time contra Vault `whaapy_postventa.inbound_token`). Verificar SIEMPRE los eventos contra la lista/panel real del proveedor, no contra ejemplos de otra sección de la doc.

### Segundo Whaapy (Post-venta) totalmente aislado del de Venta
- **Regla:** todo el stack Post-venta usa namespace propio `whaapy_postventa` para no tocar el Whaapy de Venta: bag de Vault `{api_key, webhook_secret, inbound_token}`, namespace de dedup `whaapy_postventa`, endpoint `/api/webhooks/whaapy-postventa`, cliente `lib/whaapy-postventa/*`, columna `organizations.whaapy_postventa_business_id` (migración 0037), filas `whaapy_raw_webhooks.endpoint='postventa'`. Base URL compartida (`https://api.whaapy.com`). **Kill switch `POSTVENTA_WHAAPY_SYNC_ENABLED` (default OFF)** gatea TODO el outbound (webhooks 1,2,4); el deploy es seguro sin activarlo. Al agregar un segundo destino de un proveedor ya integrado, duplicar cada punto single-valued (credenciales, tenant lookup, endpoint, dedup, cliente) en vez de parametrizar el existente.

### Funnel de Whaapy es contact-céntrico → la resolución entrante NUNCA adivina
- **Causa raíz:** Whaapy tiene un solo funnel, **una etapa por contacto**, y NO existe entidad deal/card → no hay identificador por-caso. Un contacto con ≥2 casos activos es indistinguible desde Whaapy (un solo `custom_fields` por contacto; el push del 2º caso pisa el `centrhub_opportunity_id` del 1º). "Resolver el más reciente" archivaría potencialmente el caso equivocado.
- **Regla:** el worker inbound resuelve SOLO si el contacto tiene **exactamente 1** opp en "Caso problemático" no resuelta (candidatos scoped a esa etapa + `resolved_at IS NULL`); 0 → no-op; **≥2 → NO auto-archiva**: audit `postventa_whaapy_inbound_needs_manual_review` + notifica a Customer Success para resolver el correcto en la plataforma. Escalar a revisión manual es correcto; adivinar no. `resolvePostventaCase` reusa el flujo M4v2 (setea `resolved_at`, no mueve etapa) y guarda etapa+no-resuelto, así que ningún id fuera de "Caso problemático" se archiva por ninguna vía.

### Anti-bucle bidireccional de la resolución (webhooks 3↔4)
- **Causa raíz:** resolver en la plataforma mueve el contacto de Whaapy a "Caso Resuelto" (webhook 4), lo que dispara el inbound de vuelta (webhook 3) — y viceversa → eco infinito.
- **Regla (R11-style, dos capas + idempotencia):** capa 1 — `resolvePostventaCase` dispara el push saliente SOLO con `source="platform"`; el worker inbound llama con `source="whaapy_postventa_inbound"` → no re-propaga. Capa 2 — el push saliente **salta el `move`** si el contacto ya está en la etapa destino (no re-dispara el evento de Whaapy). Idempotencia — `resolvePostventaCase` sobre opp ya resuelta = no-op. Cortan el bucle por ambos lados.

### Disparo outbound cubre TODAS las vías; match por teléfono con AUTO-CREACIÓN
- **Regla:** los webhooks 1/2 se enganchan en `moveOpportunityStage` (motor automático + drag manual) Y en `reopenOpportunityIntoProblemCase` (botón "+", drag de reapertura, reapertura M4v2) — no hay choke point único, hay que cubrir ambos. El webhook 4 se engancha en `resolvePostventaCase`. Todos los hooks son **non-fatal** (encolan a Inngest tras el commit; fallo de Whaapy → retry → DLQ, nunca rompe el movimiento de la opp) y gateados por el kill switch. Match del contacto: por **teléfono E.164** (Whaapy Post-venta es instancia independiente; la plataforma no tiene su contact_id). Las variables de Automation NO exponen custom_fields (solo `{{contact.name/phoneNumber/email}}`, system, business), por eso el inbound recibe solo teléfono y resuelve por conteo de casos.
- **Regla (auto-creación — cases 1/2/4):** el Whaapy de Post-venta **arranca vacío** (la base maestra vive en el de Venta), así que si el contacto no existe por teléfono se **CREA** (`POST /contacts/v1` con name+phone+email+custom_fields) y LUEGO se mueve — nunca "registrar y no romper" (esa decisión previa dejaría todos los webhooks sin efecto). El mensaje automático se garantiza SIEMPRE vía el **move API** (crear con `funnel_stage_id` no está confirmado que dispare `pipeline_stage_entered`; el `move` sí) → crear-sin-etapa + mover. Idempotente: search-first + 409 `duplicate_contact` → enlaza `existing_contact_id` (cubre la carrera; el teléfono es único en Whaapy). **Sin eco:** crear dispara `contact.created` en Whaapy pero NO suscribimos ningún webhook del Post-venta Whaapy (el único inbound es la Automation de "Caso Resuelto"), y el Post-venta Whaapy no es fuente de contact-sync de la plataforma → crear/mover no llama de vuelta. Parseo del id del create: respuesta envuelta `{contact:{id}}` con fallback plano `{id}` (misma lección del wrapper del GET).

### Autoría de la resolución inbound = usuario real, anclado por user_id ESTABLE (no email ni nombre)
- **Causa raíz:** `opportunities.resolved_by_user_id` es FK a `user_profiles(id)` y el webhook corre server-side sin sesión. Anclar la atribución por **email o nombre es frágil**: el email es una credencial editable (M9.2) y el nombre puede renombrarse/tener typos/duplicados → un edit rompería la resolución.
- **Regla:** el resolutor es el usuario real "Customer Success", creado vía GoTrue `createUser` (login latente, rol vendedor) — NUNCA por SQL crudo (revienta GoTrue, ver "auth.users insertado por SQL crudo" + migración 0028). Se ancla por su **`user_id` estable** en `organizations.config.postventa.resolver_user_id` (lo escribe el seed `maintenance:seed-customer-success`; repuntable con `storePostventaResolverUserId`). Cambiar la PERSONA = editar email/nombre de ese membership (el `user_id` no cambia, repair-in-place lo preserva) → la atribución nunca se rompe. Sin resolver configurado → audit `postventa_whaapy_inbound_resolver_unresolved` + NO resolver (seguro).

### Contacto creado por API en el Whaapy Post-venta nace SIN conversación → las automatizaciones no le corren (rompe webhooks 1/2 y 3)
- **Causa raíz:** el Whaapy de Post-venta es un número de WhatsApp distinto al de Venta, así que un contacto que la plataforma crea ahí (`source=api`) nunca le escribió: nace con `conversations: []` y `assigned_agent_id: null`. Las acciones de automatización de Whaapy son conversación-céntricas — `send_message` solo vale dentro de la ventana de 24h de WhatsApp (fuera, error `131047`; hay que usar `send_template` aprobado por Meta), y sin conversación tampoco se observa disparar el `http_request` de la Automation. Resultado: el push de la plataforma llega **correcto** (contacto creado + movido de etapa, audits `postventa_whaapy_contact_created`/`_stage_pushed`) pero NO produce mensaje, ni agente asignado, ni conversación → invisible en la bandeja, que lista conversaciones y no contactos. En sentido inverso, mover ese mismo contacto a "Caso Resuelto" no llama al webhook 3 y el caso se queda abierto en la plataforma.
- **Regla:** el éxito del outbound **no** se mide por los audits del push — se mide por si el contacto quedó con conversación. Diagnóstico canónico: `npm run whaapy:diagnose-postventa`, bloque 7, columna `conv` — un `source=api` con `conv=0` frente a un `source=webhook` con `conv=1` en la misma etapa aísla el fallo dentro de Whaapy, no en la plataforma. Discriminante para descartar "automatización borrada/apagada": sacar y volver a meter en la etapa un contacto CON conversación; si ése sí dispara, la variable es la conversación. La automatización de "Caso Problemático" debe usar `send_template` (nunca `send_message`) + asignar agente; sin abrir conversación, ninguna automatización posterior de ese contacto corre.
- **Regla (dónde NO buscar):** `whaapy_raw_webhooks` inserta la fila **antes** de auth/parseo del body (`recordProductiveIngress` en `app/api/webhooks/whaapy-postventa/route.ts`) → **sin fila = la request nunca llegó a Vercel**, no es token inválido ni tenant mal resuelto. Y el inbound Option A resuelve tenant por `body.org` (slug) y autentica con `whaapy_postventa.inbound_token`: `organizations.whaapy_postventa_business_id` en NULL y `whaapy_postventa.webhook_secret` ausente **no participan** en este camino — no perseguirlos como causa.

## Notas operativas

### Protected Customer Data — Custom Apps tienen acceso automático
- **Regla:** los formularios de Protected Customer Data y el request manual de `read_all_orders` aplican SOLO a apps publicadas en el **App Store**. Las **Custom Apps** (Dev Dashboard, instalación 1-a-1 por OAuth — modelo Centr Hub) tienen acceso automático a Levels 1/2 y `read_all_orders` al instalar (consentimiento del merchant al aprobar scopes). Si una query de customers/orders devuelve vacío en producción, **es bug** (token, scope omitido, rechazo silencioso en instalación), NO restricción regulatoria. Antes de documentar bloqueos a milestones futuros, verificar bajo qué modelo de distribución opera la app.

### Verificar estado real contra el sistema externo antes de un correctivo
- **Lección:** antes de un correctivo sobre "datos rotos en producción", verificar el estado REAL contra el sistema externo en lugar de confiar en la premisa del reporte — la mitad del trabajo puede estar ya hecha por un worker en vivo (ej. `draft_orders/delete` ya cancelaba las cotizaciones "fantasma"). Cuando el prompt plantea un mecanismo "a futuro", confirmar primero si ya existe implementado. El barrido COMPLETO (no solo el set listado) da la certeza de "no quedan más casos".

### Herramientas de diagnóstico permanentes (lectura pura) — patrón `inspect-*`
- Cualquier integración inbound/outbound de un proveedor merece su `scripts/<proveedor>/inspect-*.ts` de lectura pura, registrado en `package.json`, reusando los clientes productivos (auth/rate-limit/error idénticos a los workers). **Invariante: el script NO escribe a BD propia, NO modifica el recurso del proveedor.** Existentes: `shopify:inspect-get-customer` (imprime todos los teléfonos candidatos con hex de codepoints para revelar BOM/NBSP/ZWSP invisibles + resultado de `normalizePhone`), `whaapy:inspect-get-contact`, `whaapy:inspect-webhook-headers`.

### Dirección estructurada de contacto: convivencia con campo plano legacy sin migración
- **Causa raíz:** `contacts.address` (jsonb) guardaba `{line1: <texto>}`; Shopify necesita campos separados.
- **Regla:** se pasó a estructurada (10 campos = Shopify Address) SIN migración (jsonb ya sin shape forzado = cambio de convención). Módulo puro compartido `lib/contacts/address.ts` (cliente+servidor, NO `server-only`): `parseStoredAddress` lee ambas formas y mapea alias legacy (`line1→address1`, `state→province`, `postal_code→zip`); al guardar persiste solo la forma canónica (promoción incremental al editar). `structuredAddressToShopify` es passthrough 1:1.
