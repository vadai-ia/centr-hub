# ERRORES.md — Bugs conocidos, workarounds y lecciones del proyecto Centr Hub

> Documento vivo. Cada bug descubierto durante un milestone se documenta aquí antes del commit final del milestone. Permite a milestones posteriores no repetir los mismos errores.

## Estructura de cada entrada

Cada entrada documenta UN bug o lección con la siguiente estructura:

- **Título:** descripción corta del problema.
- **Milestone donde se detectó:** M0, M1, M2, ...
- **Síntoma:** qué se observó.
- **Causa raíz:** qué lo provocó.
- **Workaround / fix:** cómo se resolvió o cómo evitarlo.
- **Lección:** principio general que aplica a milestones futuros.

### Dirección estructurada de contacto: convivencia con el campo plano legacy sin migración

- **Milestone donde se detectó:** Fix de pipeline pre-M10.2, Parte 2 (junio 2026).
- **Contexto:** la dirección del contacto era un texto plano guardado como `{ line1: <texto> }` en `contacts.address` (jsonb). Shopify necesita la dirección en campos separados; con un solo `line1` la dirección llega incompleta. Se pasó a **estructurada** (10 campos que replican el Shopify Address: country, first_name, last_name, company, address1, address2, zip, city, province, phone). Ninguno obligatorio.
- **Por qué NO hubo migración de schema:** `contacts.address` YA era `jsonb` sin shape forzado, así que el cambio es solo de convención de claves — cero DDL. Además el **mapper inbound de Shopify ya guardaba** el `default_address` crudo (address1/address2/city/province/country/zip/phone/company), o sea los contactos venidos de Shopify YA estaban casi estructurados. El único formato "plano" era el de contactos editados/creados desde M6 (`{ line1 }`).
- **Cómo conviven viejo y nuevo (sin correctivo forzado):** un módulo puro compartido `lib/contacts/address.ts` con `parseStoredAddress` que lee AMBAS formas y mapea los alias legacy a las canónicas (`line1→address1`, `line2→address2`, `state→province`, `postal_code→zip`; la forma nueva gana si ambas existen). Al **guardar** (`structuredAddressToJson`) se persiste SOLO la forma canónica → una dirección vieja se "promueve" a estructurada en cuanto se edita. Las que no se editen quedan planas pero se leen bien; el backfill de M10.2 las completa desde Shopify (que ya tiene la estructurada). El módulo NO es `server-only` a propósito: lo consumen tanto Server Actions/worker como los Client Components (form de edición y modal "Crear contacto en Shopify").
- **Mapeo a Shopify directo:** las 10 claves canónicas coinciden 1:1 con el Shopify Address, así que `structuredAddressToShopify` es un passthrough de los campos no vacíos (con fallback de `phone` al teléfono del customer). Se cableó en los 3 caminos salientes: botón "Crear contacto en Shopify" (create), edición de contacto enlazado (worker `shopifyOutboundContactUpdate` — que ANTES omitía la dirección por no tener traducción), y el modal. `formatAddress` (resumen 1-línea) se extendió para incluir `province`.
- **Detalle de cobertura:** el popup de oportunidad (`opportunity-dialog`) arma su prefill desde `OpportunityContactSummary`, que NO trae el `address` jsonb completo → su prefill usa `emptyStructuredAddress()` (igual que antes pasaba `null`); el usuario lo llena en el modal o se completa desde el detalle de contacto. No es bug — es la misma limitación de datos del summary que ya existía.
- **Lección:** cuando una columna jsonb ya existe, "estructurar" un campo plano es un cambio de convención + un parser tolerante a la forma vieja, NO una migración destructiva. La clave es centralizar lectura/escritura/serialización en un módulo puro compartido (cliente+servidor) que mapee los alias legacy y persista solo la forma canónica — así la promoción es incremental (al editar) y nada se rompe mientras tanto.

### Auto-ocultar cerradas: `lost_at` materializado + dos gotchas de TS (select dinámico, Insertable)

- **Milestone donde se detectó:** Fix de pipeline pre-M10.2, Parte 1 — anti-ruido (junio 2026).
- **Contexto / decisión de modelado:** el kanban debe ocultar Ganadas/Perdidas tras N días del cierre (default 7, configurable). Para Ganadas existe `won_at`; para **Perdidas NO había columna** — "Perdida" solo vivía como entrada en `opportunity_stage_history`. Cruzar el historial en cada render del kanban reintroduce el lag de M5-DT-03. Solución (migración 0026): columna **`opportunities.lost_at`** espejo de `won_at`, poblada hacia adelante en `pipeline-move.ts` (simétrica al won_at: se setea al mover a etapa `is_lost`, se limpia al salir) y **backfilleada** desde la última transición a etapa `is_lost` del historial. NULL-handling deliberado: una cerrada con timestamp NULL NO se oculta (no inventamos antigüedad).
- **Por qué el ocultar NO afecta KPIs:** el filtro vive SOLO en `listKanbanOpportunities`/`countKanbanOpportunitiesByStage` (data layer del kanban). El dashboard usa sus propias queries en `lib/db/dashboard.ts` y NO pasa por estas funciones — las cerradas se siguen contando. Verificado: ningún cómputo del dashboard importa las funciones del kanban.
- **Gotcha 1 — `.select(variable)` rompe la inferencia tipada de PostgREST.** Pasé un string dinámico a `.select()` (para traer `won_at, lost_at` solo cuando hace falta bucketear ocultas). postgrest-js infiere el tipo del SELECT a partir del **literal**; con un string variable el tipo de `data` colapsa a `ParserError<...>` y el `as Array<...>` falla con TS2352. Fix: castear el resultado vía `as unknown as Array<...>` (el runtime es correcto; solo se pierde la inferencia, que de todos modos no aplica a un select dinámico). Alternativa válida: usar dos `.select(literal)` ramificados.
- **Gotcha 2 — `Insertable<Row>` exige TODA columna nueva en CADA insert.** `Insertable` (database.ts) solo hace opcionales `id`/`created_at`/`updated_at`; cualquier otra columna del Row es **requerida** en los inserts. Al agregar `lost_at` al `OpportunityRow`, los dos sitios que construyen un insert de opp (`draft-orders.ts` y `r12-auto-creation.ts`) dejaron de compilar hasta agregar `lost_at: null` (junto a su `won_at: null`). Lección: al sumar una columna no-default a un Row, `tsc` lista todos los inserts a actualizar — seguir la lista, no asumir que un default de BD la hace opcional en el tipo.
- **Paso operativo obligatorio (NO es código):** la migración 0026 agrega `lost_at` y la lee el SELECT del conteo. **Debe aplicarse a la BD ANTES/junto con el deploy** — si Vercel deploya sin la migración, el conteo del kanban hace `select ... lost_at` contra una columna inexistente y la página de pipeline rompe entera. Igual patrón que 0024/0025: el operador aplica la migración (SQL Editor o `supabase db push`).
- **Lección:** materializar la fecha de un evento que solo vivía en un log inmutable es el patrón correcto cuando una vista en caliente (kanban) lo necesita por fila — espeja la columna existente (`won_at`), puebla hacia adelante en el servicio que ya hace la transición, y backfillea desde el log. Y el filtro de visualización debe quedar acotado al data layer de esa vista para no tocar otras lecturas (KPIs).

### Cotizaciones con draft borrado en Shopify — el webhook ya las cancelaba; las 7 "fantasma" ya estaban canceladas

- **Milestone donde se detectó:** Fix de pipeline pre-M10.2, Parte 3 (junio 2026). Confirmado contra BD + Shopify de producción Centr.
- **Síntoma reportado:** el operador creía que 7 opps en etapa "Cotización" (#D967, #D968, #D969, #D970, #D971, #D981, #D987) eran cotizaciones fantasma activas cuyo Draft Order da 404 en Shopify, inflando KPIs. Pedido: cancelarlas con metadata (motivo "Borrado de Shopify"), reusando el mecanismo de cancelación, con dry-run.
- **Causa raíz / hallazgo real:** las 7 **ya estaban canceladas** desde el 22–25 may 2026, con `cancellation_source = 'shopify_draft_deleted'`, etapa preservada en "Cotización" y la nota del sistema. Es decir, el worker `draft_orders/delete` (que YA existe en `lib/inngest/functions/draft-orders.ts`, NO era deuda pendiente pese a que el prompt lo planteaba como "a futuro") las absorbió correctamente cuando Shopify emitió el evento de borrado. La premisa "fantasmas activos" estaba desactualizada: al estar canceladas, ya estaban excluidas del kanban (`listOpportunities`/`listKanbanOpportunities` filtran `cancelled_at IS NULL`) y de los KPIs del dashboard (win rate excluye canceladas) desde mayo.
- **Verificación (sweep completo):** se barrieron las **64 opps activas** (no canceladas) de Funnel Venta en etapa "Cotización" haciendo `GET /draft_orders/{id}.json` contra Shopify. Resultado: **64/64 devuelven 200 (existen), 0 dan 404**. No queda ninguna cotización fantasma con draft borrado. El único conjunto borrado eran las 7, ya canceladas.
- **Workaround / fix:** `scripts/maintenance/cancel-deleted-draft-opportunities.ts` — reusa EXACTAMENTE `cancelOpportunity({ source: 'shopify_draft_deleted', note: 'Borrado de Shopify — ...' })` (no SQL crudo). Verifica 404 contra Shopify ANTES de cancelar (`--dry-run` primero); **solo cancela las 404 confirmadas**, jamás las 200. Idempotente (`cancelOpportunity` preserva el primer `cancelled_at` → `already_cancelled`). Audit `opportunity_cancelled_deleted_draft_corrective`. Dos modos: `--refs` (default = las 7) y `--all-cotizacion` (barre toda la etapa). Match defensivo `funnel='venta'` para no tocar la hija de Post-venta que hereda `display_reference` (0021) pero no `shopify_draft_order_id`. El script quedó como herramienta operativa idempotente — su corrida live es no-op hoy (nada que cancelar).
- **Lección:** antes de un correctivo sobre "datos rotos en producción", verificar el estado REAL contra el sistema externo en vez de confiar en la premisa del reporte — la mitad del trabajo puede estar ya hecho por un worker en vivo. Y cuando el prompt plantea un mecanismo automático "a futuro", confirmar primero si ya existe implementado (este webhook estaba completo desde M3, no era deuda). El barrido completo (no solo el set listado) es lo que da la certeza de "no quedan más fantasmas".

### Tooltips de KPI clipeados por `overflow-hidden` de la tarjeta + tooltip sin dependencias

- **Milestone donde se detectó:** M8.2 rediseño visual del Dashboard (junio 2026).
- **Síntoma esperado si se implementa mal:** al agregar tooltips explicativos por KPI (hover/focus → popover), el popover queda CORTADO por la tarjeta. La `KpiCard` previa usaba `overflow-hidden` (para redondear la barra de acento lateral); cualquier popover hijo posicionado `absolute` fuera del box se recorta y se ve truncado.
- **Causa raíz:** `overflow-hidden` en el contenedor de la tarjeta recorta TODO hijo que desborde, incluido un tooltip que debe salir por debajo/encima del borde.
- **Workaround / fix:** el rediseño reemplazó la barra de acento lateral por fondo tintado + chip de ícono, así que `overflow-hidden` dejó de ser necesario y se quitó de `KpiCard`. El radio redondeado del fondo se logra con `rounded-xl` sin clipear hijos (el background-color respeta el border-radius sin `overflow-hidden`; solo los hijos lo desbordan). El tooltip (`info-tooltip.tsx`) se posiciona `absolute z-50` y puede salir de la tarjeta libremente.
- **Decisión de implementación — tooltip propio, sin dependencias:** CLAUDE.md prohíbe instalar deps sin aprobación y el stack no tiene Radix. El tooltip es un componente local mínimo: `<button>` enfocable (trigger) + popover en estado local, mostrado en `onMouseEnter/onFocus` y ocultado en `onMouseLeave/onBlur` (+ `onClick` toggle para touch), con `role="tooltip"` + `aria-describedby`. Texto 100% ESTÁTICO — no pega a BD ni recalcula (requisito del prompt: el hover no debe tener costo de datos).
- **Lección:** antes de meter popovers/tooltips/menus dentro de una tarjeta, revisar si el contenedor tiene `overflow-hidden` (común cuando se usa para clipear barras de acento o esquinas). Si lo tiene, el popover se corta — o se quita el `overflow-hidden` (preferible si el redondeo se puede lograr de otra forma) o se portaliza el popover. Y para tooltips simples y estáticos, un componente local accesible es suficiente; no hace falta una dependencia de UI.

### KPIs de opportunities y opportunity_stage_history fechados por la fecha de importación en vez de la fecha real de Shopify

- **Milestone donde se detectó:** Fix crítico pre-M10.2 (junio 2026), continuación del fix de `orders` (0024). Confirmado contra BD de producción Centr.
- **Síntoma:** el dashboard ubicaba en el tiempo varios KPIs de Funnel Venta por la fecha en que el registro entró a la BD, no por la fecha real del hecho en Shopify. Concreto: **Cotizaciones enviadas** y filtro Pipeline/Activas por `opportunities.created_at`; **Ganadas / Win-Loss / fin de Sales cycle** por `opportunities.won_at`; **Leads / Calificados / Perdidas / Win-rate-por-etapa** por `opportunity_stage_history.changed_at`. Una carga del 4-8 jun metió ~11 opps que en realidad son borradores viejos de Shopify (#D bajos, feb-abr) con `created_at` de junio; varias nacieron "ganadas al instante" (`won_at` a segundos del `created_at`). Con filtro junio, Cotizaciones marcaba ~34 (real ~24) y Ganadas contaba cierres viejos como de junio. Mismo modelado defectuoso que `orders` (0024), pero en las dos entidades restantes que el dashboard reporta por periodo.
- **Causa raíz:** ninguna de las tres fechas usadas es la del hecho en Shopify. `opportunities.created_at`/`opportunity_stage_history.changed_at` son `default now()` (hora del INSERT). El mapper de draft orders **ya extraía** `normalized.createdAt` (= `created_at` del Draft Order en Shopify) pero el worker nunca lo persistía — idéntico al bug de orders. `won_at` se setea `now()` en el RPC `trigger_f1_to_f2` (0020) y en `pipeline-move`. Al importar registros históricos, `now()` = fecha de importación.
- **Principio validado (no asumido):** un registro PROVENIENTE de Shopify se ubica por su fecha real de Shopify; un registro NACIDO en plataforma conserva su fecha propia. A diferencia de `orders` (todas de Shopify → se excluye NULL), `opportunities` MEZCLA filas de Shopify (opps con `shopify_draft_order_id` = Cotizaciones) y nacidas en plataforma (lead R12 sin draft, win/avance manual). Por eso la fecha efectiva es **`COALESCE(fecha_shopify, fecha_plataforma)`**.
- **Criterio para el historial de etapas (distinción genuino vs importación por `context`):** las entradas de origen Shopify se re-fechan a su evento real; las de origen humano/plataforma conservan `changed_at` (que ES su verdad). `context='webhook'` (entrada a Cotización) → `created_at` del Draft Order; `context='trigger_f1_f2'` (Ganada por completación) → fecha real del pedido; `context='manual'`/`'automation'` (Lead nuevo R12, arrastre manual, Perdida) → no se tocan. Consecuencia: Leads (entradas a "Lead nuevo", que son R12/manuales) y Perdidas (arrastre manual) resultan **ya correctos**; solo se re-fechan Cotización y Ganada, que alimentan el cohort de Cotización y Win-rate-por-etapa.
- **Constraint encontrado:** `opportunity_stage_history` es **inmutable** (`tg_block_mutation` bloquea UPDATE y DELETE, 0004:171). El correctivo no podía re-escribir `changed_at`. Solución (mirror del fix de orders): agregar columna **nueva** y dejar la vieja intacta, no re-escribirla.
- **Workaround / fix (migración 0025):**
  1. **Columnas nuevas + generadas.** `opportunities.shopify_created_at` (nullable; el sync la pobla desde el draft) + `effective_created_at GENERATED ALWAYS AS (coalesce(shopify_created_at, created_at)) STORED` (+ índice). `opportunity_stage_history.shopify_event_at` (nullable; solo contextos Shopify) + `effective_event_at GENERATED AS (coalesce(shopify_event_at, changed_at)) STORED` (+ índice). Las generadas son filtrables/indexables — PostgREST no expresa COALESCE en un `.gte()`, una columna generada sí.
  2. **Relajación quirúrgica de la inmutabilidad.** Se reemplaza `tg_block_mutation` sobre stage_history por `tg_stage_history_shopify_event_guard`: permite UPDATE **solo si el único campo que cambia es `shopify_event_at`** (compara el resto vía `is distinct from` sobre row tuple), DELETE sigue bloqueado. `changed_at` (audit trail) queda 100% inmutable.
  3. **`won_at` corregido in situ** (es semánticamente "la fecha de ganada", no un eje paralelo). El RPC `trigger_f1_to_f2` resuelve la fecha del pedido vinculado (`orders.shopify_created_at`) y la usa para `won_at` y el `shopify_event_at` de la Ganada; cae a `now()` si el pedido aún no aterrizó (carrera en vivo, donde `now()` ≈ tiempo real). **Decisión del operador:** la fecha de ganada = `orders.shopify_created_at` (momento de conversión draft→orden), no `paid_at`.
  4. **Sync de ahora en adelante.** Worker draft-orders persiste `opportunities.shopify_created_at = normalized.createdAt` y pasa esa fecha como `shopifyEventAt` de la entrada "Cotización". R12 pasa `shopify_created_at: null` (lead nacido en plataforma).
  5. **Dashboard cuenta por la fecha real.** `listDraftOppsCreatedInPeriod` y `listLivePipelineOpps` filtran `effective_created_at`; `listStageEntriesInPeriod`/`listLostEntriesInPeriod` filtran `effective_event_at`; Sales cycle usa `effective_created_at`; `listWonOppsInPeriod` sigue por `won_at` (re-fechado in situ).
  6. **Correctivo `scripts/maintenance/backfill-opportunity-shopify-dates.ts`** — `--dry-run` primero, idempotente, audit log. Parte A: GET `/draft_orders/{id}.json` (reusa el mapper, no inventa parseo) → puebla `shopify_created_at` + `shopify_event_at` de la Cotización. Parte B: re-fecha `won_at` + `shopify_event_at` de la Ganada desde `orders.shopify_created_at` LOCAL (no llama a Shopify). **Prerrequisito: correr antes el correctivo de orders 0024** (Parte B lee de ahí).
- **Diferencia de NULL-handling vs orders:** orders EXCLUYE NULL (una fecha desconocida no se inventa, y todas son de Shopify). Opps usa COALESCE a `created_at` porque los leads nacidos en plataforma legítimamente solo tienen `created_at` — no se pueden excluir. Consecuencia: entre el deploy y el correctivo, las opps importadas siguen mostrándose en su mes de importación (no desaparecen como las orders); tras el correctivo migran a su mes real.
- **Lo verificado que NO se rompió:** Revenue por `paid_at` ($601,570), Pedidos en periodo (22) por `orders.shopify_created_at`, atribución de asesor — sin cambios. La separación `funnel='venta'` de las queries del dashboard sigue aislando los KPIs de Venta de la hija de Post-venta.
- **Lección:** el patrón de 0024 (columna `shopify_*` nueva + sync que la pobla + dashboard que cuenta por ella + correctivo que reusa el mapper, con dry-run) se generaliza a toda entidad de Shopify reportada por periodo. Dos refinamientos: (a) cuando la tabla MEZCLA registros de Shopify y nacidos en plataforma, la fecha efectiva es COALESCE materializada como columna generada (filtrable/indexable), no exclusión de NULL; (b) para una tabla inmutable, NO re-escribir la fecha vieja — agregar una columna nueva y relajar la guarda de inmutabilidad SOLO para esa columna (DELETE y el audit trail original quedan intactos). Y la distinción "evento genuino vs generado por importación" en el historial se resuelve por `context`, no por heurística temporal.

### Orders fechadas por `created_at` de BD en vez de la fecha real de creación en Shopify

- **Milestone donde se detectó:** Fix crítico pre-M10.2 (junio 2026). Confirmado contra BD de producción Centr.
- **Síntoma:** el dashboard contaba "Pedidos en el periodo" y "Pedidos por mes" (Post-venta) usando `orders.created_at`, que es **cuándo el registro entró a la BD local**, no cuándo se creó el pedido en Shopify. Con filtro 1-9 junio mostró **102 pedidos**; el conteo real en Shopify Admin es ~22. Diagnóstico: 69 de esos 102 entraron a la BD el 4-jun (carga/sync masivo de origen no identificado) pero su `paid_at` real va de **nov-2025 a abr-2026** — pedidos viejos contados como junio. Son órdenes huérfanas (sin `opportunity_id`, válidas por O6), solo mal fechadas. Las `opportunities` NO tienen este bug (su `created_at` es confiable: ganadas por `created_at` ≈ ganadas por `won_at`). El bug estaba **acotado a orders**.
- **Causa raíz:** la tabla `orders` nunca guardó la fecha de creación del objeto Order de Shopify. Tenía `created_at`/`updated_at` (BD), `last_modified_at`, `paid_at`, `cancelled_at` — ninguna es la creación en Shopify. El mapper (`mapOrderWebhookToNormalized`) **sí extraía** `normalized.createdAt` (= `created_at` de Shopify) pero el worker nunca lo persistía. El dashboard, a falta de mejor campo, filtraba/agrupaba por `created_at` de BD.
- **Workaround / fix (migración 0024):**
  1. **Columna nueva `orders.shopify_created_at timestamptz` (nullable)** — la fecha real de creación del pedido en Shopify. Nombre con prefijo `shopify_*` (como `shopify_order_id`, `shopify_name`) para desambiguar del `created_at` de BD. Índice parcial `(organization_id, shopify_created_at) where not null` para el filtro del dashboard.
  2. **Sync poblando de ahora en adelante** — el worker de orders (`lib/inngest/functions/orders.ts`, ambos paths create/update) y el backfill incremental (`scripts/shopify/backfill-incremental.ts`) escriben `shopify_created_at = normalized.createdAt`. En update se usa `coalesce` defensivo (`?? existing.shopify_created_at`) — la fecha es inmutable en Shopify, nunca se borra.
  3. **Dashboard cuenta por la fecha de Shopify** — `listOrdersCreatedInPeriod` (`lib/db/dashboard.ts`) filtra `gte/lte shopify_created_at` (antes `created_at`) y `computePostventaMetrics` (`lib/services/dashboard-metrics.ts`) bucketea "Pedidos por mes" por `shopify_created_at`. Definición de negocio (decisión del operador): "Pedidos en el periodo" = creados en el periodo por fecha de Shopify, **pagados + pendientes por igual** (sin filtro de `financial_status`). **Revenue NO se tocó** (sigue por `paid_at`, R5) ni los KPIs de Venta (fechas de opportunities, confiables).
  4. **Correctivo `scripts/maintenance/backfill-order-shopify-created-at.ts`** — para cada orden con `shopify_created_at IS NULL` hace `GET /orders/{id}.json` (reusa el mismo mapper del sync, no inventa parseo de fecha) y escribe SOLO esa columna. `--dry-run` primero (hace los GET read-only para reportar a qué fecha refecharía + verificación de existencia, sin escribir). Idempotente (solo toca filas NULL → re-correr no reprocesa). Audit `order_shopify_created_at_backfilled`. Tope defensivo `--expected-max` y throttle `--delay-ms` (rate limit REST de Shopify).
  5. **Verificación de las 69 huérfanas contra Shopify** — el correctivo reporta cuántas órdenes existen (GET 200) y cuántas NO (GET 404) **antes** de cualquier escritura, con desglose del subconjunto huérfano (`opportunity_id IS NULL`). Una orden 404 **NO se borra** — se reporta para que el operador decida (las huérfanas son válidas por O6; un 404 podría ser basura de la prueba rota de origen desconocido, pero no se asume).
- **Prerequisito del backfill M10.2/M11:** el backfill traerá miles de órdenes históricas que entrarían con `created_at` de "hoy"; sin `shopify_created_at` el dashboard las mostraría todas como de hoy. La columna + el sync quedan listos para que el backfill las popule correctamente desde el inicio.
- **Manejo de NULL en el dashboard:** el filtro `gte/lte shopify_created_at` excluye filas con NULL (comparación con NULL = unknown en Postgres). Decisión consciente: una fecha desconocida NO se inventa (no se hace `coalesce` a `created_at`, que es justamente el dato malo). Entre el deploy del fix y la corrida del correctivo, "Pedidos en el periodo" cae para órdenes viejas — esperado; el operador corre el correctivo justo después. El sync popula las nuevas desde ya.
- **Lección:** distinguir SIEMPRE "fecha del evento en el sistema externo" de "fecha de entrada a la BD local". Un `created_at` de BD es la hora del INSERT, no del hecho de negocio — usarlo como eje temporal de un KPI produce conteos que se ven como bug de cálculo pero son de modelado. El mapper ya traía el dato correcto (`normalized.createdAt`); bastaba persistirlo. Y para correctivos sobre datos reales que dependen de un sistema externo: verificar existencia (GET 404) y reportar ANTES de actuar, nunca borrar por inferencia — un registro "huérfano" puede ser válido (O6).

### Filtro de fecha personalizado del Dashboard no se aplicaba + Pipeline $/Activas eran snapshot fijo

- **Milestone donde se detectó:** M8.2 Bloque 2 (rediseño del Dashboard, junio 2026).
- **Síntoma:** (a) al elegir un rango personalizado (desde/hasta) los KPIs no cambiaban; (b) "Pipeline $ (bruto)" y "Oportunidades activas (con cotización)" mostraban el mismo número sin importar el periodo seleccionado.
- **Causa raíz:** (a) el rango custom se auto-aplicaba en `onChange` de cada `<input type="date">`; mientras una de las dos fechas estuviera vacía, `fetchWith` retornaba temprano (`if (!customFrom || !customTo) return`). El usuario percibía "no pasa nada" porque el disparo dependía de un estado parcial frágil y sin feedback. (b) `listLivePipelineOpps()` era un snapshot sin parámetros de periodo — leía TODAS las opps vivas de la org siempre, ignorando el filtro de fecha.
- **Workaround / fix (M8.2):**
  1. **Botón "Aplicar" explícito** para el rango custom. El toolbar mantiene un draft local de las fechas (`draftFrom`/`draftTo`) y solo dispara el recálculo al hacer click en "Aplicar" (deshabilitado hasta que ambas estén llenas). Click en "Personalizado" solo muestra los inputs, NO recalcula. Elimina el disparo por estado parcial.
  2. **`listLivePipelineOpps(startUtc, endUtc)`** ahora acota por `created_at` al periodo. Definición operativa: **"activa en el periodo = creada en el periodo"** — la más simple y consistente con los demás KPIs, evita reconstrucción de estado histórico (cara y no pedida). Aplica también a "Activas con cotización" (deriva del mismo dataset).
- **Verificación adicional (#7):** Pipeline $ NO suma ganadas ni perdidas. La query ya filtra `won_at IS NULL` (excluye ganadas) y el loop del servicio salta `stage.is_won || stage.is_lost` (excluye perdidas, que llegan con `won_at` NULL pero en etapa perdida). Confirmado por el test `pipeline $ bruto coalesce ... excluye ganadas/perdidas` (fixture incluye una opp en Ganada con monto 999 y otra en Perdida con 500; el total esperado las ignora).
- **Lección:** para filtros con múltiples campos interdependientes (rango desde/hasta), un botón "Aplicar" explícito es más robusto que auto-aplicar en cada `onChange` — el auto-aplicar sobre estado parcial produce "no hace nada" silencioso. Y todo KPI que el usuario espera ver "acotado al periodo" debe recibir el periodo en su query; un snapshot global sin parámetros se ve idéntico a un bug de cálculo.

### Opp de Venta sin asesor pese a que su pedido tiene asesor (tag de vendedor tardía)

- **Milestone donde se detectó:** Fix post-M7.2 (junio 2026). Confirmado en BD de producción Centr.
- **Síntoma:** una oportunidad del Funnel Venta quedaba con `assigned_advisor_id` NULL aunque su **pedido** (`order`) sí tenía asesor atribuido por tag de vendedor. El admin no veía el trabajo de ese asesor en el pipeline de Venta (filtra por asesor de la opp), pero el pedido sí contaba para el vendedor (mira el asesor de la orden). Caso real: 3 opps de Venta en "Ganada" con asesor NULL cuyo pedido tiene tag "Pepe" (`c092874e-...`, `cb1c6a05-...`, `251bc26c-...`) — las F1 madre de las 3 hijas de Post-venta corregidas por 0022.
- **Causa raíz:** misma ventana de carrera que 0022 pero un nivel arriba. La opp de Venta se crea/avanza por la tag del **Draft Order**, mientras que la tag de vendedor aterriza en el **pedido** vía un webhook `orders/*` independiente y sin orden garantizado. Si el pedido llega con su tag después de que la opp ya avanzó, la opp queda sin asesor y nada la re-corregía.
- **Workaround / fix (migración 0023):**
  1. **Hook en `orders/*` extendido.** El mismo bloque que 0022 usa para la hija de Post-venta ahora también realinea la **F1 de Venta** (`reattributeVentaOpportunityForOrder` → RPC `reattribute_venta_opportunity_advisor`). Cuando un pedido con asesor se vincula a una opp de Venta SIN asesor, le rellena el asesor del pedido. Las dos RPC del bloque tocan filas distintas y funnels distintos (`venta` la F1, `post_venta` la hija), así que **no colisionan ni duplican trabajo** en el mismo evento de orden.
  2. **Correctivo de opps existentes.** RPC `reattribute_venta_opportunity_advisor(p_opportunity_id, p_dry_run, p_source)`, doble uso (hook + correctivo), misma semántica. Orquestado por `scripts/maintenance/reattribute-venta-opportunity-advisor.ts` (`npm run maintenance:reattribute-venta-opportunity-advisor -- --org-slug centr [--dry-run]`), con tope defensivo `--expected-max`. Dry-run primero (lista qué opps rellenaría y a quién), luego live.
- **Diferencia clave con 0022 — la regla es "rellenar NULL", NUNCA pisar:** 0022 SÍ sobrescribe el asesor de la hija de Post-venta con el de la orden (decisión: quien cierra atiende post-venta). Aquí, en cambio, la opp de Venta hereda el asesor del pedido **solo si está SIN asesor**; si ya tiene asesor (por tag de draft — atribución primaria R2 — o manual), NO se toca. Por eso esta RPC **no necesita** la guarda anti-reasignación-manual de 0022: cualquier valor no-NULL queda intacto por definición, así que la atribución manual nunca se pisa. Ese guardrail también hace idempotente la RPC (tras rellenar, el segundo run cae en `opportunity_already_assigned`).
- **Atomicidad / idempotencia / R2:** UPDATE + audit `venta_opportunity_advisor_reattributed` en la misma invocación sin EXCEPTION (todo-o-nada); solo toca el asesor de la OPP de Venta, nunca la orden ni el contacto. Resolución del pedido: canónica por `orders.opportunity_id = opp.id` (pedido con asesor), fallback por `shopify_order_id` que la opp espeja. Sin pedido con asesor → `noop`.
- **Lección:** el patrón de 0022 (trigger + hook idempotente del lado de la fuente + correctivo, compartiendo un único RPC) se reusa para cerrar la misma clase de ventana de carrera un nivel arriba. Y cuando la decisión de negocio es "rellenar huecos sin borrar trabajo ajeno", el guardrail "solo NULL" es más simple y más seguro que una guarda anti-manual: subsume la protección manual y la idempotencia en una sola condición.

### Hija de Post-venta hereda el asesor de la F1 (NULL) en vez del de la orden cerrada

- **Milestone donde se detectó:** Fix post-M7.2 (junio 2026). Confirmado en BD de producción Centr.
- **Síntoma:** un pedido cerrado con tag de vendedor dejaba el `order` atribuido a ese vendedor (vía parser de tags), pero la **oportunidad hija de Post-venta** quedaba con `assigned_advisor_id` NULL. Inconsistencia visible: el dashboard contaba el pedido para el vendedor (mira el asesor de la orden) pero el pipeline de Post-venta filtrado por ese vendedor no mostraba nada (mira el asesor de la opp). Caso real: order `7070657282324`, tag "Pepe", asesor de orden = Pepe, hija de Post-venta con asesor NULL.
- **Causa raíz:** el trigger `trigger_f1_to_f2` (0020/0021) copiaba `assigned_advisor_id` de la **F1 madre** a la hija. La F1 muchas veces está sin asignar (NULL) porque la atribución por tag aterriza en la **orden**, no en la F1. Además hay una **carrera de webhooks**: el trigger F1→F2 nace de la completación del Draft Order (`draft_orders/*`), mientras que el asesor de la orden lo setea un webhook `orders/*` independiente, sin orden garantizado. Si la orden aterriza después del trigger, la hija nace con el fallback de la F1 y nada la re-corregía luego.
- **Workaround / fix (migración 0022):**
  1. **Trigger ajustado.** Al crear la hija, el asesor se resuelve con `coalesce(asesor_de_la_orden, asesor_de_la_F1)`. La orden se resuelve por `shopify_order_id` (el mismo valor que la hija espeja; unique por org → ≤1 fila). Si la orden todavía no aterrizó (carrera), el asesor de orden es NULL → cae al fallback F1. Atomicidad/idempotencia/R2 intactas (es un SELECT extra dentro del mismo RPC sin EXCEPTION; el guard `child_already_exists` sigue garantizando una sola hija; el trigger toca la hija UNA vez).
  2. **Hook en `orders/*` que cierra la ventana de carrera de forma permanente.** Cuando una orden con asesor se vincula a una F1 que ya tiene hija de Post-venta, el worker re-atribuye el asesor de la hija (`reattributePostventaChildForOrder` → RPC `reattribute_postventa_child_advisor`). Idempotente: no-op si ya está alineado o si la F1 aún no tiene hija. Así, complete-draft-antes-de-orden queda cubierto: el trigger nace con fallback F1 y el `orders/paid` (o cualquier `orders/*`) posterior lo realinea.
  3. **Correctivo de hijas existentes.** RPC `reattribute_postventa_child_advisor(p_child_id, p_dry_run, p_source)` (misma migración) realinea hijas ya existentes reusando exactamente la semántica del trigger. Orquestado por `scripts/maintenance/reattribute-postventa-child-advisor.ts` (`npm run maintenance:reattribute-postventa-child-advisor -- --org-slug centr [--dry-run]`), con tope defensivo `--expected-max`. Dry-run primero (lista qué hijas reasignaría y de quién a quién, resolviendo nombres de vendedor), luego live.
- **Cómo se distingue "heredó NULL/F1" de "reasignación manual a propósito":** el correctivo solo cambia el asesor de la hija si la **orden tiene asesor y difiere** del actual de la hija; si la orden no tiene asesor → noop (el fallback a la F1 ya es el estado correcto). Para no pisar reasignaciones manuales, el RPC consulta `audit_log` por un evento de reasignación manual de asesor (actor humano: `event_type in ('opportunity_advisor_reassigned','opportunity_reassigned') and actor_user_id is not null`) sobre esa hija; si existe, se salta (`manual_reassignment_detected`). **Hoy NO existe feature de reasignación manual de oportunidad en la app** (el único reassignment es de contactos, en `contacts.ts`), así que esa guarda nunca matchea — toda hija con asesor no-NULL lo tiene por herencia del trigger, no por acción humana, de modo que realinearla con el asesor de la orden es correcto por la decisión de negocio. La guarda queda como defensa para cuando V2 introduzca reasignación manual de opps. **Conclusión: la distinción es fiable en el estado actual del código** (no se necesitó reportar ambigüedad al operador).
- **R2 / independencia:** el cambio NO propaga hacia atrás — el RPC y el trigger solo tocan el asesor de la HIJA, nunca la F1 ni el contacto. La re-atribución posterior la dispara la ORDEN (no una reasignación de la F1), y solo cuando la orden tiene asesor.
- **No infla KPIs del dashboard:** las queries de revenue/pipeline del dashboard filtran `funnel = 'venta'`, así que el asesor de la hija de Post-venta no entra en win rate ni revenue del Funnel Venta. Esto solo corrige a quién se le muestra el seguimiento de Post-venta.
- **Lección:** cuando una entidad derivada nace de un trigger pero su fuente de atribución real (la orden cerrada) llega por un webhook **distinto y sin orden garantizado**, heredar al nacimiento no basta — hay que cerrar la ventana de carrera con un hook idempotente del lado de la fuente que re-aplique la atribución cuando ésta aterriza. El trigger cubre el camino feliz (orden ya presente); el hook cubre el desfase; el correctivo cubre el histórico. Las tres piezas comparten un único RPC para garantizar semántica idéntica. Y antes de un correctivo que pisa valores, verificar si existe un camino de edición manual: si no lo hay, todo valor no-NULL proviene de herencia automática y es seguro realinearlo; documentarlo en vez de asumir.

### Trigger F1→F2 crea la hija de Post-venta sin datos comerciales

- **Milestone donde se detectó:** Fix crítico post-M7.2 (junio 2026). Confirmado en BD de producción Centr.
- **Síntoma:** al disparar el trigger F1→F2 (draft completado → F1 a Ganada → nace hija en "Cotización completada"), la hija nacía como cascarón: `shopify_order_id`, `actual_amount` y `estimated_amount` en NULL, sin `display_reference` (#D...) ni line items. En el pipeline, la F1 ganada mostraba monto ($773,749) y referencia (#D493) pero su hija solo mostraba el teléfono. Contacto, asesor y parent SÍ se heredaban bien.
- **Causa raíz:** el INSERT de la hija en `trigger_f1_to_f2` (migración 0020) solo copiaba `contact_id`, `assigned_advisor_id`, `parent_opportunity_id` y `currency`. Nunca copió los campos comerciales ni los line items de la F1.

Idempotencia intacta (guard `child_already_exists` → los line items se copian una sola vez, en el nacimiento). Contacto/asesor/parent/currency sin cambios.
  2. **`shopify_draft_order_id` NO se hereda — decisión de diseño forzada por dos invariantes.** (a) La columna tiene `unique (organization_id, shopify_draft_order_id)` (0004): copiarla a la hija violaría la unicidad y ABORTARÍA el RPC atómico → la hija nunca nacería. (b) `findOpportunityByDraftOrderId` usa `.maybeSingle()` sin filtrar funnel: dos filas con el mismo draft id lo harían fallar y romperían la idempotencia de todos los webhooks `draft_orders/*` posteriores. Idempotente: scalars vía `coalesce` (solo rellena NULLs), line items copiados SOLO si la hija no tiene ninguno (cero duplicados en re-run). - **Lección:** cuando un trigger crea una entidad derivada que debe ser "completa", enumerar explícitamente TODOS los campos de negocio a heredar — heredar identidad (contacto/asesor/parent) no basta. Y antes de copiar un campo "porque el negocio lo pide", verificar constraints de unicidad y los lookups que asumen cardinalidad: un campo con `unique` + `.maybeSingle()` no se puede duplicar entre filas sin romper atomicidad e idempotencia. La referencia visible desacoplada (`display_reference`) del identificador crudo (`shopify_draft_order_id`) permite mostrar lo que el usuario necesita sin arrastrar el identificador conflictivo.

### Target TS < es6: iterar Map/Set y unicode regex `\p{}` fallan en compilación

- **Milestone donde se detectó:** M8.2.
- **Síntoma:** `tsc` con errores `TS2802: Type 'Set<...>' can only be iterated ... '--downlevelIteration' or '--target' of 'es2015'` al hacer `for (const x of set)` / `[...map.entries()]`, y `TS1501: This regular expression flag is only available when targeting 'es6' or later` por usar `/[^\p{L}\p{N}]+/gu`.

### recharts v3: el `formatter` del Tooltip recibe `ValueType` (puede ser undefined), no `number`

- **Milestone donde se detectó:** M8.2.
- **Síntoma:** `tsc` error `TS2322` en cada `<Tooltip formatter={(v: number) => ...}>`: "Type '(v: number) => ...' is not assignable to type 'Formatter<ValueType, NameType>' ... Type 'undefined' is not assignable to type 'number'".
- **Causa raíz:** en recharts 3 el tipo del `formatter` declara el primer parámetro como `ValueType` (`number | string | (number|string)[] | undefined`). Anotarlo como `number` es más estrecho que la firma esperada y TS lo rechaza.
- **Workaround / fix:** no anotar el parámetro (dejar que TS lo infiera desde la firma esperada) y coercir con `Number(v)` dentro del formatter. Para el tercer arg (payload entry) castear puntualmente: `(item as { payload?: { amount?: number } })?.payload?.amount`.
- **Lección:** con recharts 3 + TS strict, los callbacks (`formatter`, `tickFormatter`, `labelFormatter`) tipan los valores como `ValueType`/`NameType` (uniones que incluyen undefined). Coercir con `Number()`/`String()` en el cuerpo en vez de anotar parámetros estrechos.

Si un parser viejo hubiera stripeado acentos, `original_tag` conservaría el casing original `"GinaJiménez"` — pero acá es `"ginajimenez"` ya sin acento, prueba de que el STRING FUENTE en Shopify estaba sin acento.

La action **re-verifica en servidor** el conteo (orders + contactos) antes de borrar — no confía en el conteo del cliente. Audit `tag_mapping_deleted`. **Sin purga automática** — la decisión es manual del admin (no se quiere borrar mappings que el operador podría querer conservar).

- **Lección:** `tag_mappings` es append-only por `upsert(onConflict normalized_tag)` y NO refleja si la tag sigue viva en alguna entidad. Una tag puede quedar huérfana por: corrección de ortografía/acento en Shopify, borrado/anonimización de la entidad que la portaba, o tag de prueba. La pantalla de Mapeo (M7.2 B5) muestra el conteo de entidades por tag — **una tag con conteo 0 es señal de huérfano** y ahora es eliminable manualmente desde la UI (fix #5). Si en V2 el fenómeno se vuelve frecuente, evaluar un GC opcional (con confirmación) de mappings con 0 entidades tras N días — pero el default sigue siendo decisión manual.

### Trigger F1→F2: atomicidad por RPC e idempotencia por hija-existente, no por flag de webhook

- **Milestone donde se detectó:** M7.2 (decisiones de diseño documentadas en construcción).
- **Síntoma esperado si se implementa mal:** los anti-patrones que M7.2 tiende a producir — (a) transacción sin rollback real (la F1 queda Ganada sin hija si el proceso muere entre el UPDATE y el INSERT de la hija); (b) idempotencia mal hecha (cada webhook de completación duplicado crea otra hija en Post-venta); (c) propagación accidental a la hija (reasignar la F1 después del trigger cambia también el asesor de la F2).
- **Causa raíz / decisión:** la completación de un Draft Order llega como `draft_orders/update` (puede repetirse) y la transición toca 4 tablas. Implementar la transición en TypeScript con varios `await` deja una ventana de inconsistencia entre pasos; un compensating-revert no la cierra del todo (si el proceso muere, no corre el revert).
- **Workaround / fix (patrón correcto):**
  1. **Atomicidad por RPC Postgres.** Toda la transición vive en `public.trigger_f1_to_f2` (migración 0020), una función PL/pgSQL SIN bloque EXCEPTION. Corre dentro de la transacción del statement que la invoca → si cualquier paso falla, Postgres revierte TODO. No existe estado intermedio posible. Es atomicidad real del motor, no emulada en app.
  2. **Idempotencia por hija-existente, NO por flag.** Antes de crear, el RPC hace `SELECT ... FROM opportunities WHERE parent_opportunity_id = F1.id AND funnel='post_venta'`. Si existe → `skipped/child_already_exists`. Un `FOR UPDATE` sobre la F1 serializa completaciones concurrentes del mismo draft. Esto cubre tanto el webhook duplicado como el caso "F1 ya estaba Ganada manualmente" (no se duplica la hija; si no había hija, se crea una sola vez).
  3. **R2 sin propagación a la hija.** El RPC copia `assigned_advisor_id` de la F1 a la hija UNA vez, en el momento del trigger, y nunca vuelve a tocar la hija. Una reasignación posterior del admin sobre la F1 (`updateOpportunity`) modifica solo la F1 — la hija conserva el asesor heredado. El edge case crítico del CHECKPOINT valida exactamente esto.
- **Lección:** para transiciones multi-tabla disparadas por webhooks repetibles, la combinación correcta es **RPC transaccional + idempotencia por estado observable (existencia de la entidad derivada) + lock pesimista sobre el agregado padre**. No confiar en "el webhook llega una vez" ni en flags mutables como `won_at` para la idempotencia (un movimiento manual a Ganada setea `won_at` sin crear hija — usar `won_at` como guardia saltaría la creación legítima de la hija). El discriminador del toast (webhook vs manual) usa `shopify_order_id` poblado: solo el trigger lo escribe, así que su presencia en una transición no-ganada→ganada identifica de forma fiable el origen webhook.

### Reconciliación de seeds con FK `on delete restrict`: renombrar in situ, no borrar+crear

- **Milestone donde se detectó:** M7.2 (Bloque 3, reconciliación seed Post-venta 6→7).
- **Síntoma esperado si se implementa mal:** la migración aborta con violación de FK al intentar `DELETE` de una `pipeline_stage` ("Preparación / Envío") que tiene oportunidades apuntándola (`opportunities.stage_id ... on delete restrict`), o peor, deja oportunidades huérfanas si se fuerza.
- **Causa raíz:** el prompt describía el cambio como "eliminar Preparación/Envío + agregar dos nuevas". Un `DELETE` literal choca con el FK restrictivo en cuanto exista una sola opp en esa etapa (entornos de prueba o producción).
- **Workaround / fix:** la migración 0019 **renombra** "Preparación / Envío" → "Envío en curso" (preserva el `id` de la etapa y por lo tanto todas sus oportunidades), quita `is_initial` de "Pago confirmado", inserta la nueva inicial "Cotización completada" y renormaliza posiciones. El estado final son las 7 etapas objetivo con cero pérdida de datos. Orden crítico: quitar `is_initial` de la inicial vieja ANTES de insertar la nueva, para no violar el índice único parcial `pipeline_stages_one_initial_per_funnel_idx`. Idempotente: si "Cotización completada" ya existe, salta.
- **Lección:** cuando una reconciliación de catálogo "elimina X y agrega Y" pero X y Y son semánticamente equivalentes (aquí ambas son la etapa logística intermedia) y X está protegida por FK, **renombrar es la migración correcta** — logra el mismo estado final sin tocar las filas dependientes. Reservar borrar+crear solo cuando no hay equivalencia semántica, y en ese caso migrar las dependencias a una etapa válida ANTES del DELETE. Con índices únicos parciales (`WHERE is_initial = true`), siempre liberar el valor único antes de insertar el nuevo titular.

### Lead nuevo duplicado con Cotización activa por race de webhooks (R12 eco de Shopify→Whaapy)

- **Milestone donde se detectó:** M6 producción (junio 2026), 8 contactos afectados en la org Centr.
- **Síntoma:** contactos con `shopify_customer_id` Y `whaapy_contact_id` aparecían en el pipeline con DOS oportunidades activas en Funnel Venta: una en etapa "Lead nuevo" (auto-creada por R12) y otra en etapa "Cotización" (proveniente de Shopify Draft Order). La coexistencia no es un estado válido — el Lead nuevo solo tiene sentido mientras no exista una oportunidad más concreta. En los 8 casos confirmados, el Lead nuevo R12 fue creado ANTES que la Cotización (entre 28 segundos y 20 horas antes — query de auditoría: `opp_minus_r12` positivo).
- **Causa raíz:** doble bug, ambas variantes del mismo concepto (race de webhooks Inngest paralelos sin invariante a nivel de contacto):
  1. **Anti-eco faltante en `contact.created`.** Cuando un customer nace en Shopify, M3 propaga a Whaapy vía POST outbound (`whaapyOutboundContactSync` — asimetría v5.1). Whaapy responde y de paso emite un webhook `contact.created` que es ECO de nuestra propia escritura. El worker `whaapyContactCreated` no tenía defensa R11 sobre ese evento (sí existía sobre `contact.updated`), así que invocaba `evaluateAndCreateC2Opportunity` como si fuera un lead orgánico de WhatsApp. Resultado: Lead nuevo sintético por cada customer Shopify propagado.
  2. **Sin invariante en el camino de creación de Cotización.** Independiente del eco, `draftOrdersCreate` insertaba la Cotización sin mirar si el contacto ya tenía un Lead nuevo activo del propio R12. Aun para leads orgánicos legítimos (no ecos) que después progresan a Cotización por Draft Order, las dos opps quedaban activas en simultáneo.
  - La precondición de R12 (`active_opportunity_exists` en `lib/services/r12-auto-creation.ts:100-108`) sí estaba implementada y funcionaba — pero solo cubre la dirección "R12 evalúa con Cotización ya en BD". La dirección inversa (R12 evalúa primero, Cotización aterriza después) quedaba descubierta porque la pre-condición se evalúa contra el estado actual de la BD, no contra eventos futuros.
- **Workaround / fix:** dos cambios coordinados, cada uno cubre una dirección de la race; juntos garantizan la invariante "Lead nuevo + opp avanzada nunca coexisten":
  1. **R11 opción A sobre `contact.created`.** El payload Whaapy de `contact.created` incluye `data.custom_fields` (validado por `WhaapyContactCreatedPayloadSchema`), y nuestro outbound inyecta `custom_fields.last_platform_write_at` con timestamp en cada POST/PATCH. Extraído el helper a `lib/services/whaapy-echo-detection.ts` (`isEchoByCustomFieldMarker`) para que `whaapyContactCreated` y `whaapyContactUpdated` lo compartan. Si el marker está presente y dentro de la ventana de 5 minutos hacia atrás, `whaapyContactCreated` registra audit `sync_loop_prevented` (reason `custom_field_marker_match_on_created`, suppressed `r12_auto_creation`) y RETORNA sin invocar R12. La hidratación del contacto local (identity match + LWW) sigue ejecutándose normal — solo se suprime la creación sintética de la opp.
  2. **Absorción del Lead nuevo en `draftOrdersCreate`.** Nuevo servicio `lib/services/opportunity-absorption.ts` (`absorbInitialStageOpportunities`) que, después de crear la Cotización, busca opps activas del mismo contacto en Funnel Venta con `stage.is_initial = true` (excluyendo la opp absorbente como defensa edge case) y las cancela vía `cancelOpportunity` con `cancellation_source = "absorbed_by_advanced_opportunity"`. Audit log `lead_nuevo_absorbed_by_advanced_opportunity` con `absorbing_opportunity_id`, `absorbed_opportunity_id`, `contact_id`, `trigger` (`draft_orders_create` o `draft_orders_update_as_create`). Invocado en ambos paths de creación de Cotización (`draftOrdersCreate` + el fallback create-branch de `draftOrdersUpdate`).
  3. **Cancelado ≠ perdido se preserva.** El absorber usa el mecanismo de cancelación existente (migración 0014): `cancelled_at` se setea, la etapa se PRESERVA, NO se inserta en `opportunity_stage_history`. El default de `listOpportunities` ya excluye canceladas → el Lead absorbido no contamina win rate (R5), no aparece en kanban activo (M5), no aparece en detalle de contacto activo (M6). Sigue visible vía `includeCancelled` / `onlyCancelled` para auditoría.
  4. **Los 8 contactos ya duplicados NO se tocan en este fix** — es un cambio preventivo. La corrección de datos históricos es un paso aparte (cancelar los Lead nuevo absorbidos manualmente con SQL que filtre por `contact_id` que tengan ambos opps activas en Funnel Venta).
- **Lección:**
  - **Cualquier worker inbound debe distinguir eco vs evento orgánico antes de disparar lógica de auto-creación.** R11 estaba implementado solo donde se notaba (LWW por campo en `contact.updated`), pero la mecánica del marker `custom_fields.last_platform_write_at` aplica igual al payload del `contact.created` — el primer webhook lo trae. Anti-patrón: asumir que "el evento existe → es orgánico". Patrón correcto: chequear marker antes de cualquier side-effect generador (auto-creación, notificación, propagación).
  - **Las precondiciones contra "estado actual de BD" son frágiles frente a races de workers paralelos.** Una precondición que mira `SELECT ... FROM opportunities` solo es válida si la inserción concurrente está serializada por contacto (lock, advisory lock, unique constraint). Sin eso, hay que cubrir AMBAS direcciones de la race — la precondición en R12 cubre una; la absorción en draft_orders cubre la otra. Si V2 introduce más disparadores de auto-creación, replicar el patrón o introducir un advisory lock por `contact_id` antes de evaluar.
  - **Cancelación con source semántica habilita post-mortem trivial.** Un `cancellation_source = "absorbed_by_advanced_opportunity"` en BD permite contestar "¿cuántas opps absorbió el sistema este mes?" con un `SELECT count(*)`. Si en V2 el fenómeno se vuelve frecuente, ese contador es la señal para reevaluar si el patrón sigue siendo correcto o si conviene migrar a lock por contacto.

### Lote polish M6 ronda 2 — pipeline filtros silenciosos, conteos lentos y URL de Shopify mal construida

- **Milestone donde se detectó:** lote polish M6 (correcciones ronda 2, junio 2026).
- **Síntoma:** (1) la barra de búsqueda del pipeline no filtraba nada — al escribir nombre/teléfono/referencia seguían apareciendo todas las tarjetas; (2) el rango de fechas tampoco cambiaba el resultado; (3) la plataforma reaccionaba con lag perceptible que antes del lote no existía; (4) el botón "Cliente en Shopify" del popup llevaba a la página genérica de la tienda, no al customer específico; (5) las notas en el timeline aparecían atribuidas a "Regina Vadai" aun cuando se creaban desde la cuenta del admin de Centr.
- **Causa raíz:**
  - **Búsqueda:** el `.or()` de PostgREST en `listKanbanOpportunities` mezclaba predicados sobre la tabla principal (`display_reference`) y sobre el embedded resource (`contact.full_name`, etc.) en un solo string. PostgREST NO soporta esa mezcla — el `.or()` aplica solo sobre la tabla principal salvo que se pase `{ referencedTable }`, y aún así no puede combinar parent + embedded en un solo predicado lógico. El resultado: el filtro completo se ignoraba silenciosamente.
  - **Fechas:** el filtro usaba `last_modified_at` (el campo de LWW del proyecto), no `created_at`. Como `last_modified_at` se actualiza con cada webhook o edit, las opps "recientes" según ese campo eran casi todas — el rango no se notaba.
  - **Lag:** la nueva función `countKanbanOpportunitiesByStage` traía TODAS las filas (sin `.limit()`) con un `!inner` join sobre `contacts` solo para contar en JavaScript. Con 5 000 opps, esa consulta era ~5 000 filas × join cartesiano vs 9 stages — operación pesada repetida por toggle de funnel, cambio de filtro y polling fallback cada 30s.
  - **Shopify URL:** se construía `https://{shopify_store_domain}/admin/customers/{id}`. El formato correcto del admin moderno es `https://admin.shopify.com/store/{handle}/customers/{id}`, donde `handle` es la parte antes de `.myshopify.com`. El formato viejo redirige a la tienda root.
  - **Autoría timeline:** el código resolvía el nombre del autor desde `user_profiles.full_name`, que se llenó en el bootstrap inicial con el nombre del operador VADAI (Regina). Cuando el admin de Centr opera desde la misma cuenta auth (o desde una nueva donde nadie actualizó user_profiles), el resolver muestra Regina porque es el valor sembrado, no porque sea quien hace la acción. El código siempre usó `session.userId` correctamente — el problema vive en DATA, no en LÓGICA.
- **Workaround / fix:**
  - **Búsqueda:** introducido `searchContactIdsForQuery(rawQuery)` en `lib/db/opportunities.ts` que pre-resuelve los `contact_id` matching y los inyecta en el `.or()` como `contact_id.in.(...)` — predicado puro de tabla principal. El caller (`loadInitialPipelineState` + `loadKanbanPageAction`) corre la sub-query una sola vez y comparte el resultado entre count + N stage queries via `matchingContactIds`.
  - **Fechas:** ambos `listKanbanOpportunities` y `countKanbanOpportunitiesByStage` cambiaron `last_modified_at` por `created_at` en los filtros de rango.
  - **Lag:** la función de conteo ya no joina contacts ni trae filas de más — `select("stage_id")` puro + `limit(50000)` como circuit breaker. La perf mejora en orden de magnitud para orgs con miles de opps.
  - **Shopify URL:** `lib/actions/opportunities-m6.ts` strips `.myshopify.com` del `shopify_store_domain` para obtener el handle y construye `https://admin.shopify.com/store/{handle}/customers/{id}`.
  - **Autoría timeline:** el resolver `loadUserNamesMap` ahora consulta `auth.users.raw_user_meta_data.full_name` después de `user_profiles.full_name` y le da prioridad si existe — el operador puede corregir su display name desde la Auth UI sin tocar BD. Además, fix definitivo en datos: ejecutar este SQL contra Supabase con el `auth_user_id` real del admin de Centr:
    ```sql
    -- Encuentra el user id del operador (admin de Centr):
    SELECT id, email FROM auth.users WHERE email = '<email-del-admin>';
    -- Actualiza el display name en ambos lugares:
    UPDATE public.user_profiles SET full_name = 'Nombre correcto' WHERE id = '<auth-user-id>';
    UPDATE auth.users SET raw_user_meta_data =
      raw_user_meta_data || jsonb_build_object('full_name', 'Nombre correcto')
      WHERE id = '<auth-user-id>';
    ```
- **Lección:**
  - PostgREST `.or()` con embedded resources es trampa silenciosa — el filtro no falla, solo se ignora. Cuando el query toca múltiples tablas relacionadas, la regla operativa segura es pre-resolver la sub-query a una lista de IDs y aplicar el OR sobre la tabla principal.
  - Las funciones de "count" que no aprovechan `count: 'exact', head: true` y no acotan con `.limit()` son una bomba de relojería de performance — el costo escala con el tamaño total de la tabla, no con la página visible. Siempre acotar el conteo con limit defensivo + select mínimo (solo el discriminador).
  - El campo de fecha "fecha de creación" del usuario casi siempre es `created_at`, no `last_modified_at` ni `updated_at`. Cuando se construye un filtro de rango en la UI, confirmar contra schema antes de cablear — `last_modified_at` se actualiza con LWW de webhooks/syncs y no refleja "cuándo apareció esta opp".
  - `user_profiles.full_name` y `auth.users.raw_user_meta_data.full_name` pueden divergir. El display autoritativo de "quién hizo qué" debe priorizar el campo que el usuario controla activamente (Auth UI) sobre el campo sembrado.
  - El handle Shopify del Admin URL moderno no es el dominio crudo `*.myshopify.com` — es el slug del store. Verificar formato con un link real antes de cablear builders de URL.

### RETURNING INTO variable escalar con INSERT multi-fila falla en PL/pgSQL

- **Milestone donde se detectó:** M1.
- **Síntoma:** función `bootstrap_organization` fallaba con `ERROR: P0003: query returned more than one row` en la línea del INSERT de 7 etapas Funnel Venta.
- **Causa raíz:** `INSERT ... VALUES (multi-fila) RETURNING id INTO variable_escalar` es inválido en PL/pgSQL — una variable escalar solo puede recibir 1 fila. Para casos multi-fila se requiere `RETURNING ... BULK COLLECT INTO arr` o, como en este caso, eliminar la cláusula RETURNING si no se necesita.
- **Workaround / fix:** se eliminó la cláusula `RETURNING ... INTO` del INSERT multi-fila. Los IDs de las etapas se recuperan inmediatamente después por nombre con `SELECT ... INTO ...`, que era la lógica funcional. La línea problemática era redundante.
- **Lección:** cuando un INSERT inserta múltiples filas y la lógica posterior necesita los IDs, NO usar `RETURNING ... INTO variable_escalar`. Opciones válidas: (a) recuperar por columna única posterior con SELECT, (b) usar `RETURNING ... BULK COLLECT INTO array`, (c) hacer INSERTs uno por uno con su propio RETURNING. La opción (a) es legible y suficiente cuando ya hay un identificador único como `name + organization_id + funnel`.

### Flujo de invitación incompleto — hash fragment vs PKCE en Supabase Auth

- **Milestone donde se detectó:** M2 (fix post-entrega).
- **Síntoma:** click en el email de invitación de Supabase redirigía al usuario a `/login` sin mostrar ninguna pantalla para definir contraseña. La activación de cuenta nunca se completaba.
- **Causa raíz:** `app/auth/callback/route.ts` (Route Handler) sólo manejaba el flujo PKCE — tokens llegando como `?code=`. Supabase envía las invitaciones (y password recovery) en flujo implícito: los tokens llegan como `#access_token=...&refresh_token=...&type=invite` (hash fragment). Los hash fragments son **client-side only** — el servidor nunca los recibe. El Route Handler veía la request sin `?code=`, caía al catch-all, y redirigía a `/login?error=link_expired`.
- **Workaround / fix:**
  1. **Route Handler actualizado:** si no hay `?code=`, devuelve un HTML mínimo con `<script>window.location.replace('/auth/confirm'+window.location.hash)</script>`. El script ejecuta en el navegador y redirige a `/auth/confirm` preservando el hash fragment (que el servidor nunca habría visto). `window.location.replace` evita que `/auth/callback` quede en el historial del navegador.
  2. **Nueva página `/auth/confirm`** (`app/(auth)/auth/confirm/page.tsx`): Client Component que parsea el hash en `useEffect`. Para `type=invite` o `type=recovery` renderiza un formulario para definir contraseña (validación mínima 8 caracteres + confirmación). Llama `supabase.auth.setSession()` con los tokens del hash y luego `supabase.auth.updateUser({ password })`. Para `type=magiclink`/`email` establece sesión y redirige al dashboard. Edge cases: hash vacío, error en hash, tokens expirados — todos muestran mensaje en español con link a `/login`.
  3. **Middleware actualizado:** `/auth/confirm` agregado a `PUBLIC_ROUTES`.
- **Lección (parte 1 — Route Handler):** Supabase Auth tiene **dos flujos distintos en Next.js App Router**: (a) **PKCE** (`?code=` → `exchangeCodeForSession` en Route Handler o Server Component) y (b) **Implícito** (`#access_token=` → sólo accesible client-side). Las invitaciones y password recovery de Supabase usan el flujo implícito con hash fragment. Un Route Handler nunca puede manejarlos directamente. La técnica correcta es servir desde el Route Handler un HTML mínimo que haga el redirect client-side con `window.location.replace`, preservando el hash. La nueva página `/auth/confirm` actúa como landing unificado para todos los flujos de hash.
- **Lección (parte 2 — Site URL como landing):** `/auth/confirm` sólo recibe tokens si Supabase está configurado con una URL específica como redirect (ej. `redirect_to=/auth/callback`). Cuando el Site URL de Supabase es la raíz del dominio (`http://localhost:3000`), las invitaciones aterrizan en `/login#access_token=...` — la página de login ignora el hash y el flujo muere silenciosamente. **Fix:** `LoginForm` (`components/auth/login-form.tsx`) detecta en `useEffect` si `window.location.hash` contiene `access_token`; si es así, hace `window.location.replace('/auth/confirm' + hash)` antes de renderizar el formulario (`ready` state en `false` evita que el form flashee). No basta con tener `/auth/confirm` aislado: cualquier página pública a la que Supabase pueda redirigir debe también interceptar el hash.

### Validador de env falla en startup por variables opcionales definidas vacías en .env.local

- **Milestone donde se detectó:** M2 (fix post-entrega).
- **Síntoma:** la app falla al arrancar con `Variables de entorno server inválidas: ...` señalando `SHOPIFY_WEBHOOK_SECRET` y/o `WHAAPY_API_KEY`. Estas variables están en `.env.local` como `SHOPIFY_WEBHOOK_SECRET=` (vacías a propósito, pendientes de M3).
- **Causa raíz:** `z.string().min(1).optional()` en Zod NO es equivalente a "ausente o no vacío". `.optional()` permite `undefined` (campo ausente), pero cuando la variable SÍ existe en el entorno como cadena vacía `""`, Zod la ve como presente y aplica `.min(1)` — que falla. En `.env.local`, `VARIABLE=` sin valor se expande como `""` en `process.env`, no como `undefined`.
- **Workaround / fix:** cambiar a `z.string().optional()` (sin `.min(1)`) para las dos variables de entrada diferida. El startup validator solo exige que, si están presentes, sean strings — sin restricción de longitud. Para proteger el uso en runtime, se agregan helpers de acceso tardío `getShopifyWebhookSecret()` y `getWhaapyApiKey()` en `lib/env.ts`: lanzan un error descriptivo con contexto de milestone cuando la variable está vacía o ausente. M3+ debe usar estos helpers en lugar de leer `getServerEnv().SHOPIFY_WEBHOOK_SECRET` directamente.
- **Lección:** en proyectos con milestones incrementales, distinguir entre dos categorías de variables en el schema de Zod: (a) **siempre requeridas** — `z.string().min(1)` sin `.optional()`, falla en startup si faltan; (b) **requeridas desde milestone X** — `z.string().optional()` en startup + helper de acceso que valida en runtime. La validación tardía es preferible a eliminar la protección: el error sigue siendo descriptivo, pero no bloquea arranques legítimos en milestones anteriores. Antipatrón a evitar: `z.string().min(1).optional()` — comunica "no vacío si presente" pero la semántica de startup es confusa cuando `.env.local` define la variable como vacía.

### search_path mutable en funciones PL/pgSQL sin SET search_path

- **Milestone donde se detectó:** M2 (post-entrega, Supabase Security Advisor).
- **Síntoma:** Security Advisor reportó "Function has a mutable search_path" para `tg_set_updated_at`, `current_organization_id`, `assert_organization_context` y `tg_block_mutation`.
- **Causa raíz:** Las funciones PL/pgSQL sin `SET search_path` heredan el `search_path` de la sesión en el momento de ejecución. Un atacante con permisos para alterar el `search_path` de la sesión puede hacer que la función resuelva tablas o funciones de un schema malicioso en lugar del `public` esperado.
- **Workaround / fix:** `ALTER FUNCTION public.<nombre>() SET search_path = public;` en migración nueva idempotente (0011). Para funciones SECURITY DEFINER el riesgo es mayor — pero las del proyecto ya tenían `set search_path` en el cuerpo o como opción de función (`is_member_of`, `bootstrap_organization`); el fix de 0011 cubre las que faltaban.
- **Lección:** Toda función PL/pgSQL debe declarar `SET search_path = public` (o el schema relevante) como **opción de función**, no como primera sentencia del `$$` body. La forma idiomática es: `create or replace function public.myfn() returns void language plpgsql set search_path = public as $$ ... $$;` — el `SET search_path` va entre el `language` y el `as $$`. Si se omite en el `CREATE FUNCTION`, corregir con `ALTER FUNCTION ... SET search_path = public;` en una migración posterior.

### SECURITY DEFINER callable externally — PostgREST expone funciones con EXECUTE en PUBLIC

- **Milestone donde se detectó:** M2 (post-entrega, Supabase Security Advisor).
- **Síntoma:** Security Advisor reportó "Function is callable by PUBLIC" para `bootstrap_organization` e `is_member_of`. También reportó `rls_auto_enable` — que resultó ser una función Supabase-interna, no una función custom del proyecto.
- **Causa raíz:** PostgREST (la capa REST de Supabase) expone como endpoint `/rest/v1/rpc/<nombre>` toda función sobre la que PUBLIC (o cualquier rol equivalente) tenga EXECUTE. Las funciones SECURITY DEFINER expuestas así son un riesgo porque cualquier cliente anónimo puede invocarlas con los privilegios elevados del owner.
- **Workaround / fix (intento 1, migración 0011 — INCOMPLETO):** `REVOKE EXECUTE ON FUNCTION ... FROM PUBLIC; GRANT EXECUTE ... TO <roles>;`. Aplicado en migración 0011. **Resultado: no silenció los warnings.** Ni la migración ni un fix manual posterior del operador (también solo REVOKE FROM PUBLIC) movieron la aguja en Security Advisor.
- **Workaround / fix (intento 2, migración 0012 — DEFINITIVO):** REVOKE explícito de `PUBLIC, anon, authenticated`. Para `bootstrap_organization`: GRANT solo a `service_role`. Para `rls_auto_enable` (no definida en migraciones propias — la creó Supabase): DO block que itera `pg_proc` para aplicar el patrón a todas las sobrecargas existentes. Para `is_member_of`: warning intencional — `anon` y `authenticated` DEBEN conservar EXECUTE para que RLS funcione (ver decisión arquitectónica en 0012). Aplicado en migración 0012.
- **Lección (causa del intento 1 fallido):** Supabase configura por defecto `ALTER DEFAULT PRIVILEGES IN SCHEMA public GRANT EXECUTE ON FUNCTIONS TO anon, authenticated`. Estos grants son **separados** del grant a `PUBLIC` — `REVOKE FROM PUBLIC` NO los toca. PostgREST sigue exponiendo la función como RPC porque `anon`/`authenticated` retienen EXECUTE vía sus grants explícitos. Patrón siempre erróneo: `REVOKE ... FROM PUBLIC` solo. Patrón correcto: `REVOKE ... FROM PUBLIC, anon, authenticated` + GRANT explícito a los roles que realmente lo necesitan.
- **Lección (warnings residuales intencionales):** Funciones SECURITY DEFINER usadas en RLS policies (como `is_member_of`) NO pueden tener `anon`/`authenticated` revocados — las policies fallarían con "permission denied for function". Security Advisor seguirá reportándolas como "callable by anon/authenticated"; documentar como deuda consciente en CLAUDE.md y omitir. Alternativas (SECURITY INVOKER, mover a schema privado) son invasivas y aportan poco frente al riesgo real, dado que la función solo retorna boolean y consulta tablas con RLS propio.
- **Lección (functions desconocidas reportadas por Advisor):** Si Security Advisor reporta una función no encontrada en migraciones propias (caso `rls_auto_enable`), probablemente es función Supabase-interna o de extension/template. NO crear migración con signature asumida — usar DO block + `pg_proc` para descubrir signatures reales y aplicar REVOKE/GRANT a las que existan. El patrón está en migración 0012.

### Protected Customer Data malinterpretado — Custom Apps tienen acceso automático

- **Milestone donde se detectó:** M2 (post-entrega, durante setup de credenciales reales de Shopify).
- **Síntoma:** documentación en CLAUDE.md afirmaba que los scopes `read_customers`, `write_customers` y `read_all_orders` requerían aprobación formal de Shopify antes de operar — Protected Customer Data Form para los dos primeros y request manual en Partner Dashboard para `read_all_orders`. La consecuencia implícita era bloqueo de la sincronización real de contactos en M3 contra la tienda de Centr y del backfill completo de M11 hasta que Shopify aprobara solicitudes externas.
- **Causa raíz:** confusión entre dos categorías distintas de apps Shopify. Los formularios de Protected Customer Data y el request manual de `read_all_orders` aplican **únicamente a apps publicadas en el Shopify App Store** (distribución pública, instalación masiva). Las **Custom Apps creadas en el Dev Dashboard e instaladas por organización vía OAuth** (modelo de Centr Hub) tienen acceso automático a Protected Customer Data Levels 1 y 2 y a `read_all_orders` — el consentimiento del merchant se otorga al aprobar los scopes durante la instalación, no por trámite externo. El malentendido se introdujo al documentar el "Setup post-M2" sin distinguir estos dos modelos.
- **Workaround / fix:** sección "Scopes protegidos de Shopify" en CLAUDE.md reescrita para clarificar el modelo Custom App y explicitar que los scopes están operativos al instalar la app. Nota equivalente en "Alcance del backfill inicial" corregida — M11 no está bloqueado por aprobación pendiente. Si la query de customers u orders devuelve vacío en producción, se trata como bug a investigar (token mal obtenido, scope omitido en la lista solicitada, rechazo silencioso en la instalación), no como restricción regulatoria.
- **Lección:** para proyectos Shopify, distinguir desde el primer milestone entre dos modelos de distribución:
  - **Custom Apps** (Dev Dashboard, instalación 1-a-1 vía OAuth por organización): scopes protegidos operativos al instalar, sin trámite externo. Modelo SaaS multi-tenant típico, aplica a Centr Hub.
  - **Apps públicas del App Store** (distribución masiva, store-listing): scopes protegidos requieren Protected Customer Data Form y, para `read_all_orders`, request manual con justificación en Partner Dashboard.
  - La documentación de Shopify mezcla los dos modelos en páginas adyacentes sin etiquetarlos siempre con claridad. Antes de documentar restricciones operativas o bloqueos a milestones futuros, verificar explícitamente bajo qué modelo opera la app. El disparador de esta corrección fue el cuestionamiento operativo del operador ("¿por qué necesitaríamos un trámite externo si la app es 1-a-1?") durante el setup post-M2 — ese tipo de pregunta es la señal correcta para revisar el supuesto.

### Falso positivo posible en R11 dentro de la ventana de 30s (trade-off aceptado)

- **Milestone donde se detectó:** M3 (documentado tras cierre).
- **Síntoma esperado en producción:** un usuario edita un contacto directamente en Shopify Admin (cambia nombre, teléfono, dirección) dentro de los ~30 segundos posteriores a una escritura outbound de la plataforma sobre ese mismo contacto. El webhook `customers/update` resultante lleva `updated_at` cercano al `contact.last_modified_at` local Y el contact tiene `last_modified_source = 'platform'` → la defensa anti-bucle lo descarta como si fuera echo de la propia plataforma. El edit del usuario NO se aplica al maestro local y NO se propaga a Whaapy. Silencioso del lado del usuario; solo aparece en el audit log `sync_loop_prevented`. No hay reporte de error.
- **Causa raíz:** la mecánica R11 implementada es la **opción B** descrita en CLAUDE.md (comparación de timestamps + marker `last_modified_source`). Detecta correctamente los echos reales de Shopify cuando la plataforma escribió, pero NO puede distinguir un echo real de un edit legítimo del usuario hecho dentro de la misma ventana. Es una propiedad inherente a la mecánica: si `payload.updated_at` cae dentro de `[last_local_write_at, last_local_write_at + 30s]` Y la última fuente local es `platform`, se asume eco.
- **Por qué no opción A:** la opción A (marker en metafield/note custom del customer) requiere request adicional contra Shopify para leer el metafield por cada webhook entrante — duplica el tráfico contra la API y consume cuotas. La opción B no requiere round-trip y captura el 99%+ de los casos reales en producción típica (Shopify entrega webhooks en <5s en operación normal; la ventana de 30s deja margen para latencia transitoria sin abrir tanto que aumente el falso positivo).
- **Probabilidad e impacto:** **probabilidad baja en operación real** (requiere que un humano edite manualmente en Shopify Admin justo en la ventana donde la plataforma acaba de escribir; la mayoría de los edits manuales son aleatorios en el tiempo y no caen en esa ventana). **Impacto alto cuando ocurre** porque es silencioso — el usuario no recibe error, solo nota que su cambio "no se propagó" si vuelve a la plataforma.
- **Decisión: aceptar el trade-off.** No re-implementar opción A profilácticamente. Si la evidencia operativa muestra incidentes (Mayor o el admin reporta "edité X y se perdió"), re-evaluar.
- **Workaround / fix:** trazabilidad mejorada en el audit log `sync_loop_prevented`. El payload ahora incluye:
  - `delta_ms` — diferencia absoluta en ms entre `payload.updated_at` y `contact.last_modified_at`.
  - `payload_updated_at` — timestamp del webhook entrante.
  - `last_local_write_at` — timestamp de la última escritura outbound local.
  - `echo_window_ms` — la constante de la ventana (30000ms).
  Con estos campos, si un usuario reporta pérdida de un edit:
  1. Consultar `audit_log` filtrado por `event_type = 'sync_loop_prevented'` y `entity_id = <contact_id>`.
  2. Si aparece un evento con `delta_ms` cercano al límite (~25-30s) Y `payload_updated_at > last_local_write_at` por varios segundos: alta sospecha de falso positivo. El edit del usuario probablemente cayó en la ventana.
  3. Si `delta_ms < 5s`: muy probablemente echo real (Shopify entrega webhooks ~3-5s después de la escritura).
- **Lección:** defensas heurísticas con ventana temporal siempre tienen falsos positivos potenciales. La regla operativa en milestone M3 fue "implementar defensa desde el primer commit, no diferir" — eso obliga a aceptar la heurística más simple disponible. Documentar el trade-off **con telemetría suficiente para diagnosticar el bug si se manifiesta** es la única defensa contra "no sabíamos que ocurría". Patrón aplicable a futuras defensas similares (rate limiting, dedup atómico, etc.): siempre exponer en audit/log los parámetros de la decisión, no solo el resultado.

### Cancelado ≠ Perdido — la cancelación administrativa NO debe mapearse a etapa `is_lost`

- **Milestone donde se detectó:** M3 (corrección post-entrega).
- **Síntoma:** El worker `draft_orders/delete` movía la oportunidad cuya Draft Order fue eliminada en Shopify a la etapa `is_lost` ("Perdida"). Esto contamina win rate del vendedor: cada DO borrado por error/duplicado/auto-borrado de Shopify tras 1 año contaba como pérdida comercial real. Un vendedor con muchos DOs de ciclo largo (>1 año, auto-borrados por Shopify) y un admin que limpia duplicados generaban pérdidas falsas masivas que NO eran culpa del vendedor.
- **Causa raíz:** El diseño inicial de M3 mapeaba el delete de Shopify al concepto "pipeline" más cercano del Funnel Venta (etapa Perdida). Pero "Perdida" en la doctrina significa transición real del pipeline (vendedor compitió y perdió contra precio/competencia/ghosting → requiere motivo, impacta win rate). Una cancelación administrativa no es lo mismo: no hubo competencia comercial, no requiere motivo, no debe impactar métricas. El modelo conceptual exigía un side-flag independiente de la etapa, no una transición.
- **Workaround / fix:** Migración 0014 agrega columnas `cancelled_at`, `cancellation_source`, `cancellation_note` a `opportunities` + índice parcial `WHERE cancelled_at IS NULL` para el pipeline activo. Worker `draft_orders/delete` ahora invoca `cancelOpportunity(...)` que marca el side-flag SIN transitar de etapa y SIN insertar en `opportunity_stage_history` (no hubo cambio de etapa — la etapa actual se preserva como auditoría de "dónde estaba al cancelarse"). `listOpportunities(...)` excluye canceladas por default; opt-in explícito con `includeCancelled` o `onlyCancelled`. CLAUDE.md sección "Cancelación de oportunidades — modelo independiente de etapa" documenta el contrato para M5/M6/M10. Win rate del dashboard (M10) debe usar el filtro default — denominador = Ganadas + Perdidas SIN canceladas.
- **Lección:** "Borrado externo del proveedor" NO equivale a "transición del pipeline" en sistemas con métricas operativas sensibles al funnel. Cuando un evento externo dispara un side-effect que parece encajar en una etapa existente, validar la **semántica** primero: ¿qué pregunta operativa responde esa etapa? Si la respuesta es "el vendedor perdió comercialmente", entonces eventos administrativos NO deben mapear ahí — necesitan un dimensión independiente (cancelled_at, archived_at, deleted_at) que vive al lado de stage_id pero no lo reemplaza. Patrón aplicable también a (futuro): "snoozed" no es etapa, "archivado por inactividad" no es etapa, "duplicado fusionado" no es etapa. Cada uno son flags ortogonales con sus propias queries de exclusión por default.

### Inngest v4 quitó `EventSchemas` y la signature de `createFunction` cambió

- **Milestone donde se detectó:** M3.
- **Síntoma:** El typecheck falló con `Module '"inngest"' has no exported member 'EventSchemas'` y `Expected 2 arguments, but got 3` al pasar `{ id }, { event }, handler` a `inngest.createFunction(...)`. La documentación pública mencionaba EventSchemas pero la versión instalada (4.4.0) ya no lo exporta.
- **Causa raíz:** Inngest SDK v4 reorganizó la tipificación de eventos. (a) El export `EventSchemas` desapareció — los schemas ahora se aplican **por-trigger** vía `schema: StandardSchemaV1<...>` o se asume `unknown` y se castea en runtime. (b) `createFunction` ahora acepta **2 argumentos**: `(opts, handler)`, donde `opts` incluye `triggers: [{ event: "..." }]`. La firma vieja `(opts, trigger, handler)` ya no existe.
- **Workaround / fix:** (1) Eliminar el generic `Inngest<{ schemas: EventSchemas }>` del cliente — usar `new Inngest({ id })` sin tipos de eventos. (2) Cada función pasa `triggers: [{ event: "topic/name" }]` dentro de las opciones. (3) En el handler, `event.data` queda tipado como `unknown` — castear explícitamente a `ShopifyWebhookEnvelope` al inicio: `const envelope = event.data as unknown as ShopifyWebhookEnvelope;`. Aceptable porque hay UN único productor (endpoint webhook) que construye el envelope antes de `inngest.send`.
- **Lección:** En SDKs que evolucionan rápido (Inngest sube versiones mayores con frecuencia), preferir patrones de tipificación **runtime-castable** sobre type-system fuerte cuando hay un productor único bien controlado. El cast manual es explícito y resistente a cambios de API; el generic tightly-coupled rompe con cada bump. Para validar correctitud, escribir tests sintéticos del productor que validan el shape del envelope antes de enviarlo a Inngest.

### `Insertable<R>` espera todos los campos no-auto-generados — defaults SQL no eximen al TS

- **Milestone donde se detectó:** M3.
- **Síntoma:** Cada `createContact(...)` y `createOpportunity(...)` falló typecheck con `Property 'X' is missing in type '{...}'` para campos como `assigned_advisor_id`, `whaapy_contact_id`, `deleted_in_shopify`, `parent_opportunity_id`, `probability_override`, etc. Aunque la BD tiene `default false`/`default null` para esos campos, el TS hand-written `Insertable<R>` solo marca `id`, `created_at`, `updated_at` como opcionales.
- **Causa raíz:** El tipo `Insertable<R>` definido en `lib/types/database.ts` es: `Omit<R, "id" | "created_at" | "updated_at"> & Partial<Pick<R, "id" | "created_at" | "updated_at">>`. Eso hace OBLIGATORIOS todos los demás campos del Row, incluso los que tienen `DEFAULT` en SQL. Sin generador de tipos automatizado desde el schema, no hay forma de inferir cuáles tienen default sin enumerarlos.
- **Workaround / fix:** Cada caller de `createContact`/`createOpportunity` debe pasar EXPLÍCITAMENTE todos los campos del Row (incluso con `null`/`false`). Para evitar duplicación, se introdujo el helper `buildContactInsert(...)` en cada worker (customers, draft-orders, orders, backfill) que centraliza la construcción del payload con defaults explícitos. Similar para opportunity con `buildOpportunityInsertFromDraftOrder(...)`. Cuando Supabase CLI esté habilitado y `lib/types/database.ts` se regenere, los Insert types reflejarán correctamente los defaults SQL y los helpers podrán omitir esos campos.
- **Lección:** Mientras `lib/types/database.ts` siga hand-written, los inserts son verbosos por necesidad. NO refactorizar agregando `?` manualmente al type Row para "hacer más opcional" — eso enmascara la columna como nullable a nivel modelo, lo que se propaga a queries de lectura como `string | null` cuando son `string`. Mejor: helpers `buildXxxInsert(...)` por aggregate, con todos los defaults explícitos en un solo lugar. Cuando M11+ habilite el generador, todos los helpers se simplifican de golpe.

### Inngest `retries` espera union de literales 0..20, no `number`

- **Milestone donde se detectó:** M3.
- **Síntoma:** `inngest.createFunction({ id, retries: args.retries ?? 5, ... })` falló typecheck con `Type 'number' is not assignable to type '0 | 1 | 2 | ... | 20 | undefined'`. La aritmética `args.retries ?? 5` widena el resultado a `number`, no a literal `5`.
- **Causa raíz:** En Inngest v4 el tipo de `retries` es una unión de literales numéricos 0..20 (el SDK limita reintentos máximos a 20). TypeScript no infiere `5` como literal cuando viene de una expresión `??`.
- **Workaround / fix:** Definir alias local `type InngestRetries = 0 | 1 | 2 | ... | 20;` y tipar el parámetro como `retries?: InngestRetries`. El cast es a nivel de la firma del helper, no en cada callsite.
- **Lección:** SDKs que usan unions de literales en lugar de `number` ofrecen mejor safety pero crean fricción cuando se quiere parametrizar. Patrón: aliasear el union localmente y usar ese alias en todas las firmas internas — el cast se centraliza.

### `vi.mock` se hoistea desde dentro de funciones, perdiendo el closure

- **Milestone donde se detectó:** M3.
- **Síntoma:** Test helpers de M3 (`tests/helpers/fake-supabase.ts`) exportaban una función `installFakeSupabase()` que llamaba `vi.mock(...)` con una referencia a una variable local `fake`. Los tests que importaban este helper fallaban con `ReferenceError: fake is not defined` en `getSupabaseAdminClient` — y la traza apuntaba al closure DENTRO del helper, no al test caller.
- **Causa raíz:** Vitest hoistea TODAS las llamadas `vi.mock(...)` al inicio del archivo donde aparecen, sin importar si están dentro de una función. Cuando `installFakeSupabase()` contenía `vi.mock`, Vitest lo extraía a module-top del archivo `helpers/fake-supabase.ts`. La referencia a `fake` (declarada dentro de `installFakeSupabase`) quedaba apuntando a `undefined` porque la función nunca corría — el módulo solo se importaba.
- **Workaround / fix:** Eliminar `installFakeSupabase()` del helpers file. Cada test que necesita mockear `@/lib/supabase/admin` debe declarar `vi.mock` a module-top en el propio test file, con la instancia `fake` como `const` arriba. El helper solo exporta la `class FakeSupabase` reutilizable.
- **Lección:** No envolver `vi.mock` dentro de funciones — el hoisting de Vitest rompe el closure. Patrón correcto: `const fake = new FakeSupabase(); vi.mock("@/path", () => ({ ...: () => fake }));` a module-top del archivo de test. El `fake` declarado afuera SÍ es accesible porque también queda hoisteado (es un `const` evaluado lazy en runtime, no en parse-time como `vi.mock`).

### supabase-js 2.105 — Database type hand-written incompatible con shape estricta

- **Milestone donde se detectó:** M1.
- **Síntoma:** `next build` fallaba con `Object literal may only specify known properties, and 'organization_id' does not exist in type 'never[]'` en TODAS las llamadas a `.insert(...)` y `.update(...)` del data layer. `tsc --noEmit` reportaba ~30 errores idénticos. El cliente reportaba el shape interno `PostgrestVersion: "12"` con `never` en todas las posiciones.

### Middleware redirigía endpoints server-to-server (`/api/webhooks/*`, `/api/inngest`) a `/login`

- **Milestone donde se detectó:** M3 (fix post-entrega — bug crítico en producción).
- **Síntoma:** POST a `https://centr-hub.vercel.app/api/webhooks/shopify` devolvía `307` a `/login` antes de llegar al handler. Los webhooks de Shopify nunca se procesaban en producción. GET a la misma URL desde un navegador autenticado sí devolvía `405` (handler alcanzado) porque el navegador llevaba la cookie de Supabase y el middleware lo dejaba pasar — eso enmascaró el bug durante el desarrollo, donde casi todas las pruebas se hacían desde el browser logueado.
- **Causa raíz:** el matcher del middleware (`/((?!_next/static|_next/image|favicon.ico|.*\.(?:svg|png|jpg|jpeg|gif|webp)$).*)`) cubría todo excepto assets estáticos — incluyendo `/api/webhooks/shopify` y `/api/inngest`. Los webhooks llegan server-to-server (Shopify, Inngest), nunca con cookies de Supabase. `supabase.auth.getUser()` retornaba null, la ruta no estaba en `PUBLIC_ROUTES`, y el middleware emitía `307 → /login`. Shopify recibía el redirect, no seguía POST a /login (correcto), y el evento se perdía.
- **Workaround / fix:** exclusión a nivel matcher en `middleware.ts`: `"/((?!api/webhooks|api/inngest|_next/static|_next/image|favicon.ico|.*\\.(?:svg|png|jpg|jpeg|gif|webp)$).*)"`. Los prefijos `api/webhooks` y `api/inngest` quedan fuera del middleware completamente — no corre la llamada a Supabase ni la lógica de cookies. Esto cubre `/api/webhooks/shopify`, futuros `/api/webhooks/whaapy` (M4), y el handler de Inngest. Otras rutas `/api/*` que sí requieren sesión (data del dashboard, server actions, M5+) siguen pasando por middleware.
- **Por qué exclusión de matcher en lugar de `PUBLIC_ROUTES`:** agregar a `PUBLIC_ROUTES` también arreglaba el redirect, pero seguía ejecutando `supabase.auth.getUser()` (round-trip a Supabase) por cada webhook. Bajo carga real (Shopify puede enviar bursts) ese overhead es desperdicio puro. Exclusión de matcher = zero-cost en webhooks + semántica más clara (estos endpoints NUNCA pasan por auth de sesión).
- **Lección:** en Next.js App Router, el matcher del middleware es la primera línea de defensa Y la primera línea de ataque a la latencia. Cualquier endpoint server-to-server (webhooks de proveedores, signing endpoints, health checks, Inngest/Trigger.dev/QStash) debe excluirse del matcher por defecto — no agregarse a una lista de "rutas públicas" dentro del middleware. Patrón anti-bug: cuando se agrega un endpoint nuevo bajo `/api/*` que será invocado server-to-server, **el primer commit que crea la ruta debe actualizar el matcher**, no diferir. El bug es invisible en dev (browser tiene cookies) y solo se manifiesta cuando un proveedor real golpea el endpoint en producción — el costo de descubrirlo tarde es altísimo (webhooks perdidos, datos desincronizados, debugging caro). Regla operativa: cada vez que se cree un endpoint público nuevo bajo `/api/*`, validar con un curl SIN cookies (`curl -X POST -i ...`) que la respuesta NO es 307 a /login antes de mergear.

### Scripts CLI con tsx no pueden importar `server-only` — paquete vive solo dentro de Next.js

- **Milestone donde se detectó:** M3 (fix post-entrega — al ejecutar `npm run shopify:*` por primera vez desde la terminal).
- **Síntoma:** los tres scripts en `scripts/shopify/` (`configure-webhooks.ts`, `backfill-incremental.ts`, `harness-create-customer.ts`) fallaban con `Error: Cannot find module 'server-only'` al ejecutarse vía `tsx`. La traza apuntaba a `lib/supabase/admin.ts`, que arranca con `import "server-only";` para proteger el cliente con `service_role_key` de cualquier Client Component.
- **Causa raíz:** el paquete `server-only` es un "marker package" — Next.js lo declara como dependencia pero solo lo instala dentro de `node_modules/next/dist/compiled/server-only/`, no en el root de `node_modules/`. Next.js lo aliasea internamente vía webpack/SWC en cada build, así que el import funciona en runtime de Next.js (dev, build, serverless) sin que el paquete viva en el resolution path normal de Node. Cuando `tsx` ejecuta un script directamente, no hay aliaseo: Node intenta resolver `server-only` con sus reglas estándar y no lo encuentra. Si lo encontrara (instalado como dep real), tampoco serviría — el `index.js` de `server-only` lanza un error explícito cuando se importa sin la condition `react-server`, que solo Next.js setea.
- **Workaround / fix:** `scripts/_lib/server-only-shim.ts` (módulo vacío, `export {};`) + `scripts/tsconfig.json` que extiende `../tsconfig.json` y añade `paths: { "server-only": ["./_lib/server-only-shim.ts"] }`. Los tres scripts npm en `package.json` ahora invocan `tsx --tsconfig scripts/tsconfig.json scripts/shopify/...`. tsx honra los `paths` de tsconfig al resolver imports, así que la cadena `script → lib/supabase/admin.ts → import "server-only"` resuelve al shim vacío durante la ejecución CLI. Importante: el `tsconfig.json` raíz NO se modifica — Next.js sigue usando el `server-only` real con su semántica protectora intacta (un Client Component que lo importe sigue rompiendo el build).
- **Por qué este patrón en lugar de alternativas evaluadas:**
  - **Refactor de `admin.ts` para no importar `server-only`**: viola explícitamente la restricción "NO debilitar la protección" del prompt M3. Descartada.
  - **Instalar `server-only` como devDependency**: el paquete sin la condition `react-server` lanza un error en el `index.js`. Aunque `--conditions=react-server` haría que Node resuelva al `empty.js`, agregar una dep "marker" externa contradice el principio de no actualizar deps sin razón fuerte (CLAUDE.md). Descartada.
  - **Preload via `node -r` o `module.register`**: requiere parchear `Module._resolveFilename` o instalar un loader ESM custom. Funcional pero hacky y opaco; el `paths` de tsconfig es semántica nativa de TypeScript/tsx. Descartada.
  - **`paths` en el tsconfig raíz directamente**: contaminaría la compilación de Next.js (el bundler aplicaría el shim también en producción, derrotando el propósito de `server-only`). Por eso el tsconfig vive en `scripts/` y solo se usa con `--tsconfig`.
- **Lección:** scripts CLI que comparten `lib/` con código de Next.js heredan los markers de aislamiento de RSC (`server-only`, `client-only`) que no resuelven fuera del bundler. **Cada script nuevo bajo `scripts/` que importe (directa o transitivamente) algo de `lib/` debe correr vía `tsx --tsconfig scripts/tsconfig.json`**, no vía `tsx` plano. Aplicable a futuros scripts de M4 (Whaapy), M6 (utilities de contactos) y M11 (backfill bulk). El shim queda en `scripts/_lib/server-only-shim.ts`; si futuros markers de RSC aparecen (`react-server`, etc.), se añaden al mismo patrón (otra entrada en `paths` + otro stub vacío).

### `shopify_tags` NULL violation por LWW que convierte `[]` a `null`

- **Milestone donde se detectó:** M3 (bug productivo detectado durante CHECKPOINT M4, commit `f29bba4`).
- **Síntoma:** `audit_log` muestra múltiples entradas `shopify_webhook_failed` con error `null value in column shopify_tags of relation contacts violates not-null constraint` para topics `customers/create` y `customers/update`. El contact SÍ entra en la tabla (INSERT funciona), pero acumula failures con el mismo `shopify_event_id` por los 5 retries de Inngest. Caso real reproducible: customer Shopify `10100735082772` ("Pruebas Vadai 2", sin tags, sin email) — el INSERT inicial creó la fila, pero el UPDATE subsiguiente del worker falla repetidamente. El bug NO aparece para customers CON tags (camuflado en pruebas tagged "Gina"/"Regina") porque solo se activa cuando `normalized.tags = []`.
- **Causa raíz:** En `lib/services/last-write-wins.ts`, `isEmptyValue()` retornaba `true` para arrays vacíos `[]` (línea 107: `if (Array.isArray(value) && value.length === 0) return true;`) y luego `normalizedValue = proposalEmpty ? null : proposal.value` convertía ese `[]` en `null`. Cuando `buildFieldProposals` de `lib/inngest/functions/customers.ts` proponía `{ field: "shopify_tags", value: [] }` (customer sin tags), el reconciler producía `patch.shopify_tags = null`. El SQL `UPDATE contacts SET shopify_tags = NULL` violaba el `text[] NOT NULL default '{}'` de la migración 0003. Los 5 retries de Inngest repetían el mismo fallo (el INSERT inicial ya existe, identityMatching lo encuentra, llega al mismo UPDATE roto). NO era race condition — bug determinístico para `tags = []`. El path solo se activa en `customers.ts` (único worker que enruta `shopify_tags` por LWW); INSERTs directos en `orders.ts`, `draft-orders.ts`, `whaapy-contacts.ts` y scripts pasan `[]` literal sin tocar LWW, por eso no se manifestó ahí.
- **Workaround / fix:** En `lib/services/last-write-wins.ts`, agregado `ARRAY_TYPED_FIELDS = new Set(["shopify_tags"])` + helper `emptyValueFor(field)` que retorna `[]` para campos array-typed y `null` para el resto. La línea `normalizedValue = proposalEmpty ? null : proposal.value` ahora usa `emptyValueFor(field)`. Semántica doctrinal "empty overwrites" (R3 "Borrados intencionales propagados") se mantiene intacta — `[]` sigue sobrescribiendo `["X"]` cuando la propuesta es más reciente; solo cambia la representación SQL del "empty" para columnas `text[] NOT NULL`. Tests sintéticos agregados en `tests/last-write-wins-fields.test.ts`: (a) CREATE con `shopify_tags: []` → patch contiene `[]`, no `null`, decision `first_value`; (b) UPDATE con `shopify_tags: []` sobre contact con `["Gina"]` previo → patch contiene `[]`, no `null`, decision `empty_overwrite`.
- **Lección:** la regla de LWW "valores vacíos representan borrado intencional y se almacenan como `null`" asume implícitamente que la columna acepta `null`. Para columnas `NOT NULL` con default no-vacío (típicamente `text[] default '{}'` o `jsonb default '{}'::jsonb`), la representación de "vacío" debe ser ese mismo default, no `null`. Patrón anti-bug general: cuando un schema marca una columna como `NOT NULL DEFAULT X`, el reconciler de LWW debe usar `X` como representación de empty para esa columna, no `null`. Caso adyacente que podría manifestarse en milestones futuros: si M5/M6 introducen otra columna `NOT NULL` con default (ej. `jsonb` de preferencias), agregar al `ARRAY_TYPED_FIELDS` set (o renombrar a `NON_NULLABLE_FIELDS_WITH_DEFAULT` cuando el set crezca más allá de arrays). Lección operativa adicional: bugs determinísticos camuflados por datos de prueba sesgados (en este caso, todos los customers de prueba tenían tags) son la principal razón para tener al menos un test sintético del "happy path mínimo" — un customer sin tags es el caso más simple posible y debía haber estado cubierto desde el primer commit de M3.
- **Auditoría de columnas array `NOT NULL` (post-fix):** búsqueda en `supabase/migrations/` confirmó dos únicas columnas `text[] NOT NULL DEFAULT '{}'`: `contacts.shopify_tags` (afectada, cubierta por el fix) y `orders.shopify_tags` (no afectada — el worker `orders.ts` pasa `shopify_tags: normalized.tags` directamente en INSERT/UPDATE sin enrutar por `reconcileContactFields`; LWW de orders es a nivel registro con `shouldApplyRecordUpdate`). El set `ARRAY_TYPED_FIELDS` keyed por nombre de campo cubre ambas tablas preventivamente si un milestone futuro decide enrutar `orders.shopify_tags` por un reconciler análogo. No hay otras columnas array `NOT NULL` en el schema actual.
- **Acción operativa post-deploy (`Pruebas Vadai 2` y similares):** los dos `shopify_event_id` reportados por el operador (`c6260726-7665-5848-9c62-45218f36b5aa` y `b415447f-4118-54b2-afed-c8cd17f3752d`) muy probablemente ya estén en estado `failed` en Inngest tras agotar los 5 retries (backoff default exponencial agota en ~15 min). Inngest NO reintenta automáticamente runs en estado `failed` — requiere **Replay manual** desde la UI de Inngest (`Dashboard → Functions → shopify-customers-create / shopify-customers-update → Runs → filtrar Failed → seleccionar evento → Replay`). Alternativa equivalente: desde Shopify Admin del customer 10100735082772 disparar "Resend webhook" si Shopify lo permite para customers. Sin uno de estos dos pasos, el contact "Pruebas Vadai 2" quedará en estado parcial: existe en `contacts` con `shopify_customer_id` y `shopify_tags=[]` (del INSERT que sí completó), pero sin el patch de LWW (sin `field_metadata`, sin `last_modified_at` del payload, sin intent de creación en Whaapy). Para validar post-replay: `SELECT field_metadata, last_modified_at FROM contacts WHERE shopify_customer_id = '10100735082772';` — `field_metadata` debe tener entradas por campo y `last_modified_at` debe coincidir con el `updated_at` del payload Shopify.

### `businessId` de Whaapy vive en root del payload, no dentro de `data`

- **Milestone donde se detectó:** M4 (bug productivo detectado durante CHECKPOINT M4, commit `f29bba4` + fix M3 `06c83c9`/`29f78fe`).
- **Síntoma:** Vercel runtime logs muestran 4 POSTs consecutivos a `/api/webhooks/whaapy` con status `200` y mensaje exacto `whaapy_webhook_missing_business_id`. NO hay rastro en `audit_log` porque el endpoint descarta ANTES de auditar (línea ~85 de la versión bug: `console.warn("whaapy_webhook_missing_business_id"); return 200`). Resultado operativo: el contacto creado en Whaapy nunca llega al maestro, R12 nunca dispara, la propagación a Shopify nunca se invoca. Indistinguible de un endpoint que "está caído" desde la perspectiva del operador — el HTTP 200 oculta que el payload se descartó silenciosamente.
- **Causa raíz:** Durante M4 implementation, Claude Code asumió que `businessId` estaba anidado dentro de `data` (path `payload.data.businessId`). El payload REAL que Whaapy entrega tiene `businessId` a NIVEL ROOT junto a `event` y `timestamp`:
  ```json
  {
    "event": "contact.created",
    "timestamp": "2026-05-22T23:28:04.685Z",
    "businessId": "1db0bff4-e554-4a07-9585-faaf93b401f4",
    "data": { "name": "...", "contact_id": "...", "phone_number": "...", "tags": [], "created_at": "..." }
  }
  ```
  Esta estructura está documentada en la doc pública de Whaapy (`/api-reference/webhooks/payloads`) — el ejemplo de payload muestra `businessId` al mismo nivel que `event`/`timestamp`/`data`. El bug se camufló porque (a) los tests sintéticos de M4 también usaban la estructura asumida `data.businessId` (auto-validaban el bug), y (b) el endpoint devuelve 200 incluso cuando descarta — no hay error en la respuesta HTTP que alertara al operador. **Adicionalmente**: el identificador del contacto dentro de `data` también estaba mal — la implementación usaba `data.id`, el payload real usa `data.contact_id` para eventos `contact.*`.
- **Workaround / fix:** En `lib/whaapy/mappers.ts`:
  1. `extractBusinessId(payload)` ahora lee `obj.businessId` (root) en lugar de `obj.data.businessId`.
  2. Los 7 schemas Zod (`WhaapyContactCreatedPayloadSchema`, `WhaapyContactUpdatedPayloadSchema`, `WhaapyContactDeletedPayloadSchema`, los 4 de `conversation.*`) ahora declaran `businessId: z.string()` y `timestamp: z.string().nullish()` a NIVEL ROOT.
  3. Los 3 schemas de `contact.*` renombran `data.id` → `data.contact_id` (consistente con el payload real). Los 4 schemas de `conversation.*` mantienen `data.id` (id de la conversación) y `data.contact_id` (referencia al contacto), que ya estaban correctos.
  4. Nuevo helper `extractTimestamp(payload)` extrae el timestamp del root para trazabilidad opcional.
  En `lib/inngest/functions/whaapy-contacts.ts`: todas las referencias `data.id` y `parsed.data.id` en los 3 workers `contact.*` reemplazadas por `data.contact_id` / `parsed.data.contact_id` (11 ocurrencias). En `tests/whaapy-webhook-endpoint.test.ts`: payloads actualizados a la estructura real (helper `realWhaapyPayload()` con `businessId` en root) + nuevo test de regresión `regresión: businessId DENTRO de data NO debe resolver tenant` que valida el bug nunca vuelve. Comentarios actualizados en `app/api/webhooks/whaapy/route.ts` y `lib/inngest/client.ts`.
- **Lección (path real vs path asumido):** los ejemplos en docs de APIs públicas muchas veces usan placeholders ambiguos (`"uuid"`, `"<value>"`, payloads abreviados con `...`) que no clarifican la jerarquía exacta. Cuando una integración nueva depende del SHAPE EXACTO del payload entregado por un proveedor externo, **el primer test sintético debe construirse desde un payload REAL capturado del proveedor en runtime**, no desde una reconstrucción mental basada en la doc. Patrón operativo: antes de cerrar un milestone de integración inbound, exigir al menos UN webhook real entregado por el proveedor (vía sandbox, tunnel local, o staging) y usar ese JSON exacto como fixture base de los tests. Lo que las docs muestran como `{ "data": { "businessId": "uuid" } }` puede en realidad ser `{ "businessId": "uuid", "data": {...} }` — la indentación del JSON ejemplo en la doc no es vinculante si el modelo de objetos no está explícito en una sección "Schema" separada.
- **Lección (HTTP 200 silencioso encubre descartes):** el patrón "200 + return temprano" para topics/payloads no-procesables se eligió en M3/M4 para no acumular DLQ del lado del proveedor (Shopify y Whaapy reintentan hasta desactivar el webhook tras N fallos). Trade-off: descartes silenciosos son invisibles desde HTTP. Mitigación parcial: el descarte por `missing_business_id` ya emite `console.warn` que llega a Vercel runtime logs — pero no a `audit_log` porque sin tenant resuelto no podemos abrir contexto. Patrón anti-bug futuro: cuando un descarte temprano ocurra >N veces en M minutos para el MISMO evento, escalar a alerta — pero la implementación correcta requiere infra adicional (contador en Upstash con TTL deslizante). Por ahora, los Vercel runtime logs son el canal de diagnóstico operativo cuando un endpoint reporta 200 pero el comportamiento downstream no ocurre.
- **Acción operativa post-deploy:** los 4 webhooks descartados (`whaapy_webhook_missing_business_id` en Vercel runtime logs) NO entraron a Inngest, por lo tanto NO hay run para "replay". Whaapy probablemente ya los marcó como entregados exitosamente (HTTP 200 del lado del endpoint) y no los reintentará. Para validar el fix end-to-end, el operador debe **re-crear el contacto en Whaapy tras el deploy del fix** y verificar: (a) Inngest dashboard muestra al menos un run de `whaapy-contact-created` con status `Completed`, (b) `audit_log` contiene entrada `whaapy_webhook_received` con `topic="contact.created"`, (c) el contact aparece en la BD con `whaapy_contact_id` poblado. Si el operador necesita recuperar los contactos descartados pre-fix, la única vía es manual: identificar los `contact_id` en Whaapy (vía dashboard o `GET /contacts/v1`) y dispararlos por el script `whaapy:configure-webhook` con un endpoint dummy, o editarlos en Whaapy para forzar `contact.updated`. El backfill propiamente dicho es scope de M11.

  Observaciones clave: `address` simplemente NO aparece (omitido, no `null`); `email` viene como `null` explícito; `tags` como array vacío `[]`.
- **Causa raíz:** En `lib/whaapy/mappers.ts`, el helper `WhaapyAddressSchema` estaba declarado como `.object({...}).passthrough().partial().nullable()`. `.nullable()` acepta `null` pero NO `undefined`. En Zod la diferencia es semántica y crítica: `.nullable()` = `T | null`, `.optional()` = `T | undefined`, `.nullish()` = `T | null | undefined`. Cuando Whaapy omite el campo `address` del JSON (porque el contacto no tiene dirección cargada), el parser interpreta `undefined` y falla con `invalid_type` (espera `object`, recibe `undefined`). El mismo bug aplicaba al `WhaapyContactGetResponseSchema` (snapshot del GET de reconciliación de `contact.updated`) que también referenciaba `WhaapyAddressSchema`. El bug se camufló porque (a) los tests sintéticos de M4 (`whaapy-webhook-endpoint.test.ts`) solo validan routing/HMAC/dedup, NO ejecutan el schema completo — el endpoint stubea Inngest con `FakeInngest.send` que solo registra el envío y nunca invoca al worker; (b) los tests de mapper para Whaapy directamente NO existían (el patrón sí existía para Shopify en `shopify-mappers.test.ts`, pero no se replicó al cerrar M4); (c) los payloads de test usaban `realWhaapyPayload()` con la estructura completa pero el endpoint nunca llegaba a parsearlo profundo. El bug solo se manifiesta cuando un payload real omite `address` (todos los contactos sin dirección — caso común en producción).
- **Workaround / fix:** En `lib/whaapy/mappers.ts`, `WhaapyAddressSchema` cambiado de `.nullable()` a `.nullish()` (un solo carácter de diff conceptual). Cubre las dos referencias al schema en una sola edición: `WhaapyContactCreatedPayloadSchema.data.address` y `WhaapyContactGetResponseSchema.address`. Comentario explícito agregado encima del schema documentando la razón y referenciando esta entrada. Resto de los 7 schemas auditados — todos los campos opcionales ya usaban `.nullish()` o `.default([])` correctamente. Nuevo test file `tests/whaapy-mappers.test.ts` que invoca directamente los schemas con (a) el payload real capturado del log (caso mínimo con `address` omitido), (b) un payload completo con todos los campos opcionales presentes para no regresar el caso opuesto, (c) `address: null` explícito (caso adyacente: si el usuario limpia la dirección, Whaapy podría enviar null), (d) edge cases por evento (cada uno con su tolerancia documentada — `assigned_to` permanece required en `conversation.assigned` porque el evento es semánticamente meaningless sin él).
- **Lección (semántica `.nullable()` vs `.optional()` vs `.nullish()` en Zod):** los tres modificadores parecen equivalentes a primera vista pero representan tres conjuntos distintos. `.nullable()` solo acepta `null` (no omisión). `.optional()` solo acepta omisión (no `null`). `.nullish()` acepta ambos. Para integraciones inbound con proveedores externos donde "campo no cargado" puede serializarse como omisión O como `null` según el lenguaje/SDK del proveedor (Whaapy usa Node.js con JSON.stringify que omite `undefined` pero conserva `null`), **siempre preferir `.nullish()` sobre `.nullable()` salvo que haya evidencia mecánica de que el proveedor SIEMPRE envía el campo como null cuando está vacío**. La doc pública rara vez explicita esto.
- **Lección (testing de schemas externos requiere payloads reales en distintos estados de completitud):** el test sintético del endpoint solo valida routing — el schema profundo lo ejecuta el worker downstream. Un test que `mock`ea Inngest con `FakeInngest.send` valida hasta el dispatch, NO el procesamiento. Para integraciones inbound nuevas, el patrón completo requiere DOS niveles de tests: (1) endpoint test (HMAC, dedup, routing — ya existía), (2) **mapper/schema test** que ejecuta `Schema.parse(payload)` directamente con (a) payload mínimo real capturado del proveedor, (b) payload completo con todos los campos opcionales, (c) edge cases observados (campos con `null` explícito vs omitidos). Sin (2), bugs como este pasan verde en CI y solo se descubren en producción tras agotar retries de Inngest. Patrón ya implementado para Shopify en `shopify-mappers.test.ts` desde M3; se replicó para Whaapy con este fix. Aplicable preventivamente a cualquier integración futura (Stripe en V2, etc).
- **Lección (la doc pública NO refleja cómo se serializan campos vacíos):** la doc de Whaapy `/api-reference/contacts/create` enumera campos como `avatar_url`, `custom_fields`, `external_ids`, `notes`, `funnel_stage_id`, `source`, `company`, `address`, `city`, `state`, `postal_code`, `country`, `assigned_agent_id` — pero NO especifica cuáles son omitidos vs enviados como `null` cuando vacíos. Tampoco indica si la estructura de `address` es anidada (`{ street, city, state, country, zip }`) o aplanada (`address`, `city`, `state` como hermanos en `data`). En este caso `.passthrough()` salva el shape desconocido (el worker solo consume `data.address`, ignora hermanos), pero la tolerancia mínima del schema (`undefined` vs `null` vs objeto) es algo que solo el payload real revela. Patrón operativo: para cada campo opcional documentado por el proveedor, **asumir por defecto `.nullish()` en el schema hasta que haya evidencia de que solo manda una de las dos formas**.
- **Acción operativa post-deploy:** los 4 webhooks descartados en este bug (los que llegaron tras el fix de `businessId` y antes del fix de schemas) tienen runs `failed` en Inngest dashboard. Tras desplegar el fix, ejecutar **Replay manual** desde la UI de Inngest (`Dashboard → Functions → whaapy-contact-created → Runs → filtrar Failed → seleccionar evento → Replay`) — los payloads ya están encolados con tenant resuelto, solo falta que el worker los procese con el schema corregido. Alternativa equivalente: re-crear el contacto en Whaapy (lo cual el operador hará para validar end-to-end post-deploy). Para validar el fix: (a) Inngest dashboard muestra el run `whaapy-contact-created` en status `Completed`, (b) `audit_log` contiene `whaapy_webhook_received` Y NO `whaapy_webhook_failed` para el mismo `whaapy_event_id`, (c) el contact aparece en `contacts` con `whaapy_contact_id` y `field_metadata` poblado por LWW.

### Endpoint Whaapy sin visibilidad por audit-only-in-worker pattern

- **Milestone donde se detectó:** M4 (CHECKPOINT post fixes `c650a98` + `c54e9d4`).
- **Síntoma:** tras el fix de schemas Zod, el operador re-creó el contacto en Whaapy para validar end-to-end. Vercel runtime logs confirman 2 POSTs recientes a `/api/webhooks/whaapy` con status 200 sin errores (18:09:30 y 18:11:46). Sin embargo `audit_log` para `organization_id = a1edfbdf-b0a9-45db-a652-5241dc49b48b` está **completamente vacío en los últimos 15 minutos** — ni siquiera aparece `whaapy_webhook_received`. El contact en BD sigue sin `whaapy_contact_id` poblado. Regresión aparente vs los fixes previos donde sí se veía `whaapy_webhook_received` aunque después el worker fallara más adentro.
- **Causa raíz (visibilidad — confirmada):** el audit `whaapy_webhook_received` vivía exclusivamente dentro de `runWhaapyWebhookWorker` (`lib/inngest/helpers.ts:84-95`), que corre como parte de la función Inngest, NO en el handler HTTP del endpoint. La cadena para que `whaapy_webhook_received` aparezca en `audit_log` requería: (1) `inngest.send` resuelve sin throw en el endpoint, (2) Inngest cloud notifica a `/api/inngest`, (3) el SDK valida la firma con `INNGEST_SIGNING_KEY`, (4) el worker arranca, (5) `recordAuditEvent` se ejecuta antes de cualquier throw downstream. **Si CUALQUIERA de los 5 pasos falla silenciosamente, el audit jamás aparece** — y desde la perspectiva del endpoint todo respondió 200. Con `console.warn` como único rastro, el operador queda sin trazabilidad estructurada en BD para diagnóstico.
- **Causa raíz (dispatch — pendiente de confirmar):** la regresión específica (antes veíamos `whaapy_webhook_received`, ahora no) muy probablemente es un dispatch silencioso de Inngest. Hipótesis: `INNGEST_SIGNING_KEY` en Vercel Production no matchea con la signing key actual del workspace de Inngest (rotación silenciosa post-deploy, env var mal seteada en Production environment, función no re-sincronizada tras el push de `c54e9d4`). Los endpoints `/api/inngest` y `/api/webhooks/whaapy` responden correctamente desde producción al probing externo (verificado con `curl`): `X-Inngest-Sdk-Handled: true` en la respuesta del primero, `missing_signature` 400 esperado en el segundo. La confirmación final requiere dashboard de Inngest (ver acción operativa). El fix de visibilidad aquí cierra la brecha diagnóstica independientemente: si tras el deploy hay `whaapy_webhook_received` a nivel endpoint Y `audit_log` no tiene la entrada del worker, sabemos que el problema es 100% dispatch — sin esa señal, era imposible distinguir entre "endpoint roto", "Inngest dispatch roto" y "worker silenciado".
- **Workaround / fix:** en `app/api/webhooks/whaapy/route.ts`:
  1. **Fix primario** — nuevo helper `safeAuditAtEdge(orgId, { eventType, payload })` que envuelve `withTenantContext` + `recordAuditEvent` con try/catch interno (audit no debe bloquear respuesta 200 a Whaapy). El handler invoca `safeAuditAtEdge(org.id, { eventType: "whaapy_webhook_received", payload: { topic, whaapy_event_id, ... source: "endpoint" }})` después de HMAC verify + topic resolution, ANTES de dedup y enqueue. El audit del worker se mantiene intacto — los dos NO son redundantes: el del endpoint prueba "el HTTP llegó y pasó HMAC", el del worker prueba "Inngest dispatchó y el handler arrancó". El campo `source: "endpoint"` los distingue para queries de auditoría.
  2. **Fix secundario 1 (dedup hit)** — path 5 ahora invoca `safeAuditAtEdge(org.id, { eventType: "whaapy_webhook_deduped", ... })` antes de devolver 200 con header `x-centrhub-dedup: hit`. Hace visibles retransmisiones del mismo `X-Webhook-ID` (antes solo se reflejaban en el header, sin rastro en BD).
  3. **Fix secundario 2 (enqueue fail)** — path 7 ahora invoca `safeAuditAtEdge(org.id, { eventType: "whaapy_webhook_enqueue_failed", payload: { topic, ..., error: errMsg }})` antes de devolver 503. Si `inngest.send` throwea (Inngest cloud down, signing key rotada, red), el operador tiene rastro en BD con el mensaje exacto del error.
  4. **Fix secundario 3 (paths sin tenant)** — `extractBusinessId` null y `org not found` no podían escribir audit_log por la constraint `NOT NULL` de `audit_log.organization_id` (migración 0007). Se reforzó `console.warn` con payload estructurado (JSON.stringify de `{event: "whaapy_webhook_discarded", discard_reason, ...}`) para que Vercel runtime logs den señal parseable. Migración para aflojar la constraint a nullable queda en PENDIENTES.md como M4-DT-05.
  5. **Tests sintéticos** — 3 nuevos en `tests/whaapy-webhook-endpoint.test.ts`: (a) happy path → `whaapy_webhook_received` escrito a nivel endpoint con `source: "endpoint"`; (b) dedup hit con mismo eventId 2 veces → `whaapy_webhook_received` x2 + `whaapy_webhook_deduped` x1 (el primer hit pasa por audit edge antes del dedup, el segundo también, y SOLO el segundo escribe deduped); (c) `sendMock.mockRejectedValueOnce(new Error("inngest_unreachable"))` → `whaapy_webhook_received` + `whaapy_webhook_enqueue_failed` con `error: "inngest_unreachable"` + status 503.
- **Lección (diseño del patrón audit-edge):** el endpoint público de un webhook DEBE auditar la recepción a nivel HTTP, independientemente del estado de cualquier sistema downstream (queue, worker, BD). El audit dentro del worker es valioso PERO NO sustituye al audit del endpoint — los dos miden cosas distintas. Si solo se audita en el worker, un bug de dispatch (queue silenciosamente perdida, signing key mismatch, función no registrada) es completamente invisible desde la BD. Patrón aplicable a cualquier endpoint público que enqueue trabajo asíncrono (webhooks de proveedores, signing endpoints, futuros endpoints de Stripe en V2): el endpoint audita "evento aceptado y enviado a procesamiento", el worker audita "evento recibido y procesado". Los dos se cruzan al diagnosticar: ambos presentes = todo OK; endpoint sí + worker no = dispatch roto; ninguno = endpoint roto.
- **Lección (audit-edge no bloquea respuesta):** el audit del endpoint tiene que ser explícitamente non-blocking. Si el insert de `audit_log` falla (RLS, conexión, schema mismatch), el endpoint debe loguear el fallo a stderr y CONTINUAR respondiendo al proveedor — el alternativo (500 a Whaapy/Shopify) cuenta como fallo del lado del proveedor y eventualmente desactiva el webhook tras N fallos consecutivos. El patrón implementado: `safeAuditAtEdge` envuelve toda la cadena en try/catch que solo emite `console.error` en stderr. Coste de perder un audit ocasional < coste de webhook desactivado por el proveedor.
- **Lección (M3 tiene la misma deuda — diferida):** el endpoint Shopify `app/api/webhooks/shopify/route.ts` mantiene el patrón viejo (audit `shopify_webhook_received` solo dentro del worker, vía `runWebhookWorker` en `lib/inngest/helpers.ts:33-43`). No bloqueante porque Shopify funciona hoy y el síntoma operativo no se manifestó en M3, pero es la misma trampa diagnóstica latente: si en algún momento futuro Inngest dispatch falla del lado Shopify, será igualmente invisible. Diferido a M4-DT-04 (PENDIENTES.md) como replica directa del patrón.
- **Acción operativa post-deploy:**
  1. Operador valida (a), (b), (c) del dashboard de Inngest (registro de funciones M4, runs en últimas 4h, env vars `INNGEST_SIGNING_KEY`/`INNGEST_EVENT_KEY` en Vercel Production).
  2. Operador re-crea el contacto en Whaapy.
  3. Verificación esperada en `audit_log`:
     - **Si `whaapy_webhook_received` con `source: "endpoint"` aparece Y el del worker NO**: confirmado dispatch roto. Próximo paso es rotar `INNGEST_SIGNING_KEY` en Vercel y forzar sync de funciones desde dashboard Inngest.
     - **Si los dos aparecen**: dispatch funciona; investigar por qué el contact no se persiste (LWW, error downstream del worker).
     - **Si ninguno aparece**: el endpoint mismo no recibió el webhook (Whaapy no entregó, o request rechazada por middleware/firewall) — chequear primero que el webhook esté configurado en Whaapy con la URL correcta.

### Secret HMAC de Whaapy desactualizado en Vault tras recrear el webhook

- **Milestone donde se detectó:** M4 (CHECKPOINT post fixes `0836b07` audit-at-edge + `57e360b` endpoint raw + `7e7f154` instrumentación exit_reason).
- **Síntoma:** tras desplegar el fix audit-at-edge (`0836b07`), el operador re-creó el contacto en Whaapy esperando ver `whaapy_webhook_received` con `source: "endpoint"` en `audit_log`. El audit seguía sin aparecer. Vercel runtime logs mostraban POSTs con status 200, pero el contact no aterrizaba en BD y los workers de Inngest no se ejecutaban. Patrón observable indistinguible de un dispatch silencioso de Inngest — la hipótesis inicial documentada en la entrada anterior. Más de 8 iteraciones de debugging consumidas en validar signing keys de Inngest, re-deploys, revisar URLs configuradas en Whaapy, sin progreso. El endpoint paralelo `whaapy-raw` (commit `57e360b`) sí registraba los bodies entrantes — confirmando que el HTTP llegaba a Vercel — pero el endpoint productivo seguía silencioso. Solo cuando la instrumentación de exit_reason (commit `7e7f154`) inyectó tags `endpoint`/`exit_reason` en la misma fila de `whaapy_raw_webhooks` que ya capturaba el endpoint productivo, el log mostró `exit_reason: "invalid_hmac"` con el body crudo correctamente entregado por Whaapy.
- **Causa raíz:** durante las iteraciones previas del debugging, el operador había recreado el webhook en el dashboard de Whaapy varias veces. Whaapy obliga a borrar+crear el webhook para cambiar la URL (no permite editar in-place), y cada recreación **genera un secret HMAC nuevo que se muestra una sola vez en el alert post-creación**. La última versión activa del webhook en Whaapy estaba firmando con un secret distinto al que vivía en `organizations.vault_keys.whaapy.webhook_secret` (Vault tenía el secret `88de5c7e...c4dc` del primer webhook). `verifyWhaapyWebhookSignature(...)` rechazaba todos los intentos con `invalid_hmac` y el endpoint respondía 401 — pero en commits previos al fix audit-at-edge el path `invalid_hmac` NO escribía audit_log. El síntoma observable desde el operador era exactamente "200 + audit vacío + contact no entra", camuflando el problema real (401 silencioso por HMAC mismatch). El diagnóstico era complicado porque el fix de visibilidad audit-at-edge requiere que `extractBusinessId` resuelva el tenant ANTES de poder auditar, y la verificación HMAC corre ANTES de eso — por lo tanto el path `invalid_hmac` ni siquiera con audit-at-edge llegaba a escribir en `audit_log` (no había `organization_id` para anclar la fila, y la constraint NOT NULL bloquea NULLs — ver M4-DT-05).
- **Workaround / fix:**
  1. **Diagnóstico definitivo vía instrumentación raw** — commit `7e7f154` agregó columnas `endpoint` y `exit_reason` a `whaapy_raw_webhooks` + tagging desde el endpoint productivo en cada path de salida (`invalid_hmac`, `missing_business_id`, `org_not_found`, `enqueue_succeeded`, `enqueue_failed`, `deduped`). Sin necesidad de tenant resuelto, el insert va con `organization_id = NULL` permitido por la tabla raw (no es `audit_log`). Una sola consulta `SELECT exit_reason FROM whaapy_raw_webhooks ORDER BY created_at DESC LIMIT 5` reveló `invalid_hmac` y zanjó la hipótesis.
  2. **Recuperar el secret correcto** — en el dashboard de Whaapy, el secret ya generado NO se puede consultar a posteriori (es write-once en el alert post-creación). Operativa: borrar el webhook actual, recrearlo capturando el secret del alert, actualizar Vault con SQL: `UPDATE organizations SET vault_keys = jsonb_set(vault_keys, '{whaapy,webhook_secret}', to_jsonb('<nuevo_secret>'::text)) WHERE id = '<org_id>';`.
  3. **Validación post-rotación** — disparar webhook test desde Whaapy → verificar `whaapy_raw_webhooks.exit_reason = 'enqueue_succeeded'` para el último insert + `audit_log` con `whaapy_webhook_received` (endpoint + worker) + contact en `contacts` con `whaapy_contact_id` poblado. En la validación de cierre M4 inbound (22-may-2026, 02:32 UTC) el flujo completó: `event_id 306dde2b-bb55-4652-8b76-c203eb2efd2b`, `contact f38f8f2b-466d-47af-b056-f2e054567d2f` ("Test Nuevo"), `opportunity 1feb0d25-ed96-4ca0-a859-9ceadaf3df13` auto-creada por R12 en etapa "Lead nuevo" del Funnel Venta.
- **Lección (rotación implícita por recreación):** plataformas como Whaapy que obligan a borrar+crear el webhook para cualquier cambio de configuración (URL, eventos suscritos) **regeneran el secret HMAC en cada recreación**. La rotación no es un evento explícito — ocurre silenciosamente desde la perspectiva del operador. Toda recreación de webhook debe ir acompañada inmediatamente del SQL update a Vault y un disparo de validación. Patrón anti-bug: tras CUALQUIER toque al webhook en el dashboard del proveedor, el SOP exige `UPDATE vault_keys` + validación end-to-end como acción atómica, no como pasos independientes que pueden olvidarse.
- **Lección (visibilidad obligatoria desde el primer commit — no como instrumentación posterior):** los endpoints de webhooks inbound son cajas negras sin observabilidad explícita. El operador solo ve el HTTP status code que devolvió el endpoint; el proveedor no muestra el cuerpo de la respuesta ni distingue entre paths internos. **Cada endpoint debe exponer DESDE el primer commit un identificador del path de salida** (campo `exit_reason` o equivalente) escrito a una tabla auditable — no a `audit_log` necesariamente (porque puede no haber tenant resuelto), sino a una tabla operativa que permita correlacionar request crudo con decisión interna. Si esa señal no existe, cada bug downstream del endpoint requiere instrumentación reactiva que cuesta horas de debugging mientras el síntoma persiste en producción. El patrón "200 + return temprano" es necesario operativamente (Shopify/Whaapy desactivan webhooks que fallan repetidamente), pero sin exit_reason auditable el patrón es indistinguible de "endpoint funciona, problema downstream".
- **Lección (endpoint raw paralelo como red de seguridad):** el endpoint raw `/api/webhooks/whaapy-raw` (commit `57e360b`) se diseñó como sink temporal de diagnóstico — capturar request crudo SIN procesar nada, para confirmar que Whaapy realmente entregaba y no era problema de red/firewall/middleware. Operó como pieza CRÍTICA del diagnóstico: sin esa columna independiente del flujo productivo, era imposible aislar "Whaapy no entrega" de "endpoint productivo descarta silenciosamente". Es candidato a permanecer en producción con TTL (ej. 30 días) como red de seguridad para bugs futuros similares — decisión diferida al operador en `PENDIENTES.md` (entrada "Decisión sobre infraestructura de diagnóstico Whaapy raw"). El costo operativo es mínimo (una tabla pequeña con TTL); el valor diagnóstico ya está probado.
- **Lección (audit-at-edge es necesario pero no suficiente):** el fix audit-at-edge (`0836b07`) resolvió la visibilidad para los paths donde `extractBusinessId` resuelve tenant exitosamente. Pero `invalid_hmac` corre ANTES de cualquier resolución de tenant — por arquitectura no puede escribir a `audit_log` (constraint NOT NULL en `organization_id`). M4-DT-05 propone aflojar esa constraint a nullable, lo cual cerraría el gap; mientras tanto, la columna `exit_reason` en `whaapy_raw_webhooks` cubre los paths pre-tenant. Lección general: la observabilidad debe tener una capa que NO dependa de la resolución de contexto multi-tenant — algunos errores legítimos ocurren ANTES de poder anclar la fila a una org.
- **Acción operativa post-fix:** el SOP de rotación de secret HMAC quedó documentado en CLAUDE.md (sección "Operativa Whaapy — rotación de secret HMAC del webhook"). Cualquier operador (Regina, futuro admin de Centr) que toque el webhook en el dashboard de Whaapy debe seguir el SOP de 4 pasos: (1) borrar webhook actual; (2) crear webhook nuevo y copiar secret del alert que aparece UNA SOLA VEZ; (3) `UPDATE organizations SET vault_keys = jsonb_set(...)` con el nuevo secret; (4) disparar webhook test y verificar `whaapy_raw_webhooks.exit_reason = 'enqueue_succeeded'`.

### GET /contacts/v1/{id} de Whaapy envuelve en `{contact:{...}}`, no es flat

- **Milestone donde se detectó:** M4 (CHECKPOINT item 4.2 — validación E2E `contact.updated` inbound).
- **Síntoma:** tras recrear el webhook + rotar secret + fix audit-at-edge, el endpoint `/api/webhooks/whaapy` procesaba correctamente `contact.updated` con `exit_reason = 'enqueue_succeeded'` y el worker `whaapy-contact-updated` arrancaba. Pero el worker fallaba en el paso 2 (GET reconcile) con audit_log `whaapy_reconciliation_failed` y error Zod `[{"expected":"string","code":"invalid_type","path":["id"],"message":"Invalid input"}]`. Tras 5 retries de Inngest el run se mandaba a DLQ. El contact en BD permanecía con los datos previos al edit (el maestro NO se corrompía — `throw` antes de aplicar LWW), pero la propagación a Shopify no ocurría y los nombres de campo editados quedaban desincronizados. Patrón observable indistinguible del bug previo de schemas inbound (commit `c54e9d4`) — misma forma de error Zod, mismo flujo de retries hasta DLQ.
- **Causa raíz (tres hallazgos confirmados con captura real vía `scripts/whaapy/inspect-get-contact.ts`):**
  1. **Path equivocado en el worker reconcile.** `lib/inngest/functions/whaapy-contacts.ts:214` llamaba `GET /contacts/{id}` (sin `/v1`). Whaapy expone DOS APIs distintas en el mismo host: `/contacts/{id}` retorna un shape camelCase envuelto en `{data:{...}}` con campos extra de plataforma Highlevel (`funnelStageId`, `highlevelOpportunityId`, etc.) — es API nueva. `/contacts/v1/{id}` retorna snake_case envuelto en `{contact:{...}, conversations:[]}` — es la API v1 documentada y la única consistente con la convención de webhooks Whaapy (snake_case + `custom_fields` + `phone_number`). El outbound worker `lib/inngest/functions/whaapy-outbound.ts:258` ya usaba `/contacts/v1/{id}` correctamente — la inconsistencia entre los dos workers pasó desapercibida porque el outbound nunca leyó el body de respuesta del PATCH.
  2. **Shape envuelto, no flat.** Incluso con el path `/v1/` correcto, la response del GET viene como `{contact:{id, name, phone_number, custom_fields, ...}, conversations:[]}` — no como objeto plano. El schema `WhaapyContactGetResponseSchema` (`lib/whaapy/mappers.ts:204`) asumía `id` top-level, derivado de la doc pública de Whaapy sin captura real.
  3. **Inconsistencia POST flat vs GET wrapped del proveedor.** `POST /contacts/v1` outbound retorna `{id: "..."}` plano — el código consume `created.id` directo (`lib/inngest/functions/whaapy-outbound.ts:179, 187, 197`) y funciona. ### `x-webhook-id` de Whaapy es persistente por contact, no único por delivery — dedup descartaba updates legítimos

- **Milestone donde se detectó:** M4 (CHECKPOINT item 4.2 — validación E2E `contact.updated` inbound, tras el fix anterior del GET `/contacts/v1/{id}` wrapper).
- **Síntoma:** tras corregir el wrapper del GET reconcile, el operador editó el contact `1e9f3641-...` en Whaapy varias veces seguidas. El primer `contact.updated` procesó correctamente (`exit_reason = 'enqueue_succeeded'`). El segundo y tercer `contact.updated` cayeron sistemáticamente a `exit_reason = 'dedup_hit'` pese a que cada edición generó payloads con `updated_at` distintos. Los datos posteriores al primer update no se sincronizaban a la plataforma. Patrón observable indistinguible de un dedup correcto desde el endpoint (HTTP 200 + dedup hit), pero operativamente erróneo — los updates 2..N son eventos legítimos del usuario, no retransmisiones.
- **Causa raíz (confirmada con captura real vía `scripts/whaapy/inspect-webhook-headers.ts`):** el endpoint usaba el header **`x-webhook-id`** como key de dedup (junto con topic + namespace). La captura de `whaapy_raw_webhooks` reveló que Whaapy **reusa el mismo `x-webhook-id` durante todo el ciclo de vida del contact_id**. En la captura del 23-may-2026 02:30–05:30 UTC, un único `x-webhook-id = 306dde2b-bb55-4652-8b76-c203eb2efd2b` cubrió 5 deliveries con TRES topics distintos (`contact.deleted`, `contact.created`, `contact.updated` x3) — todos del mismo contact. El header que SÍ es único por entrega es **`x-webhook-delivery-id`** (prefijo `whd_*`), que la implementación ignoraba. La discriminación por topic en la dedup key salvó el primer `contact.updated` (key topic-discriminada vs el `contact.created` previo), pero los updates 2..N colisionaron entre sí porque compartían (topic, eventId) idénticos.
- **Workaround / fix:**
  1. **Cambio del header source** — `lib/whaapy/config.ts`: la constante `WHAAPY_EVENT_ID_HEADER = "x-webhook-id"` se renombró a `WHAAPY_DELIVERY_ID_HEADER = "x-webhook-delivery-id"`. Comentario explícito documentando la semántica real y la diferencia vs Shopify (donde `x-shopify-webhook-id` SÍ es por delivery).
  2. **Rename completo `eventId` → `deliveryId` en pipeline Whaapy** — para alinear nombre con semántica y evitar mismatch futuro: `WhaapyWebhookEnvelope.eventId` → `deliveryId` (lib/inngest/client.ts); audit payloads `whaapy_event_id` → `whaapy_delivery_id` (lib/inngest/helpers.ts + app/api/webhooks/whaapy/route.ts); variables locales en el endpoint; helpers internos (`safeAuditUnhandled`, `handleUnhandledEvent`); console logs estructurados. El helper genérico `lib/redis/dedup.ts` mantiene `eventId` como nombre del parámetro (es agnóstico de proveedor) — el call site Whaapy pasa `{ eventId: deliveryId, ... }` haciendo el mapping en la frontera.
  3. **DLQ handler agnóstico** — `lib/inngest/functions/dlq.ts` se actualizó para leer `event.data?.eventId ?? event.data?.deliveryId ?? null`. M3 sigue mandando `eventId`, M4 manda `deliveryId`, el DLQ acepta ambos sin distinguir proveedor.
  4. **Tests sintéticos nuevos** — `tests/whaapy-webhook-endpoint.test.ts`:
     - "regresión M4: 3 deliveries con MISMO `x-webhook-id` pero DISTINTO `x-webhook-delivery-id` → las 3 pasan dedup". Reproduce exacto el bug: tres requests con `x-webhook-id = 306dde2b-...` compartido pero `whd_aaa`, `whd_bbb`, `whd_ccc` distintos → `sendMock` invocado 3 veces, header `x-centrhub-dedup: miss` en las 3 respuestas.
     - "retry del proveedor: 2 deliveries con MISMO `x-webhook-delivery-id` → segundo es deduped". Valida que el dedup sigue funcionando para retries genuinos: dos requests con MISMO `whd_retry_id` → primer respuesta `x-centrhub-dedup: miss`, segunda `x-centrhub-dedup: hit`, `sendMock` invocado solo 1 vez.
  5. **Script de diagnóstico permanente** — `scripts/whaapy/inspect-webhook-headers.ts` quedó en el repo (`whaapy:inspect-webhook-headers`). Lee `whaapy_raw_webhooks` (productive) y agrupa por `x-webhook-id` y por `(topic, x-webhook-id)` para revelar patrones de reutilización del proveedor sin tocar código productivo. Mismo patrón que `inspect-get-contact.ts`.
- **Lección (la semántica de headers de webhooks varía entre proveedores — no asumir convención portable):** el código previo asumía que `x-webhook-id` significa "id único por evento", basado en la convención de Shopify (`x-shopify-webhook-id`) y de la mayoría de proveedores serios. Whaapy NO sigue esa convención — su `x-webhook-id` se comporta como un `resource_id` (identificador del contact o del recurso afectado), y el id único por entrega vive en `x-webhook-delivery-id`. **Patrón operativo a internalizar: antes de elegir un header como dedup key, capturar headers reales de múltiples deliveries del mismo recurso y validar empíricamente cuál es único por entrega.** No basta con leer el nombre del header — la documentación rara vez explica la persistencia del valor.
- **Lección (capturar headers reales antes de elegir dedup key — el script inspect-webhook-headers como patrón):** el bug solo afloró tras múltiples ediciones consecutivas del mismo contact. Tests sintéticos previos validaban "mismo eventId 2 veces → dedup hit" pero **NO** validaban "mismo recurso editado 3 veces → 3 deliveries con headers distintos → 3 enqueues". Esa segunda dimensión requiere captura real porque depende del comportamiento del proveedor, no del código. El script `scripts/whaapy/inspect-webhook-headers.ts` lee `whaapy_raw_webhooks` (que ya persiste todos los headers de cada delivery vía instrumentación 0015/0016) y agrupa por `(x-webhook-id, topic)` revelando colisiones implícitas. **Patrón generalizable: cualquier integración inbound nueva debe (a) capturar todos los headers de cada delivery en una tabla raw, (b) agrupar por candidatos a dedup key para revelar el patrón de reutilización antes de codear el dedup.**
- **Lección (la convención `x-webhook-id` no es universal entre proveedores):** Shopify, Stripe, GitHub, Twilio y la mayoría de proveedores serios usan headers con prefijo `x-<provider>-webhook-id` o `<provider>-event-id` con la semántica "único por entrega". Whaapy rompe la convención al reutilizar `x-webhook-id` por recurso. Esto NO es un bug declarado del proveedor — es el contrato real que entrega, aunque no concuerde con la convención de la industria. **Patrón operativo: para cada proveedor nuevo, el primer test E2E debe validar empíricamente que el header candidato a dedup key efectivamente cambia entre deliveries del mismo recurso.** El test sintético "mismo header X 2 veces → dedup hit" es necesario pero no suficiente; falta "mismo recurso editado 2 veces → 2 headers X distintos" (test que reproduce el bug aquí documentado, ahora en `tests/whaapy-webhook-endpoint.test.ts`).
- **Acción operativa post-fix:** el operador edita el contact `1e9f3641-...` 3-4 veces seguidas en Whaapy. Verificación esperada: (a) `whaapy_raw_webhooks` muestra una fila por edit, todas con `exit_reason = 'enqueue_succeeded'`; (b) `audit_log` muestra `whaapy_webhook_received` por cada delivery (endpoint + worker, un par por edit); (c) cada edit se refleja en `contacts` con `field_metadata` actualizado por LWW; (d) Inngest dashboard muestra un run `whaapy-contact-updated` por edit, todos en status `Completed`. Si Whaapy reintenta un delivery (ej. timeout transitorio), el reintento sí debe caer en `dedup_hit` (mismo `whd_*`) — pero esto es el comportamiento correcto, no regresión.

### Supabase Realtime no entrega eventos al browser sin claim `organization_id` en el JWT

- **Milestone donde se detectó:** M5.
- **Síntoma:** la suscripción `postgres_changes` desde el browser client se establece (callback `SUBSCRIBED`), pero ningún `UPDATE/INSERT/DELETE` de `opportunities` llega al callback `.on(...)`. La fuente operativa (otro navegador o un webhook server-side) sí persiste el cambio en BD, pero el listener nunca lo recibe. Indistinguible de "real-time desconectado", excepto porque el `subStatus` es `SUBSCRIBED` y el polling fallback sí trae el cambio en el siguiente tick.
- **Causa raíz:** Supabase Realtime evalúa RLS en el rol `authenticated` del usuario suscriptor. Las RLS policies de tenant (migración 0009) requieren `organization_id = public.current_organization_id()` para SELECT. La función `current_organization_id()` resuelve el org desde:
  1. setting de sesión `app.current_organization_id` (server-side wrapper — no aplica al browser),
  2. claim `organization_id` del JWT (sesión usuario).
  
  En el flujo actual la org activa vive en cookie `centr_active_org` (cookie-based session, no JWT claim) — el JWT del Supabase Auth solo tiene `sub`, `email`, `role`. Resultado: `current_organization_id()` retorna NULL en sesiones de browser, todas las policies de SELECT evalúan a NULL (≠ org_id), y Realtime descarta cada evento por "no SELECT permission" sin generar logs visibles del lado del cliente.
- **Workaround / fix (parcial — M5):**
  1. **Polling fallback obligatorio:** `usePipelineRealtime` arranca un `setInterval` cada `PIPELINE_POLLING_FALLBACK_MS` (30s) que recarga el estado vía `loadInitialPipelineState` (Server Action — usa wrapper de tenant). Cubre el camino feliz aunque Realtime esté silencioso.
  2. **Indicador visual al usuario:** la suscripción se considera `stale` tras `PIPELINE_REALTIME_RECONNECT_TIMEOUT_MS` sin transitar a `SUBSCRIBED`. El toolbar muestra "Recarga la página" en ese estado, comunicándole al usuario que el live-update no está activo (sin distinguir "Realtime broken vs RLS hole" — el síntoma es igual para él).
  3. **Defensa multi-tenant en el filter:** la suscripción incluye `organization_id=eq.${orgId}` server-side (no negociable — sin esto, el día que el JWT claim se configure, un vendedor de una org podría recibir eventos de otra). Multi-tenant queda doblemente cubierto (filter explícito + RLS pendiente).
- **Lección (el hueco lo cierra un Auth Hook de Supabase, fuera del código):** la fix definitiva requiere configurar un Custom Access Token Hook en Supabase Auth (`postgres_function` que inyecta `organization_id` en el JWT al issue/refresh, leyendo de `memberships` la membership activa del usuario). Es configuración de panel + función SQL — NO es código del repo. Documentado en `PENDIENTES.md` como tarea M5-DT-01 + propuesta de implementación. Mientras tanto, el polling fallback de 30s cubre el camino feliz; el costo operativo es un round-trip cada 30s por usuario activo en el pipeline.
- **Status (cerrado por M5-DT-01):** función SQL creada en migración `0017_custom_access_token_hook.sql` con resolución híbrida (lee `auth.users.raw_app_meta_data->>'active_organization_id'` validado contra `memberships` activos del user, con fallback a la membership activa más antigua). `switchOrganization()` en `lib/actions/auth.ts` espeja la org activa en `app_metadata` vía admin client + fuerza `auth.refreshSession()` para que el JWT se re-emita en el acto con el claim actualizado. **Paso operativo manual obligatorio en Supabase Dashboard → Authentication → Hooks** documentado en `CLAUDE.md` ("Hook de claim organization_id en JWT"). El polling fallback queda intacto hasta M5-DT-03, que lo retira tras validación empírica de delivery consistente vía Realtime.
- **Lección (RLS basada en setting de sesión no aplica a Realtime):** el wrapper `withTenantContext` aplica `set_config('app.current_organization_id', ...)` en server-side queries, pero ese setting NO viaja al subsystem de Realtime — Realtime corre en su propio proceso con su propia conexión a Postgres, y solo lee del JWT. Cualquier RLS que dependa de setting de sesión queda inerte para Realtime. La única vía con sesiones de browser es JWT claim.
- **Lección (postgres_changes filter es defensa server-side, no requiere RLS para funcionar como filtro pero sí para entregar):** el parámetro `filter: "organization_id=eq.X"` en `.on("postgres_changes", ...)` aplica server-side y filtra qué eventos llegan al canal. Pero ese filtro NO sustituye RLS — RLS sigue evaluándose después del filtro y puede descartar el evento. Una integración correcta usa AMBOS: filter explícito por org (defensa multi-tenant) + RLS pasada (entrega real). Sin RLS pasada, el filtro reduce ruido pero entrega cero — situación actual de M5.

### Atomicidad del movimiento de oportunidad emulada en app, no transaccional en BD

- **Milestone donde se detectó:** M5.
- **Síntoma:** no es un bug observable hoy, pero es un trade-off arquitectónico que se documenta para evitar reintroducirlo o malinterpretar el contrato en M6+.
- **Causa raíz:** el prompt M5 prohíbe modificar schema/RLS/data layer M1 ("NO modificar schema, RLS, contexto de tenant, capa de datos de M1"). La operación atómica que el prompt exige (UPDATE opp + INSERT history + INSERT audit_log "o los tres o ninguno") idealmente vive en un RPC `move_opportunity_stage_atomic(...)` con `BEGIN..COMMIT`. Sin RPC, supabase-js / PostgREST no expone transacciones al app, así que cada paso es su propio statement.
- **Workaround / fix (M5):** emulación con compensating revert. `lib/services/pipeline-move.ts:moveOpportunityStage` ejecuta:
  1. snapshot pre-mutación (copia inmutable de la opp con `OpportunityRow`).
  2. UPDATE opportunidad con optimistic lock vía `eq("last_modified_at", expected)` + `.maybeSingle()`. Si 0 rows → `stale_version` (sin mutaciones reales — ni audit ni history).
  3. INSERT audit_log. Si falla → revert UPDATE al snapshot original; no se inserta history.
  4. INSERT opportunity_stage_history. Si falla → revert UPDATE al snapshot original. El audit ya quedó persistido y no se puede borrar (tabla immutable por `tg_block_mutation`); en este caso el peor escenario es una entrada de audit sin contraparte de history — estado correcto en `opportunities`, audit log con ruido conocido.
- **Lección (trade-off documentado):** el camino correcto de mediano plazo es un RPC `move_opportunity_stage_atomic` que vive en una migración futura (M6 o M7 cuando se evalúe junto con el trigger F1→F2 atómico — son problemas hermanos). Mientras tanto, el riesgo real es ínfimo: el paso 4 (INSERT history) es una sola fila plana sin constraints complejos; su tasa de fallo en producción debería ser <0.01%. La defensa de optimistic lock (paso 2) elimina el caso más común de "datos inconsistentes por race" (dos admins editando la misma card). Documentado en `PENDIENTES.md` como M5-DT-02.
- **Lección (compensating revert NO es transacción — entender los modos de falla residuales):** si el revert del paso 4 también falla (caso ultra-raro), la opp queda movida sin entrada de history. Esto es peor que el caso "audit sin history" porque el pipeline en sí queda consistente pero la auditoría no. La verificación operativa de mediano plazo: monitorear un job semanal que detecte `opportunities.stage_id` que cambió respecto a la última entrada de `opportunity_stage_history` y emita alerta. Pendiente para M10 (dashboard de health interna) — fuera de scope M5.

### Contactos Shopify creados vacíos desde webhooks de orders/draft_orders

- **Milestone donde se detectó:** M3 (fix post-entrega — diagnóstico en M6).
- **Síntoma:** de 127 contactos en BD con `shopify_customer_id IS NOT NULL`, solo 53 tenían `full_name`, 45 `email` y 25 `phone`. El resto eran stubs con todos los campos en NULL aunque correspondían a customers reales de Shopify (la tienda no vende productos a clientes anónimos). El stub solo tenía `shopify_customer_id` y `missing_phone=true`; nunca llegaba el dato del nombre/email/teléfono aunque el customer en Shopify sí los tenía.
- **Causa raíz:** dos rutas distintas creaban contactos a partir de webhooks Shopify:
  1. **Ruta correcta:** `customers/create` y `customers/update` (`lib/inngest/functions/customers.ts`) mapeaban el payload completo (`first_name`, `last_name`, `email`, `phone`, `default_address`, `tags`, ...) vía `mapCustomerWebhookToNormalized` y poblaban todas las columnas del contact.
  2. **Ruta rota:** `orders/*` y `draft_orders/*` (`lib/inngest/functions/orders.ts:resolveContactIdForOrder` y `lib/inngest/functions/draft-orders.ts:resolveOrCreateContactForDraftOrder`) extraían SOLO `customer.id` y, cuando no había contacto local, creaban un stub con TODOS los campos editables en `null`. Los schemas Zod (`shopifyOrderWebhookSchema`, `shopifyDraftOrderWebhookSchema`) tipaban el sub-objeto `customer` con un único campo `id` — el resto del body (que Shopify SÍ envía en orders y draft_orders) viajaba en `passthrough` pero el normalizador no lo leía.
  
  Para customers nacidos antes de que Centr Hub estuviera conectado a Shopify, NO había un `customers/create` retroactivo: cuando una orden histórica generaba el webhook, el stub vacío era el ÚNICO registro de ese customer en la BD. Resultado: ~74 contactos quedaron permanentemente vacíos.
- **Workaround / fix:**
  1. **Schema embebido reusable en `lib/shopify/mappers.ts`:** se introdujo `embeddedCustomerSchema` y `mapEmbeddedCustomer(raw)` que extraen el objeto completo del customer (todos los campos que `shopifyCustomerWebhookSchema` ya cubría: `first_name`, `last_name`, `email`, `phone`, `tags`, `state`, `note`, `default_address`, `updated_at`, `created_at`). El subschema usa `id.nullable().optional()` y devuelve `null` si no hay id extraíble (tolerante a edge cases sin romper schemas).
  2. **`NormalizedDraftOrder` y `NormalizedOrder` exponen `embeddedCustomer: NormalizedCustomer | null`** además del `shopifyCustomerId`. El `shopifyCustomerId` queda derivado de `embeddedCustomer` para evitar inconsistencias entre los dos campos.
  3. **Helper compartido `hydrateContactFromEmbeddedShopifyCustomer` en `customers.ts`:** reusa la lógica de `customersCreate` (identity match por phone/email + create-or-link con `buildContactInsert` + LWW por campo con `reconcileContactFields`). NO ejecuta `applyAssignmentFromTags` ni `recordWhaapySyncIntent` — esas son responsabilidades del flow de customers/*, no de orders/draft_orders.
  4. **`resolveContactIdForOrder` y `resolveOrCreateContactForDraftOrder` consumen el helper** cuando `embeddedCustomer` está disponible. El path antiguo (identity match por solo id + stub vacío) queda como fallback defensivo para el caso atípico de `customer.id` presente pero objeto sin datos (no debería ocurrir en Shopify real). La ruta de `customers/create`/`customers/update` permanece intacta.
  5. **Tests sintéticos:**
     - `tests/shopify-mappers.test.ts` extendido con casos `embeddedCustomer hidratado`, `customer ausente → null`, `customer sin id → null`, y `customer mínimo (solo id) → fullName=null pero embeddedCustomer != null`.
     - `tests/shopify-contact-hydration.test.ts` nuevo: ejercita end-to-end el helper con `FakeSupabase`. Verifica creación hidratada, `missing_phone` correcto, customer mínimo (solo id) sin error, initial match con enlace de identidad por phone, y LWW por campo que preserva valor más reciente cuando el order trae customer con `updated_at` viejo.
- **Lección (los webhooks "satellite" de un proveedor traen el body completo del recurso relacionado — no asumir que solo trae el id):** Shopify es un caso particular pero el patrón es general. Cuando un proveedor expone webhooks de `orders/*`, `draft_orders/*`, `subscriptions/*`, etc., y esos recursos referencian a otra entidad principal (customer, product, ...), el payload típicamente trae el SNAPSHOT completo de la entidad relacionada al momento del evento — no solo el id. Pero los schemas Zod tienden a tiparlo apretado (solo `id`) porque "para qué leer más si no lo voy a usar". Resultado: cuando una integración necesita esos datos a posteriori, ya se descartaron. **Patrón operativo: cuando un payload incluye un sub-objeto con id, validar con captura real qué OTROS campos vienen ahí. Si la entidad referenciada tiene un schema dedicado (como `shopifyCustomerWebhookSchema` para customers), reusar ese sub-schema en lugar de re-declarar uno más estrecho — preserva data útil sin esfuerzo adicional, y elimina divergencia entre los dos schemas.**
- **Lección (rutas paralelas de creación de la misma entidad tienden a divergir silenciosamente):** la misma entidad (Contact) podía nacer por tres rutas distintas (`customers/*`, `orders/*`, `draft_orders/*`) y cada ruta tenía su propia lógica de creación. La ruta principal (`customers/*`) estaba correcta; las dos satelitales tenían el bug. El defecto se mantuvo invisible mucho tiempo porque los tests cubrían cada ruta en aislamiento (`customers/*` con payload completo → ✓; `orders/*` con stub vacío → ✓ porque el test no validaba que el stub tuviera datos). **Patrón operativo: cuando una entidad puede nacer por múltiples rutas, factorizar el constructor común a un helper compartido — la divergencia surge precisamente cuando hay 2+ implementaciones independientes de "create X from external payload". El helper común aplica la disciplina de validación una sola vez.** En este fix, `hydrateContactFromEmbeddedShopifyCustomer` es ese helper; el bug correctivo de los ~74 contactos ya creados queda como tarea aparte (script que recorre `shopify_customer_id IS NOT NULL AND full_name IS NULL` y los enriquece via `GET /customers/{id}.json` — mismo path que el backfill incremental).
- **Acción operativa post-fix:** el operador puede confirmar el fix preventivo monitoreando los próximos `orders/*` y `draft_orders/*` que lleguen para customers sin contacto local previo — el contact creado debe tener `full_name`, `email`, `phone` poblados según lo que Shopify devuelva. Para los ~74 contactos vacíos ya en BD, queda pendiente un script correctivo (separado de este fix) que itere por `shopify_customer_id IS NOT NULL AND full_name IS NULL` y los enriquezca con `GET /customers/{id}.json` reusando `mapCustomerWebhookToNormalized` y `hydrateContactFromEmbeddedShopifyCustomer`.

### Teléfono del customer Shopify ignorado cuando vive en `default_address.phone` y no en el top-level

- **Milestone donde se detectó:** M3 (post-rehidratación correctiva — el operador validó dos casos reales sobre la corrida live del script `shopify:rehydrate-empty-contacts`).
- **Síntoma:** después de rehidratar contactos via `GET /customers/{id}.json`, varios quedaron con `phone = NULL` y `missing_phone = true` aunque en Shopify Admin el customer claramente tenía teléfono. Dos firmas distintas confirmadas:
  1. Customer con teléfono en el perfil (campo "Phone" del customer) Y en la dirección — ninguno se importó.
  2. Customer cuyo perfil NO tiene teléfono (solo email) pero la dirección default sí — tampoco se importó.
- **Causa raíz:** `lib/shopify/mappers.ts` leía únicamente el campo top-level `data.phone` (REST `customer.phone`) e ignoraba `data.default_address.phone`. El schema Zod `customerAddressSchema` ya declaraba `phone` como campo opcional de la dirección — el dato venía perfectamente parseado, solo no se leía. Tres funciones tenían la misma omisión:
  1. `mapCustomerWebhookToNormalized` (REST `customers/*` webhooks + script de rehidratación).
  2. `mapEmbeddedCustomer` (customer embebido en `orders/*` y `draft_orders/*` webhooks — el fix preventivo previo lo hereda porque comparte mappers).
  3. `mapCustomerGraphqlToNormalized` (M11 backfill via GraphQL — campo camelCase `defaultAddress.phone`).
  
  Para el caso (1) del síntoma — perfil con teléfono — sigue siendo un misterio menor por qué `data.phone` venía null o vacío, pero la observación operacional es clara: en algunos customers de Shopify el "Phone" del perfil que el merchant ve en la UI realmente vive en `default_address.phone`, no en el top-level. Shopify Admin mezcla ambos campos en el formulario de edición sin distinguirlos visualmente. Para el caso (2) — solo en dirección — es comportamiento normal de customers creados vía checkout sin que el merchant edite manualmente el perfil.
- **Workaround / fix:**
  1. **Helper compartido `pickCustomerPhone(profilePhone, address)`** en `lib/shopify/mappers.ts` con precedencia: si el `profilePhone` tras trim no está vacío, lo usa; si no, cae a `address.phone` (también validando trim). Devuelve `null` si ambos están vacíos/ausentes. No normaliza E.164 — eso es responsabilidad de `normalizePhone` en `identity-matching.ts` downstream.
  2. **Aplicado en las tres funciones** afectadas: `mapCustomerWebhookToNormalized`, `mapEmbeddedCustomer`, `mapCustomerGraphqlToNormalized`. El cambio es de una línea en cada una: `phone: pickCustomerPhone(...)` en lugar de `phone: data.phone ?? null`.
  3. **Cobertura por LWW automática:** el helper de hidratación (`hydrateContactFromEmbeddedShopifyCustomer`) ya pasa el `phone` a `reconcileContactFields` con su `updated_at` de fuente. Idempotencia + LWW siguen intactos — un teléfono más reciente registrado por Whaapy NO se pisa con uno más viejo de Shopify; un campo vacío que ahora aparece con valor se llena por la branch `first_value` (sin metadata previa) o `newer` (con metadata vieja).
  4. **`missing_phone` se autocorrige:** `persistMissingPhoneFlag` se llama al final del helper con `match.normalizedPhone` — el nuevo phone (sea del perfil o de la dirección) entra a `normalizePhone(_, "MX")`; si normaliza a E.164 válido, `missing_phone` queda `false`. Sin acción adicional necesaria.
  5. **Tests sintéticos** en `tests/shopify-mappers.test.ts`: 7 casos para `mapCustomerWebhookToNormalized` (perfil gana, fallback por `null`, fallback por ausencia, fallback por string vacío, ambos vacíos, ambos con whitespace-only, sin `default_address`), 1 caso para customer embebido en order (perfil null + dirección con phone), 3 casos para GraphQL (perfil gana, fallback, ambos null).
- **Lección (Shopify mezcla `customer.phone` y `customer.default_address.phone` sin que el merchant lo sepa):** la UI de Shopify Admin muestra un único campo "Phone" en el perfil del customer, pero la API expone dos campos separados (`customer.phone` top-level y `default_address.phone`). Dónde aterriza un teléfono dado depende de cómo se creó el customer: edit manual del merchant → top-level; checkout-driven → solo en la dirección; checkout + later edit → puede quedar en cualquiera. Asumir que `customer.phone` es la fuente única produce silencio operativo — el teléfono está en BD del proveedor pero no en BD local. **Patrón operativo: para campos que un proveedor expone en múltiples ubicaciones de su modelo (top-level + sub-objeto), siempre leer con fallback explícito y validar contra captura real de varios customers del entorno productivo, no contra doc.**
- **Lección (un mismo bug raíz puede vivir en tres mappers paralelos — buscar siempre los sibling-call-sites):** la misma fórmula `data.phone ?? null` se copió en tres normalizadores distintos (REST customer, embedded customer, GraphQL customer). Cada uno mapea desde una shape distinta del mismo recurso. **Patrón anti-bug a internalizar:** cuando se arregla un bug de mapeo de un campo en una shape, grep por todos los call-sites de ese campo en otras shapes del mismo recurso. Si hay 2+ normalizadores para la misma entidad (común en proveedores que exponen REST + GraphQL + Webhooks), el bug típicamente vive en TODOS ellos — fix uno, fix todos. El helper compartido `pickCustomerPhone` deja la fórmula en un solo lugar para que el próximo cambio (ej. fallback también a `addresses[0].phone` del array de direcciones) tenga un único punto de aplicación.
- **Acción operativa post-fix:** el operador re-ejecuta `npm run shopify:rehydrate-empty-contacts -- --org-slug centr` con el fix aplicado. Los contactos cuyo teléfono vivía en `default_address.phone` ahora se enriquecen correctamente. Los que en la corrida previa se contaron como `genuinely_empty_in_shopify` por culpa de este bug ahora pueden re-procesarse porque el filtro `full_name IS NULL` deja afuera a los que ya tienen nombre (la rehidratación previa SÍ pobló el nombre, solo el teléfono falló). Para esos casos, el operador debe AMPLIAR el filtro o ejecutar manualmente: si quiere re-disparar también para contactos con nombre pero sin teléfono, queda pendiente extender el script con `--include-phone-missing` (fuera de scope de este fix — el path actual cubre la mayoría operacional).

### LWW seal por proposals vacíos — campos quedaban bloqueados de por vida

- **Milestone donde se detectó:** M3 (post-rehidratación correctiva, junio 2026).
- **Síntoma:** 104 contactos en BD productiva con `phone IS NULL` Y `field_metadata->'phone'` poblado con `{source: "shopify", updated_at: T}`. Aunque el customer en Shopify SÍ tenía teléfono válido (verificado vía `scripts/shopify/inspect-get-customer.ts` sobre el customer `9759438635284`: `"+528115708848"` top-level + `"+52 81 1570 8848"` en address — `parsePhoneNumberFromString` confirmó `isValid=true` para ambos), una re-corrida del script de rehidratación no rellenaba el campo: el reconciler descartaba la nueva propuesta como `older_ignored` porque el `updated_at` del customer Shopify NO había avanzado desde la corrida que sembró el sello. Los contactos quedaban con `phone=null` permanente.
- **Causa raíz:** `reconcileContactFields` en `lib/services/last-write-wins.ts` escribía `field_metadata[field]={updated_at, source}` para CUALQUIER proposal, incluso cuando `proposal.value` era vacío Y el valor local también era vacío. Mecánica del sello en código pre-fix:
  1. Stub creado por order/draft-order pre-fix preventivo (o por un `customers/create` con `phone=null`). Field_metadata = `{}`, phone column = null.
  2. Primer intento de hidratación: el mapper devolvía `phone=null` (por algún bug intermedio: mapper que ignoraba `default_address.phone`, normalizador que rechazaba un formato, race transitorio del proveedor, etc.).
  3. Proposal: `{value: null, updatedAt: customer.updated_at, source: "shopify"}`.
  4. Branch `!meta` (first_value): patch.phone = null + nextMeta.phone = `{updated_at: T, source: "shopify"}`. Decision: `first_value`.
  5. Segundo intento (re-fetch con el bug ya arreglado, mapper correcto): proposal.value = `"+528115708848"`, updatedAt = T (mismo customer.updated_at, no se editó en Shopify). 
  6. Branch meta-exists: `isNewer = T > T` → false → `older_ignored`. **Field sealed permanently** salvo que customer.updated_at avance en Shopify o se borre la entrada de meta manualmente.
  
  El bug afectaba a TODOS los campos editables (no solo phone): `full_name`, `email`, `phone`, `address`, `internal_note`, `shopify_state`, `shopify_tags`. Phone fue el más visible porque la rehidratación pasada lo dejó null para ~84% de los contactos (104 / ~127), pero email y nombre tienen el mismo riesgo si alguna combinación de bugs intermedios dispara un proposal vacío.
- **Workaround / fix:**
  1. **Regla anti-sealing en `reconcileContactFields`:** se agregó una guarda temprana en el loop:
     ```ts
     if (currentEmpty && proposalEmpty) {
       decisions.push({ field, applied: false, reason: "noop_both_empty" });
       continue;  // NO patch + NO metadata
     }
     ```
     Ubicada después de `NEVER_OVERWRITE_BY_LWW` y antes de `isInitialMatch`. Cuando el campo local YA está vacío y la propuesta también, el reconciler no escribe nada: ni patch ni metadata. Esto evita que un proposal vacío selle el campo y lo bloquee de por vida.
  2. **Nueva variante en `FieldDecision["reason"]`:** `"noop_both_empty"` (terminal, `applied: false`). Permite a callers/tests/audits distinguir el caso del histórico `older_ignored` y `blocked_external_id`.
  3. **R3 (borrados intencionales propagados) queda intacto.** La rama `empty_overwrite` SIGUE escribiendo patch + metadata cuando el campo local TIENE valor y la propuesta vacía es MÁS RECIENTE — porque ahí el bump de metadata SÍ tiene sentido operativo (evita que un valor más viejo de otra fuente refile el campo después del borrado deliberado). La diferencia clave: la guarda nueva solo dispara cuando AMBOS están vacíos; cualquier transición de "tiene valor → vacío" sigue su camino normal.
  4. **Tests sintéticos:** seis nuevos en `tests/last-write-wins-fields.test.ts` bloque `anti-sealing — fix bug LWW que sellaba campos vacíos`:
     - phone null + propuesta null + sin meta previa → no patch, no meta, `noop_both_empty`.
     - phone null + propuesta null CON meta previa stale → meta NO se actualiza, queda intacta (no re-sella ni desbloquea — el desbloqueo es operativo aparte).
     - valor real más reciente sobre phone null + meta stale → SE aplica como `newer` (confirma que el path de re-fill sigue funcionando con timestamps avanzados).
     - anti-sealing dentro de match inicial Shopify-priority cuando ambos vacíos → mismo `noop_both_empty`, no sella.
     - R3 con campo POPULATED + propuesta vacía MÁS RECIENTE → `empty_overwrite` + meta avanza (R3 intacto).
     - R3 con campo POPULATED + propuesta vacía MÁS VIEJA → `older_ignored` (R3 sigue siendo direccional).
     Además se reescribió el test legacy `"shopify_tags vacío en CREATE produce []…"` para reflejar el nuevo comportamiento: la regresión NOT NULL queda cubierta por el hecho de que el patch ahora NO incluye `shopify_tags` (la columna ya tiene `[]` desde `createContact`); el test también verifica explícitamente que `nextFieldMetadata.shopify_tags` NO se escribe.
- **Cómo distinguir "vacío legítimo" de "vacío por fallo" sin romper R3:** este fue el ejercicio analítico central. Tres observaciones que llevaron a la solución:
  1. **El reconciler NO necesita distinguir las dos causas para tomar la decisión correcta.** Ambos casos ("fuente genuinamente no tiene el dato" y "el dato venía pero se perdió en el procesamiento") merecen el MISMO tratamiento: no sellar. La diferencia operativa solo aparece downstream (cómo logueamos, cómo alertamos), pero para LWW el resultado es idéntico.
  2. **R3 NO se trata de "vacío siempre se aplica".** R3 dice: "campo vacío en update reciente SÍ sobrescribe (el usuario pudo haber borrado deliberadamente)". El "sobrescribe" implica que HAY algo que sobrescribir — un valor previo. R3 no especifica qué hacer cuando no hay nada que sobrescribir (vacío → vacío). El silencio doctrinal en ese caso permite la elección de "no-op" sin contradecir R3.
  3. **La asimetría es la solución.** Vacío sobre POBLADO escribe metadata (R3 — preserva el borrado intencional para que valores viejos no refile). Vacío sobre VACÍO no escribe metadata (anti-sealing — preserva la posibilidad de fill futuro). La asimetría es la lógica correcta porque la metadata existe para PROTEGER información — proteger un vacío no aporta nada operativo, solo bloquea repair.
- **Lección (el sello silencioso es un anti-patrón general de LWW):** cualquier implementación de LWW por-campo que escriba metadata indistintamente para values vacíos y no-vacíos crea esta clase de bug. La metadata es semánticamente "esta fuente vio este valor en este momento" — pero para un valor vacío, esa información es operativamente neutra (no hay nada que defender). Sellarla solo crea acoplamientos no intencionales. **Patrón anti-bug a internalizar:** en cualquier reconciler con LWW, distinguir desde el primer commit entre "vacío sobre poblado" (write meta para preservar el delete) y "vacío sobre vacío" (no-op — preserva la posibilidad de fill futuro). La regla "siempre escribir meta" es seductora por simplicidad pero produce sellado permanente en cualquier flujo donde el proposal puede venir vacío por causas no-deliberadas (race conditions, normalizadores con bugs, parsers que fallan).
- **Lección (los tests sintéticos con setups artificiales camuflan bugs reales):** el test legacy `"borrado intencional propagado"` usaba `internal_note: ""` (vacío) como estado inicial y proponía `value: ""` (vacío) — y aceptaba decision `empty_overwrite`. El nombre del test sugería que verificaba R3, pero el setup ejercitaba la rama empty-on-empty (el bug). Pasaba con la implementación pre-fix porque la rama meta-exists fluía a `isNewer → empty_overwrite` y bumpeaba la meta sin tocar la columna. **Patrón anti-bug:** un test de R3 (borrado intencional) DEBE arrancar con un valor poblado en el estado inicial. Si arranca con vacío, no está verificando R3 — está verificando el meta-bump del sellado, que es exactamente lo que queremos evitar. Se reescribió ese test con `internal_note: "VIP cliente"` como estado inicial; ahora ejercita R3 de verdad.
- **Acción operativa post-fix (correctivo aparte, NO incluido en este commit):** los 104 contactos ya sellados quedan bloqueados — el fix detiene la sangría pero no los desbloquea. Para liberarlos hace falta un paso correctivo separado, dos opciones:
  1. **SQL one-shot** que limpia la entrada `phone` del `field_metadata` para contactos con `phone IS NULL AND field_metadata ? 'phone'`:
     ```sql
     UPDATE contacts
     SET field_metadata = field_metadata - 'phone'
     WHERE organization_id = '<org_id>'
       AND shopify_customer_id IS NOT NULL
       AND phone IS NULL
       AND field_metadata ? 'phone';
     ```
     Después re-correr `npm run shopify:rehydrate-empty-contacts -- --org-slug centr`. La nueva propuesta entra como `first_value` (sin meta previa) y se aplica con el nuevo `pickCustomerPhone` (que ya lee `default_address.phone`).
  2. **Editar cada customer afectado en Shopify Admin** para avanzar `customer.updated_at` y dejar que un re-fetch entre como `newer`. Menos práctico — son 104 ediciones manuales.
  
  La opción (1) es estándar y reversible (si algo sale mal, el SQL deja la columna `phone` igual; solo borra la entrada de meta, que es lo que estaba bloqueando). Pendiente de autorización del operador para ejecutarla. El mismo razonamiento aplica a `email` y `full_name` si surgen casos sellados — el SQL puede extenderse para limpiar múltiples keys del meta en una sola corrida.

### `normalizePhone` perdía teléfonos en silencio bajo tsx por bug de bundling de `libphonenumber-js`

- **Milestone donde se detectó:** M3 (post-fix anti-sealing + cleanup de los 104 contactos sellados, junio 2026).
- **Síntoma:** después de aplicar el fix anti-sealing y limpiar `field_metadata.phone` de los 104 contactos sellados, una re-corrida de `npm run shopify:rehydrate-empty-contacts` reportó "enriched" para todos los contactos PERO la columna `phone` quedó `NULL` para TODOS. El audit log decía `had_phone: true` (Shopify SÍ devolvía teléfono válido — verificado con `inspect-get-customer` para Sergio: `+528115708848` top-level + `+52 81 1570 8848` en address). Tests sintéticos de `normalizePhone` bajo Vitest pasaban perfecto (`normalizePhone("5512345678") → "+525512345678"`). El bug solo se manifestaba bajo el runtime real del script.
- **Causa raíz:** combinación de tres factores que se enmascaraban entre sí:
  1. **`libphonenumber-js@1.11.20` es un paquete "dual" con `"type": "module"` en `package.json` Y exports CJS** (`"exports": {".": { "import": "./index.js", "require": "./index.cjs" }}`). El bundle CJS (`index.cjs` → `min/index.cjs.js`) carga la metadata vía `var metadata = require('../metadata.min.json')` al evaluarse el módulo, y la pasa como tercer argumento a cada función mediante un wrapper `call(func, args)`.
  2. **`tsx@4.19.2` bajo Node 24 tiene un bug en el loader CJS/ESM** para JSON requeridos desde paquetes con `"type": "module"`. El `require('../metadata.min.json')` devuelve `undefined` en lugar del objeto JSON parseado. Cuando el wrapper push-ea `metadata = undefined` y la librería interna hace `metadata.countries.hasOwnProperty(country)`, explota con `TypeError: Cannot read properties of undefined (reading 'hasOwnProperty')` en `source/metadata.js:510:28`. Reproducible con `npx tsx -e 'require("libphonenumber-js").parsePhoneNumberFromString("+528115708848","MX")'`. Plain `node -e ...` y Vitest cargan el mismo bundle sin problemas — el bug es exclusivo de tsx.
  3. **`normalizePhone` tenía un `try { ... } catch { return null; }` que se tragaba TODA excepción.** El TypeError inesperado se convertía en `null` silenciosamente. El proposal del reconciler quedaba `{ value: null, ... }`, la rama anti-sealing del fix previo lo descartaba como `noop_both_empty`, y el teléfono nunca llegaba a la BD. Indistinguible de "Shopify no devolvió teléfono" o "número genuinamente inválido" — exactamente la clase de fallo silencioso que el catch debía prevenir.

  **Por qué los tests no lo detectaron:** Vitest usa Vite (esbuild) con un loader diferente. Vitest cargaba `libphonenumber-js` y la metadata correctamente, y los 8 tests de `normalizePhone` pasaban siempre. El código productivo (webhooks bajo Inngest + Next.js) tampoco lo sufría — Next.js usa webpack/SWC que también carga la metadata bien. Solo los scripts `tsx` (operación manual del operador) estaban rotos. Los tests cubrían dos runtimes pero NO el tercero donde vivían los scripts.

- **Workaround / fix:**
  1. **Bypass del auto-loader de metadata** — `lib/services/identity-matching.ts` reemplaza los imports:
     ```ts
     // Antes (top-level — usa require dinámico de metadata):
     import { parsePhoneNumberFromString, type CountryCode } from "libphonenumber-js";
     // Después (core + import explícito del JSON):
     import { parsePhoneNumberFromString, type CountryCode, type MetadataJson } from "libphonenumber-js/core";
     import metadata from "libphonenumber-js/metadata.min.json";
     ```
     `parsePhoneNumberFromString` ahora se invoca con `(trimmed, defaultCountry, metadata as MetadataJson)`. Los tres runtimes (Next.js, Vitest, tsx) cargan el JSON vía import ESM estándar — no hay `require` dinámico, no hay interop bug.
  2. **`normalizePhone` distingue invalid-number-silencioso de excepción-inesperada-ruidosa:**
     ```ts
     let phone: ReturnType<typeof parsePhoneNumberFromString>;
     try {
       phone = parsePhoneNumberFromString(trimmed, defaultCountry, metadata);
     } catch (err) {
       // parsePhoneNumberFromString NO debería tirar — devuelve undefined
       // para inputs inparseables. Si llegamos acá es bug del bundler,
       // metadata corrupta, o regresión de la librería. NO se debe tragar.
       console.error("normalizePhone: excepción inesperada de parsePhoneNumberFromString", {
         rawSample: trimmed.slice(0, 32),

     }
     ```

- **Lección (los tests verdes bajo un runtime NO garantizan que el código funcione bajo otro runtime, especialmente con paquetes dual-ESM/CJS):** este bug vivió oculto porque el código pasaba por dos runtimes (Next.js + Vitest) que cargaban `libphonenumber-js` correctamente. El runtime donde sí fallaba (tsx) no tenía cobertura sintética. **Patrón anti-bug:** para código que se ejecuta en MÚLTIPLES runtimes (producción + tests + scripts de operaciones), agregar al menos un smoke test que ejercite el camino crítico bajo el runtime de scripts. Para Centr Hub esto significa: cualquier función importada por un script en `scripts/` debe tener al menos un caso ejercitado bajo `tsx` antes de declarar el fix completo. El smoke test no necesita ser parte de la suite — basta con un `npx tsx -e "..."` o un `.tmp-*.ts` corrido y borrado durante la validación. Pero debe correrse explícitamente, no inferirse a partir de Vitest.

- **Lección (catch silencioso es un anti-patrón de seguridad/debugging — el catch DEBE distinguir esperado de inesperado):** el `try { ... } catch { return null; }` original era idiomático y se sentía defensivo, pero convertía CUALQUIER error (incluyendo TypeErrors de bundling, OutOfMemory, ReferenceError) en `null` silencioso. La distinción correcta es: si la función llamada está documentada para NO lanzar excepciones en condiciones de uso normal (como `parsePhoneNumberFromString` que devuelve `undefined` para inputs inparseables), entonces un `catch` significa "algo del runtime está mal, no del input". Esos catches deben loguear + propagar, NO tragar. **Patrón:** cuando una función documenta su forma de comunicar fallos esperados (return null, return undefined, return Result type), el try/catch debe asumir que solo atrapará lo INESPERADO — y lo inesperado merece visibilidad, no silencio. El `try/catch` se reserva para auténticos errores de runtime que no son parte del contrato.

- **Lección (paquetes con `"type": "module"` y exports CJS son una fuente recurrente de bugs de loader — preferir subpaths explícitos o imports parciales):** el bundle top-level de `libphonenumber-js` confía en un require dinámico de JSON que distintos loaders manejan distinto (Node CJS clásico funciona, Vite funciona, Next.js webpack funciona, tsx 4.19.x rompe). Cuando una librería ofrece subpaths como `/core` que evitan el auto-loader y permiten import explícito del recurso (en este caso `metadata.min.json`), preferir ese path. Es más verboso pero elimina la dependencia del comportamiento del loader. **Patrón:** ante cualquier paquete con `"type": "module"` que también ofrezca exports CJS y carga recursos no-JS internamente (JSON, .wasm, .node), investigar si tiene un subpath "core" o "without-metadata" antes de usar el top-level. El extra verbosity se paga una vez al integrar; el debugging de un bug de loader se paga muchas veces.
